## 零、三十秒版

```
技能 Skill     = 零件（固有效果 + 规则 + 阶段 + 代价）  ← 玩家编辑的是它，它可以很歪
术式 Technique = 编排（组合 + 条件 + 修饰技能）        ← 释放的是它，它必须配平到 0

账 = 现在的技能 − 出厂版那一份。（宗旨：不动任何滑块，点数就是 0）
负 = 消耗额度（更强）    正 = 提供额度（更弱/更慢/更贵）
基点（default-values.md 那张表）只是写内容的**标尺**，不进账。
```

## 一、点数的宗旨

### 1. 每个可调值都有一个默认值，在默认值下点数是 0

- **结论**：**所有点数相关的可调整的值，都具有一个默认值，在这个默认值下点数是配平为 0 的。**
- **出处**：`schema/README.md` §五「宗旨」（L152–L158，原文引用）；
  `schema/skill-schema.ts` 文件头；`technique-system/README.md`（编辑器文案那段 L180–L198）；
  `docs/default-values.md` L3–L7。**首次写入**：日志 29。
- **为什么**：`✓` 玩家 2026-09-21 亲自定的宗旨，要求"把这句话记入文件作为宗旨"。
  它后来被当作**铁律**：曾经开过一次口子（`factoryDebt`），当天就撤了（见第 3 条）。

### 2. 那个「0」是**对着每个技能自己的出厂数值**算的，不是对着全局标准表

- **结论**：**账 = 现在的技能 − `content/skills/*.json` 里那一份**（逐条相减，认 id）。
  全局标准表（`docs/default-values.md`）只是**写内容时的强度标尺**，**不参与算账**。
- **出处**：`schema/README.md` L160–L169；`src/pricing.ts` 的 `skillLedger`
  （L1376–L1401，文件头 L29 也写着）；`docs/default-values.md` L9–L23（那张"谁定 / 参不参与算账"的表）。
- **为什么**：`✓` 玩家原话（日志 29 §六）：「（默认值从哪来）**每个技能自己定（内容里的就是默认）**」。
  ⚠ 在这之前"0 点"有三种互相矛盾的读法 —— "每个**可调值**有个默认档" /
  "每个**技能**默认为 0" / "出厂**零件**可以歪"，三者在文档上长得一模一样，
  在代码里却是三种完全不同的实现（日志 30 §三）。
- **⚠ 副作用（当时当面算给玩家看过）**：出厂内容会**全部变成 0 点**、血契会**没有出厂消费者**了。
  玩家的选择是"就这么做，并且这一轮就把技能编辑器做成真的" ——
  **一个全是 0 的经济系统，只有在玩家能改东西之后才活**（日志 30 §三）。

### 3. 账从「绝对强度」改成「相对模板 / 出厂值」

- **结论**：**`priceSkill`（绝对账）留着，但身份降成"内部强度标尺"；
  玩家看到的、判配平用的是 `skillLedger`（相对账 = 现在 − 模板）。**
- **出处**：日志 30（整篇，尤其 §二.1 和 §三）；`src/pricing.ts` L1346–L1401
  （`priceSkill` 的注释明说"术式账和编辑器要用 `skillLedger`"）；
  `technique-system/README.md` L195–L198；`schema/README.md` L179–L180。
- **为什么**：`✓` 因为宗旨把"默认值"定成了每个技能自己的出厂数值，绝对账就**不再是配平判据**了。
  ⚠ 而且它**露馅过**：术式编辑器列表上写着"魔法飞弹 −0.7"，**而账上根本没有这一笔** ——
  两个数对不上，玩家看的是两个自相矛盾的数字（日志 32 §二.3 末段）。
- **⚠ 连带的地震**：`npm run calibrate` 原来靠"出厂技能恰好都该是平的"来拟合汇率，
  现在这句话**按定义**不成立了 → 汇率要由玩家**声明**（锚点表 `content/anchors.json`），
  而不是从内容里拟合出来。**锚点表至今没写，所以 calibrate 的 `--write` 不许用**
  （日志 30 §六.3、`docs/default-values.md` L108–L109）。

### 4. 出厂内容全是 0 点，**一个例外都没有**；变体的账永远对着**最初那个基础技能**算

- **结论**：① 没被改过的技能账是空的；② 从**变体**再"另存为"出的新变体，
  `basedOn` 仍然是**最初那个基础技能**（不是上一份变体）。
- **出处**：`schema/README.md` L182–L194；`src/pricing.ts` L1412–L1417（`priceTechnique` 的注释）；
  `docs/glossary.md` L124–L125、L148；`schema/skill-schema.ts` L936–L953（`factoryDebt` 的墓碑注释）。
- **为什么**：`✓` 玩家两句话：「**负债件的变体不一定是负债件**」「（宗旨）应该是**铁的**」。
  ⚠ 变体一旦成链，宗旨就断了：A 偏离 +5、从 A 派生的 B 再 +5，而 B 只显示 +5、实际偏离出厂 +10
   —— 数字看起来正常，错得很安静（日志 32 §二.2）。
- **⚠ 这一条推翻过两件事**，见 §冲突 与 §七。

## 二、为什么砍掉手写的 `points`

### 5. 点数**不存进 JSON**，全部由内容推导

- **结论**：**删掉 `Rule.points` / `Phase.points` / `StatusDef.points`** ——
  点数 = `src/pricing.ts` 拿内容算出来的函数。改数值，点数自己跟着变。
- **出处**：日志 01 §改了什么.2；`src/pricing.ts` 文件头 + `balance.json` 的
  `rates._comment`（"点数由内容推导（见 src/pricing.ts），你改数值点数就跟着变"）；
  当前实现在 `web/src/leaves.ts` L295–L304（`SKIP_KEYS` / `SKIP_SUBTREES` 的注释）。
- **为什么**：`✓` **原理性错误，不是实现 bug** ——
  ⚠ **"玩家在编辑器里把「30 伤害」拖成「300 伤害」，点数纹丝不动 —— 等于可以白嫖。"**
  手写的价格表和数值是**两份会漂移的东西**（日志 01 §二）。
- **这个坑又犯了两次（同类、不同轴）**，都记着：
  - ⚠ **射程是免费的**：裂地斩的扇形半径从 2.5 米拖到 12 米，**账面纹丝不动**（日志 18 L115）。
  - ⚠ **`factoryDebt` 差点重犯**：它当时设计成"布尔标记"，就是因为
    "手写的数字会和内容漂移（伤害 200 → 300，欠的点数纹丝不动）——那正是 `pricing.ts` 开头记着的那个坑"（日志 30 §二.3）。
- **规矩**：**编辑器里点数一个滑块都不该有**（它是算出来的，不是调的）。

## 三、⭐ 前摇 / 冷却 / 耗能的定价（**当前最要紧的一条**）

> ⚠ 这一节把「**已经定下来的**」和「**没找到的**」分开写清楚。
> **如果你只想知道"取消前摇该怎么算"——答案是今天没有答案，见 §3.7。**

### 3.1 方向：时间、能量、冷却、生命都是**代价** → **提供额度（正）**

- **结论**：`扣能量 E → +E / energyPerPoint`；`冷却 C 秒 → +C × cooldownSecondPerPoint`；
  `阶段时长 D 秒 → +D × phaseSecondPerPoint`（**前摇后摇本身就是代价**）；
  `扣生命 H → +H / hpPerPoint`。**越长 / 越贵 = 越多的额度。**
- **出处**：`src/pricing.ts` 文件头 L64–L78（公式段）+
  `pricePhase()` L1051–L1065；`balance.json` 的 `rates` L13–L38。
- **为什么**：`✓` 这是"额度账"的定义 —— **负数 = 效果消耗的额度，正数 = 代价提供的额度**。
  唯一反过来的是"打断等级"：越扛得住越是收益（消耗额度）。
- **⚠ 符号被改错过一次，玩家纠正了两次**（日志 03 §1）：
  玩家说"买卖规则位得点数的正负反了"，执行者理解成**整本账反了**、全对调，
  于是**把超模的判据也翻反了**。玩家第二次纠正：「**点数为负值的才是超模技能**」。
  **教训：账本的方向是从玩家那一侧定的，不能因为一行看着别扭就整本翻。**
  佐证：编辑器 CSS 里绿色那条本来就叫 `.gain`、红色叫 `.cost` —— 改回来之后颜色自己就对上了。

### 3.2 **前摇能不能调到 0？** —— 取决于你问的是哪一件事（三件事被混在一起了）

- **结论**：**"0" 有三种含义，历史上分别定过；这三条互相不完全一致，下面照实并列。**

| 你想要的"0" | 有没有定？ | 出处 | 说明 |
| --- | --- | --- | --- |
| **0 = "无前摇"这一档（拿点数换掉前摇）** | ✅ **定过** | `docs/default-values.md` L81–L90 | 四档里的 **「无」**：**消耗额度**（比标准快，是好处）。⚠ **还没实现** |
| **0 = 不写这个字段（中性点）** | ✅ 定过，**但被否定了** | `schema/README.md`；日志 29 §一 | 宗旨**明确否定了**"不写就是 0"这套：⚠「时长/能量/冷却**写了就提供额度**……它们的"中性点"是"不写"（0）—— **那不叫默认值，那叫没有代价**」 |
| **0 = 引擎层面的 0 秒阶段** | ⚠ **踩过坑，被主动钳掉了** | `src/sim/cast.ts` L121–L131（`attackSpeedOf`） | `windup: 0` 会让阶段时长变成 0 → **阶段不需要 tick 就完成、等于瞬发**，而且 `advancePhase` 里**可能一个 tick 走完整个术式**。所以攻速倍率**钳到 0.2~5** |

- **⚠ 要点**：**编辑器今天给不出"0 秒前摇"这个值。**
  阶段时长走点表 `VALUE_SETS.duration = [-1, 0.1, 0.2, 0.3, 0.5, 1]`
  （`web/src/leaves.ts` L114–L116）—— **里面没有 0**。倒是有 `-1`，但 `-1` 是**蓄力**哨兵值
  （时长由玩家控制），**不是"没有前摇"**。
- **⚠ 而 `schema` 这一层没有拦**：`Phase.duration: number`（`schema/skill-schema.ts` L687–L691）
  的注释只说"蓄力阶段可以设 -1"，**没有任何下限约束**。
  ⇒ 也就是说 **`0` 现在既写不出来（点表挡着）也没被禁止（schema 不拦），
  而一旦绕过点表写进去，引擎会把它当瞬发处理，定价却照 `0 × phaseSecondPerPoint = 0` 算 —— 两头都不报错。**

### 3.3 **有没有档位？是多少？每档值多少点？**

- **结论**：**档位定过：`无 / 1× / 3× / 9×` 四档（几何级数）。但"每档值多少点"没有数值互表 ——
  它是靠 `phaseSecondPerPoint` 那一根汇率线性算出来的，而那条汇率今天没有有效的标定来源。**
- **出处**：`docs/default-values.md` §「阶段时长的档位（玩家 2026-09-21 定的）」L81–L93；
  汇率在 `balance.json` 的 `rates.phaseSecondPerPoint = 0.863`；
  算法在 `src/pricing.ts` 的 `pricePhase()`（`duration × phaseSecondPerPoint`）。
- **⚠ 档位一共改过三版**（同一个问题上玩家改了两次口，按时间）：

| 版本 | 内容 | 出处 | 哪个更新 |
| --- | --- | --- | --- |
| v1 | "调成**有和无二选一**，选有就是默认值" | 日志 29 §四（L84） | 最旧 |
| v2 | "**不调成二选一了，用三选一吧：无、默认值、默认值的 3 倍（或更多倍？）**" | 日志 29 §五（L93） | 中 |
| v3 ⭐ | "甚至可以是**无、1\*、3\*、9\***，因为玩家调这个可不是为了手感，而是**获取大量点数**" | 日志 29 §六（L132）+ `docs/default-values.md` L83 | **最新** |

- **为什么做成几何级数**：`✓` 玩家动这个滑块的目的**就是换点数** ——
  ⚠「倍率是**几何级数**，不是「±0.1 秒」那种微调……**所以档位之间要拉得开**」
  （`docs/default-values.md` L92–L93）。
  这与别处的点表原则（"大部分三五个取值""夹在中间那一格不是决策"）是**同一条哲学的两个方向**：
  **要换点数的轴 → 拉开；只影响手感的轴 → 收窄并剪掉中间格。**
- **⚠ 每档的具体点数：没找到。** 文档只给了**方向**（消耗 / 0 / 提供 / 提供很多），
  没给"无 = −N 点、3× = +M 点"的数值表。见 §八.2。
- **⚠ 这张点表从来没实现**：从日志 30（L171）到日志 37（L95）**连着 8 轮欠账**都写着
  "阶段时长的 **无 / 1× / 3× / 9×** 四档"，至今仍是 ⬜
  （`docs/default-values.md` L107）。

### 3.4 时间类的"标准值"（**是标尺，不进账**）

- **结论**：标准前摇 **0.3 秒** / 命中 **0.2 秒** / 后摇 **0.2 秒**；
  能量代价基准 **0（不花）**；冷却基准 **0（无冷却）**。
- **出处**：`docs/default-values.md` §二「时间与代价」L68–L79。
- **为什么**：`✓`「（默认值从哪来）**每个技能自己定（内容里的就是默认）**」——
  这张表是给作者写新技能用的**尺子**（"不然后写的技能会越写越强或越写越弱"），
  ⚠ **不产生任何点数**（`docs/default-values.md` L9–L23 那张表把这件事钉死了）。
- **⚠ 这三条玩家自己就存疑，原话记在 `docs/default-values.md` §四（L113–L124）**：
  - 「**冷却的标准值**：真的是「无冷却」吗？—— **出厂内容里几乎每个技能都有 2~20 秒冷却。**」
  - 「**能量代价的标准值**：真的是「不花」吗？还是「一个普通技能默认花 10」？」
  - 「**前摇 / 命中 / 后摇** 的标准时长是不是应该**按机制分开**（打人的招适合 0.3/0.2/0.2，
    位移的招适合 0.1/0.1/0.1）？还是一律一套？」
  ⇒ **这三条至今没有答复。** 见 §八.3。

### 3.5 蓄力阶段（`duration: -1`）**自己有一档价**

- **结论**：蓄力阶段不按秒算，而是**一笔固定价** `chargePhasePerPoint = 3.673`。
  `pricePhase()`：`duration < 0 → +chargePhasePerPoint`，否则 `+ duration × phaseSecondPerPoint`。
- **出处**：`src/pricing.ts` L1054–L1056；`balance.json` `rates.chargePhasePerPoint`。
- **为什么**：蓄力阶段**没有固定时长**（玩家按住多久就多久），所以只能用固定价近似；
  注释写的是"蓄力阶段也是时间，**玩家得按住键等**"。

### 3.6 攻速倍率（`weapon.windup`）**乘所有阶段时长**，不是只乘前摇

- **结论**：`weapon.windup` 是**术式级攻速倍率**，`cast.ts` 里 `phase.duration * cast.speedScale` ——
  **乘的是每一段**，不只是前摇。而且**在施法瞬间锁住**（半路换武器不该让这一刀变速）。
- **出处**：日志 25（玩家拍板表 L125）+ 日志 26 §3（L64–L72）；
  实现 `src/sim/cast.ts` L928–L937（`advancePhase`）+ L121–L131（`attackSpeedOf`）+ L269–L270。
- **为什么**：`✓` 玩家的拍板是"术式级攻速倍率"（比"把 `Phase.duration` 放宽成 `ValueSpec`"好懂）。
  ⚠ 名字叫 `windup`（前摇）**但它不是只影响前摇** —— 它是整条时间轴的缩放。
  ⚠ 顺手被钳到 0.2~5，理由见 §3.2 那一行。

### 3.7 ⚠ 「取消前摇」到底怎么算 —— **没找到**

- **结论**：**在全部 48 篇日志、`docs/` 全部文档、`schema` 注释、定价表里，
  都没有"取消前摇"这件事的记录**（既没有设计决定，也没有定价规则）。
- **我找过的地方**：`grep` 了 `前摇|windup|蓄力`、`取消前摇|调到 0|0 秒|零前摇|瞬发`、
  `档位`、`阶段时长`，覆盖 `docs/`（含 log）、`schema/`、`technique-system/`。
- **最接近的几个东西，都**不是**它，别混**：

| 像但是不是 | 为什么不是 |
| --- | --- |
| **「无」这一档**（§3.3） | 它是"阶段时长 = 0"的**档位设计**，方向是**消耗额度**。⚠ 但这**违背 §3.4 的中性点**（基准 0.3 秒，基准之下才是"比标准快"），而且**从没实现** |
| **`form: 'instant'`（瞬发）**（日志 45） | 它是"**这次释放要不要一条时间轴**"的形态，**不是**"把前摇设成 0 秒"。而且它是**默认值**、**不写就不付代价**，与"拿点数换"完全是两回事 |
| **取消窗口** | `docs/sequence-and-modifier-model.md` 里"取消"只出现在"**后摇取消窗口**"（`cast.ts` 的 `cancelWindow`），是引擎里既有的手感机制，**不是定价项、也不是编辑器里的滑块** |
| **`interrupt`（打断等级）** | 那是"**挨打断不断**"，与"前摇多长"是两条轴（`pricePhase` 里分别计价） |

- **⚠ 如果玩家现在就要答案，缺的是三件事**（都得他拍板）：
  1. **"取消前摇"是"0 秒"还是"这一档不要了"？**（前者仍有那一段的量、只是时长 0；
     后者是删掉阶段 —— 而删阶段会**连带**影响打断等级、代价付在哪一段、
     以及 `effect.at` / `rules[].phaseId` 引用的完整性，见 §七）
  2. **它算收益还是代价？** 按 §3.3 的"无 = 消耗额度"是收益（要花点数买）；
     但按 §3.2 的引擎现实，"阶段时长 0"会被当成瞬发（`advancePhase` 一 tick 走完），
     而定价照 `0 × rate = 0` —— **等于免费**。**这两条对不上，必须先定一条。**
  3. **每档值多少点**（§3.3 末尾那条同样的缺口）。

## 四、「冷却」是技能的唯一属性 + 阶段时长的档位

### 6. 冷却是技能的**唯一**属性：一个秒数 + 一个时机（前摇 / 释放 / 后摇 / 没有，四选一）

- **结论**：**一个技能只有一份冷却。**编辑器里只有**一个控件**（选时机 + 一个秒数滑块，
  换时机是把冷却**搬**过去），校验器用 `COOLDOWN_TWO_PHASES` 拦住"两个阶段都有冷却"。
- **出处**：日志 34 §二（整节）——`✓` 玩家原话：
  > **冷却是技能的唯一属性，不能在前后摇都有冷却**，编辑器内可以选择这个唯一的冷却属性
  > 在前摇/后摇进入冷却。
  实现：`web/src/editor.ts` 的 `coolDownTiming()`（L613–L670）+ `isCooldownLeaf`（L827）；
  校验器 `src/validator/checks.ts` 的 `COOLDOWN_TWO_PHASES`；
  词条 `docs/glossary.md` L134。
- **为什么**：
  - `✓` 冷却时机本身是**设计自由**："早进 CD 是收益，被打断白付是风险，这个取舍该由玩家做"
    （日志 03 §4；编辑器文案原话「越靠前越先进冷却，但被打断就白付了」）。
  - ⚠ **原来的毛病是"同一个数字出现两处"**：专门控件一个滑块，通用「代价」组里又一个 `冷却` 滑块 ——
    玩家看到的是"两个地方各有一个冷却"（日志 34 §二）。
  - ⚠ **`COOLDOWN_TWO_PHASES` 的后果原本是静默的**：引擎**取大值**（只生效一个），
    而**定价两笔都算** —— **玩家付了两次钱、账面还看不出来**（日志 34 §二.3）。
- **⚠ 两个必须照抄的实现细节**：
  1. **数据仍然写在某个阶段的 `cost.cooldown` 上**，**没有**挪到技能层。
     `✓` 理由："代价付在哪一段"**参与定价**（早付是风险、晚付是安全），
     挪到技能层会把这个信息变成"一个额外的引用字段"。
     ⇒ **"唯一"是靠 `控件 + 校验器` 保证的，不是靠 schema。**
     ⚠ 玩家要是希望**字段本身**也只有一个，那是一次 **schema 迁移（30 个技能）**——
     当时挂成了欠账，**至今没做**（日志 34 §六.1）。
  2. **秒数滑块必须走 `gridOf('cooldown')` 这一个来源。** ⚠ 曾经漂移过：
     控件的兜底写 `[1,2,3,8,20]`，而点表是 `[2,3,8,20]`（**1 秒冷却早就剪掉了**，
     因为"1 秒冷却等于没有冷却，2 秒才是真正的下限"）—— 两处不一致（日志 34 §二.4、
     `web/src/leaves.ts` L172–L180）。

### 7. 阶段时长的档位 —— 见 §3.3（**同一件事，不重复写**）

- **一句话**：定的是 **`无 / 1× / 3× / 9×` 四档**（几何级数，目的是**换点数**），
  ⚠ **没实现**，而且**编辑器今天的点表是 `[-1, 0.1, 0.2, 0.3, 0.5, 1]`**（不含 0，`-1` 是蓄力）。
- **⚠ 用户记忆里的"无 / 1× / 3× / 9×"是对的**，出处 `docs/default-values.md` L81–L93 +
  日志 29 §六 L132。它不是"阶段名"的档位，是**阶段时长**的档位。

## 五、技能修正 **vs** 修饰技能（差一个字，两样东西）

### 8. 「技能修正」在技能编辑器里，管**数值和几何**；「修饰技能」在术式里，管**连接和条件**

- **结论**：

| | **技能修正**（skill modifier） | **修饰技能**（modifier skill） |
| --- | --- | --- |
| 在哪编辑 | **技能编辑器**，加在**这个技能的规则**里 | **术式编辑器**，作为术式里的一件**特殊技能**插进去 |
| 管什么 | **数值和几何**：伤害 ×2、距离 +2 米、张角 360°、时长减半 | **术式中技能的连接、条件选择** |
| 作用对象 | **它自己所在的那一个技能** | 它**后面**的技能（靠位置） |
| 进点数账吗 | 进（它是规则） | ⚠ **不进 —— 算法还没定** |

- **出处**：`docs/glossary.md` §三（L87–L113）；`docs/sequence-and-modifier-model.md` §八（L143–L162）；
  日志 29 §六（玩家原话）；日志 30 §一（"技能修正改谁？→ **它所在的这个技能自己**"）。
- **为什么**：`✓` 玩家原话（日志 29 §六）：
  > **在名词记录文件中补充：这个叫修饰技能，在技能编辑器里的规则中添加的叫技能修正，注意区分。
  > 数值和几何都可以由技能修正负责，修饰技能只负责术式中技能的连接、条件选择等任务**
  ⚠ 这条是玩家**主动要求写进名词表**的，理由就是"混着用会各说各的，而且都以为自己懂了"。
- **⚠ 改伤害 / 改冷却属于技能修正，不是修饰技能** ——
  明确写在 `docs/sequence-and-modifier-model.md` L151：
  「**技能修正** | 改伤害、改 CD 这类**数值调整** | **技能编辑器**（技能自己身上的事）」。
- **⚠ 实现进度（重做 UI 时必须知道）**：
  - **修饰技能**：形状做了（日志 48：原型住 `content/modifiers/`、副本住 `SequenceSegment.mods`）；
    ⚠ **点数怎么算玩家还没给规则**，所以**不走点数账**；
    ⚠ **编辑界面还没做**（日志 48 §七）；⚠ 时机只有 `onLowHp` / `onTick` / `onCast` 真的接了线。
  - **技能修正**：**至今只是"定了名字和分工"，那一块功能还没做** ——
    日志 30 §六.2 → 31 §四.1 → 32 §五.1 → 33 §五.2 → 34 §六.2 → 36 → 37
    **连着 7 轮欠账都挂着它**（⚠ 期间技能编辑器本身被改造过两次，见第 12 条 ——
    所以"技能编辑器"≠"技能修正那一块"）。

## 六、基础技能只读、变体才可编辑

### 9. 两个技能库：**基础技能库（只读）+ 自定义技能库（玩家拥有）**

- **结论**：出厂技能**不能改**，只能"拿它当模板创造一个技能"；变体是**玩家拥有的东西**，
  有自己的 id 和名字、**不属于任何术式**、改它**所有用到它的术式一起变**。
  术式按 id 引用技能，**两个库都能引用**。
- **出处**：日志 32（整篇，§一那张"我原来错在哪"的对照表 + §二）；`docs/glossary.md` §一之二（L27–L51）；
  实现 `web/src/main.ts` 的 `findSkill`（自定义库优先、基础库兜底）。
- **为什么**：`✓` 玩家原话（日志 32 §一）：
  > 技能是玩家拥有的东西，存在两个库：**基础技能库**（我们写的出厂配平为 0 的那些）、
  > **自定义技能库**（玩家进行编辑后的技能另存一份副本在这里）……
  > **技能不是独属于一个术式的，应该影响所有用到它的术式**，但要注意
  > **基础技能和它的变体是两样东西**……**自定义技能是独立的，它不属于术式。**
  ⚠ **这一轮推翻了上一轮**的 `Technique.skillCopies`（"术式私藏一份副本"）——
  玩家的评语是"**我觉得你的理解有问题**"。详见 §冲突.3。

### 10. 详情页按钮语义：基础 =「创造一个技能」/ 自定义 =「保存 / 另存为 / 删除」，
     **进的是同一个编辑界面**

- **结论**：

| 选中的是 | 页面怎么表现 | 有哪些按钮 |
| --- | --- | --- |
| **基础技能（出厂）** | **一整页只读**：滑块 `disabled`，顶部一句话说明"它是模板，不能直接改" | 只有一颗 **「创造一个技能」** |
| **武器技能（`readonly`）** | 同样只读，且**另有一句话**（见第 13 条） | 没有"创造"（改强度改的是武器） |
| **自定义技能 / 还没保存的草稿** | 可改、可改名 | **「保存」「另存为」「删除」「放弃改动」**（+ 名字输入框） |

- **⚠ 两者进的是同一个编辑界面**：`editor.ts` 里就是**同一套渲染**
  （`renderInner()`），区别只在 `libraryRow()` 决定顶部说什么、按钮给哪几颗、
  以及滑块 `disabled`（`web/src/editor.ts` L830–L893 的 `libraryRow()` L1128 的 `disabled`）。
- **出处**：`docs/glossary.md` §一之二 L36–L44（那张流程图）；
  日志 32 §二.3（界面重做）；`web/src/editor.ts` L414–L428、
  L834–L892（`libraryRow`）、L1395–L1398（按钮分发）。
- **为什么**：`✓` 玩家定的流程是"**创造一个技能** → 编辑 → **保存**"，
  所以**不必**给基础技能单独一个编辑器 —— 同一套界面换个身份就够了。
  ⚠ 不给基础技能"编辑"按钮，是为了**不让玩家白改一场**：
  出厂内容不该被改，而顶上一行"现在是哪一份、按哪个按钮"就是为了避免
  "拖了半天滑块才发现改的是出厂内容"（`editor.ts` L830–L837 的注释）。

### 11. 保存 / 另存为 / 删除 / 放弃的语义

- **结论**：
  - **改的是草稿，按「保存」才进库。**"改了没保存就走开 = 什么都没发生"。
  - **「保存」只写自定义技能库**；基础技能库（内容）从头到尾**只读**。
  - **「另存为」给新 id**，不就地覆盖；新变体的 `basedOn` 仍是**最初那个基础技能**。
  - **「删除」受引用限制**：还有术式在用它就**不给删**，并**列出是哪几份术式**。
  - **基础技能没有「保存」这颗按钮**（不是"灰着的保存"，是**根本没有** ——
    只读页只有「创造一个技能」）；自定义技能页上，没改动时那颗按钮的文案是「已保存」
    并**置灰**（`class="dim"`，不是 `disabled`），有改动时才变成「保存」。
- **出处**：`web/src/editor.ts` L307–L320（草稿模型）、L414–L428（创造 → 草稿）、
  L442–L465（保存 / 另存为 / 放弃）、L872–L877（那几颗按钮 + `dim`）；
  保存的宿主侧规则在 `web/src/main.ts` L1149–L1173；`docs/glossary.md` L36–L51；
  日志 32 §二.3 / §二.4。
- **为什么**：`✓` 玩家 2026-09-21 选的"**先给草稿，按「保存」才进库**"——
  ⚠ 理由是"改了不保存就走开 = 什么都没发生，**库里不会留垃圾**"（`editor.ts` L414–L415）。
  ⚠ 「另存为」**必须换 id**："不能就地覆盖（那就不是另存为了）"，
  而且编辑器必须**跟着切到新的那份**，否则下一次「保存」会写回原来那份（`web/src/main.ts` L108–L109 附近）。
  ⚠ 更要紧的是"**基础技能和它的变体是两样东西**"：想覆盖 / 还原基础版这条路**根本不成立**，
  因为基础版**永远原样在那儿**。一份术式里"一段用基础版、一段用你的变体"是**完全正常的**
  （两个 id 指向两样东西）—— 日志 32 §一末段。

### 12. 编辑器的两页结构（重做 UI 的现状基线）

- **结论**：**技能页 7 块 / 术式页 5 块**（日志 42 之后）——
  技能页：`head` / `points` / `rules` / `leaves` / `phases` / `issues` / `export`；
  术式页：`bar` / `meta` / `chain` / `library` / `ledger`。
  **挂块用 `mountBlock`（内容一样就一个字都不碰）**，所以 `<details>` 展开状态和动效立得住。
- **出处**：日志 41 / 42；`docs/editor-ui-brief.md` §五之二.6（块地图）+ §五之三（四条改布局的路）。
- **为什么**：`✓` 玩家："编辑器UI确实要提上日程让我做了，现在你做的太不直观也不美观"
  → 定下分工「**外观和交互由玩家决定，我负责实现、结构、以及"信息不能丢"**」
  （`docs/editor-ui-brief.md` 文件头）。
  ⚠ 前提是"结构固定、只更新变化的部分"——不做这个，玩家设计的**悬停 / 动效 / 拖拽根本立不住**
  （整块 `innerHTML` 重建会把状态冲掉）。⚠ 焦点接回来这件事**炸过一次**：
  假 DOM 里没有 `ownerDocument.activeElement` → **35 个断言一起红**，真因藏在"客户端加载失败"里

- **⚠ 重做 UI 时的"别碰"清单**：`data-block` / `data-act` / `#editorBody #techBody #teLedger #pick`
  / `data-hud-*` / 若干**被测试断言的文字**（`术式栏`、`基础技能库`、`我的技能`、
  `进入第 N 段`、`放不出来`、`（起手）`）。
  完整表在 `docs/editor-ui-brief.md` §五之二.3 和 §五之三末尾。

## 七、固有效果 `effect` 与规则 `rules` 的分界

### 13. 判据是**机械的**：`when === 'phaseComplete'` 的那些就是固有效果

- **结论**：**`Skill.effect`（这个技能**是什么**：载体 + 载荷 + 数值）与
  `Skill.rules`（它**额外做了什么**：挂在某个时机上的行为与反应）分开两块。**
  判据是**机械的** —— `when === 'phaseComplete'` 的进 `effect`，其余
  （`onHit` / `onCast` / `onTick` / `onLowHp` …）留在 `rules`。编辑器里 `effect` **单独一块**，
  排在规则**前面**，卡片上**不给删**。
- **出处**：日志 31（整篇）；`schema/skill-schema.ts` 的 `SkillEffect`（L658–L672）；
  `docs/glossary.md` §二（L73–L83）；`technique-system/README.md` L203–L217。
- **为什么**：`✓` 玩家第 1 条要求：
  > 技能本身的效果**不计入规则栏中**，也不具有点数盈亏。
  ⚠ 实现的关键手法：**引擎一行都没改** —— `src/effects.ts` 的 `effectAsRule()`
  把效果折成一条 `when: 'phaseComplete'` 的规则，编译 / 定价 / 说明 / 校验看到的还是同一条时间轴。
  所以那次搬家**行为零改动、账零改动**（`duel` 逐位一致、`calibrate` 的 18.4/1.47 一模一样）。
- **⚠ 一条真正要紧的教训**：**"看不见效果"的地方会静默失明；一次扫出 8 处**
  （编译漏了 → **打出去什么都没有**；定价漏了 → **效果里的数字变成真的免费**；
  跨文件引用检查漏了 → `statusId` / `entityId` **运行期才炸** …）。
  **规矩：「这个技能会做什么」只有 `allRulesOf()` 一个入口。**
- **⚠ 顺带的两次内容事故**（都是"改 26 个内容文件"这种批量活踩的，重做 UI 要小心同类活）：
  - 日志 31 §二：搬家脚本跑第二遍时把 **6 个技能的 `effect` 写成空数组、直接蒸发**，
    **没有 git、没有备份** → 靠 `calibrate` 的历史账 + 旧校验输出 + 测试钉死的数字 + 点表，四路证据反解重建。
  - 日志 30 §五：用 PowerShell `Get-Content | Set-Content` 改中文 Markdown →
    **整个文件变成乱码**。**规矩：中文文本一律用 `edit` / `write` 工具，永远不用那套组合。**

### 14. **固有效果本身不计点数盈亏，但里面的数值偏离默认值照常计价**

- **结论**：**机制免费、数值有价。**"能位移"这件事不要钱，**位移了几米**才要钱。
  效果里的数字**照样能拖、照样计点数**（偏离出厂值才算）。
- **出处**：`docs/glossary.md` §二 L77；`schema/README.md` L175–L176；日志 30 §一（玩家回答表第 1 行）；
  日志 31 §一.2（"滑块的组也多了一个「固有效果」——**效果里的数字照样能拖，照样计点数**"）。
- **为什么**：`✓` 玩家原话（日志 29 §五，这是**纠正执行者理解**的一句）：
  > 交流有问题。我的意思是**机制上的代价**：比如位移的**机制本身**是不应该有代价的，
  > 位移的**距离**有代价。我们在游戏里设置各种**互不相同的基础技能**，玩家获得它们后可以编辑，
  > 因此不会出现**两个账相同而效果不同的火球技能**
  ⚠ 执行者原来把"机制"和"数值"混成一句话了。
- **⚠ 一个直接推论**：**"基础技能"必须互不相同**（不是同一份火球换个名字）——
  因为"机制免费 + 数值有价"成立的前提是**玩家不能凭空造一个新机制**；
  玩家能造的是"**数值 + 组合 + 修正**"（日志 29 §五末）。

## 八、武器技能只读、数值由武器属性代入

### 15. 武器技能模板**只读**，数值靠 `ref: 'weapon.*'` 由武器代入

- **结论**：`content/weapon-skills/` 里的技能带 `readonly: true` ——
  **编辑器里不给改数值（滑块都不显示）**，玩家能改的**只有"怎么把它拼成武器术式"**。
  数值靠 `ref: 'weapon.reach'` / `'weapon.damage'` / `'weapon.windup'` 由武器代入，

- **出处**：日志 25 §3（L57–L61）+ 日志 25 玩家拍板表；
  `schema/skill-schema.ts` L205–L207（`ValueRef` 的 `weapon.*` 三个）、
  L921–L935（`readonly` 字段 + 玩家原话那段注释："这是**故意不该被改**，不是没实现"）；
  `docs/STRUCTURE.md` L130（`weapon-skills/` 那行）；日志 26 新增 `web/src/editor.ts`
  "只读技能不给改"（L21）；`web/src/editor.ts` L353–L358 / L843–L848。
- **为什么**：
  - `✓` 玩家的武器设计就是"每种武器的技能范围和伤害**因为属性不同而不同**"（日志 25 触发段）。
  - `✓` **改强度改的是武器，不是技能**："想改一把武器的强度，改的是**武器的属性**
    （那会代入到技能里），或者换一把武器 —— 而不是去改技能本身"（`schema/skill-schema.ts` L932–L934）。
  - ⚠ 一个必然的副作用：`✓` 玩家原话「**我不是说了武器技能不算帐吗**」——
    **武器技能和由它拼成的序列都不算账、不判配平、血契消耗恒为 0**
    （判据 `isWeaponSide()`：引用了只读技能 = 武器侧）。⚠ 用户看不到账的时候
    校验器**必须说出来**为什么没有账（`ValidationReport.priceless`）——
    **静默不显示会被读成"免费"**（日志 25 玩家拍板表 L123）。
- **⚠ 攻速那条是同一个机制的变形**：`weapon.windup` **乘所有阶段时长**（见 §3.6），
  钳到 0.2~5；`windup: 0` 会让阶段时长变成 0 → 一个 tick 走完整个术式（日志 26 §3）。

### 冲突 1：阶段时长的档位数 —— 二选一 → 三选一 → **四档**（三次都出自同一天、同一场对话）

### 冲突 2：「无」这一档的方向 vs 时间类的中性点 —— **两处对不上，都没被裁定**

- **A（`docs/default-values.md` L87）**：「无 → **消耗额度**」——理由是"瞬发（比标准快，是好处）"。
- **B（`docs/default-values.md` L72–L77）**：前摇的标准值是 **0.3 秒**，而"能量代价基准 0 / 冷却基准 0"。
- **⚠ 对不上在哪**：如果中性点是"**不写 = 0**"（`schema/README.md` 说这**不叫默认值**），
  那"无"就是"比标准快" → **收益** ✓ 与 A 一致；
  可基准已经被定成 **0.3 秒**（L72），那么**基准本身**才该是 0 点，
  「无」是**比基准快** → A 仍然自洽，但**"3×/9× 提供额度"的基准也就必须是 0.3 秒 ×N**，
  而 L89–L90 写的是"慢三倍 / 慢九倍"。**"几倍"是相对谁的？文档没写死。**
- **⚠ 定价上还有一个更硬的洞**：`pricePhase()` 就是 `duration × phaseSecondPerPoint`
  一**绝对**线性式（`src/pricing.ts` L1051–L1065），
  它**不是**"相对基准偏离才计价"——**所以"相对出厂值"这件事只发生在 `skillLedger` 的相减里**，
  而"无 / 1× / 3× / 9×"这套档位**没有任何代码或数据对应**。

### 冲突 3：技能副本的归属 —— `Technique.skillCopies`（术式私藏）**被推翻**
