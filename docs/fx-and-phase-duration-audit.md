## 用词

- **用户** = 下设计指令的人（提出这张点表要求的人）。
- **玩家** = 玩游戏的人（将来会去拖时长滑块的、实际按下攻击键的人）。
- 两者**不是同一个人**。本报告只在使用「用户要求 / 玩家会怎么拖」时分别指名。

## 一句话结论

**改动前后摇不会让特效"坏掉"，但会让特效的"时间位置"变长或变短** ——
表现层是**固定时长**的（特效不随时长拉伸，也不随时长重复），
所以「无（0 秒）」和「9 倍」分别表现为 *同帧齐射* 和 *早期一闪 + 长时间静止*。
本次确证的风险全部是**观感 / 已有不一致**级别，没有一处会让特效播不出来或让游戏崩。

## 1. 特效是"按时长拉伸 / 跟随"，还是"固定长度"？

**答案：固定长度。** 特效时长是客户端写死的常数，和阶段时长**没有任何数据通路**。

### 数据通路（确证）

| 环节 | 位置 | 说明 |
| --- | --- | --- |
| 释放事件 | `technique-system/src/sim/types.ts:827-845` | `deliveryFired` 只带**几何**：`from / dir / length / width / radius / angle / hitCount / damageType / vfx` —— **没有一个时间字段**，更没有 `duration` |
| 发射点 | `technique-system/src/sim/pipeline.ts:1475-1489` | 事件在**载体执行的那一刻**推出去，`hitCount` 用此刻的命中数，`vfx` 原样透传 |
| 特效寿命（程序化） | `technique-system/web/src/fx.ts:209-219` | `const LIVES: Record<DeliveryKind, number> = { self: 0.2, projectile: 0.2, meleeArc: 0.26, beam: 0.18, capsule: 0.2, area: 0.42, aura: 0.5, spawn: 0.3 }` —— **全是常数** |
| 取寿命 | `technique-system/web/src/fx.ts:282-303` | `spawnDelivery()` 里 `const life = LIVES[ev.kind] ?? 0.25` —— **只按载体类型查表，不看任何时长** |
| 挥砍扫描节奏 | `technique-system/web/src/fx.ts:472-473, 501` | `SWEEP_FRACTION = 0.38`，`sweep = Math.min(1, fx.age / (fx.life * SWEEP_FRACTION))` —— 扫完所需时间是 `life × 0.38`，是**它自己的 life 的比例** |
| 序列帧（作者素材） | `technique-system/web/src/assets.ts:97` | `frameTime: 1 / def.fps` —— 帧速来自 `content/fx/<id>.json` 的 `fps` |
| 序列帧寿命 | `technique-system/web/src/fx.ts:846-854, 870-872` | `spriteSteps = frames`（`pingPong` 时 `2n-2`），`spriteDone = age >= spriteSteps * frameTime` —— **等于素材自己的总长** |
| 调用点 | `technique-system/web/src/main.ts:442-458, 472-505` | `spawnSprite(ev)` 失败就 `deliveries.push(spawnDelivery(ev))`；两条路都**没有**从事件拿时长的余地 |
| 帧推进 | `technique-system/web/src/main.ts:585-595` | `updateDelivery(d, realDt)` / `updateSprite(s, realDt)` —— `realDt` 是**墙钟**时间（`main.ts:2215, 2236`） |

### 阶段与特效的绑定方式

- 技能里写的 `vfx`（`src/sim/types.ts:294`、`src/sim/types.ts:843`）**只管"用哪张素材 / 哪套程序化风格"**，不负责任何时间。
- 挂在哪一段，由"这条效果属于哪个阶段的 `phaseComplete`"决定：
  `src/effects.ts:45-55`（效果折成 `when: 'phaseComplete', phaseId: e.at` 的规则）
  → `src/sim/cast.ts:1264-1269`（时长走完才 `runRules(..., 'phaseComplete', { phaseId })`）
  → `src/sim/cast.ts:1393`（蓄力松手也是同一条 `phaseComplete`）。
- **所以时长的作用只是"什么时候把这条特效放出去"**，不是"这条特效播多久"。

### 附：`sim` 不发"阶段开始"给表现层

`src/sim/types.ts:811` 有 `castPhase` 事件，`src/sim/cast.ts:1112-1114` 会推它，
但客户端 `web/src/main.ts:373` 的 `switch (ev.type)` 里**没有 `castPhase` 分支**
（`grep castPhase web/src/main.ts` 无命中，只有 `main.ts:432` 的 `castStarted`）。
⇒ 表现层拿不到"某一段开始了"，也就**不可能**做"按阶段进度推进的特效"。
这是"固定长度"这个结论的结构性原因，不是疏漏。

## 2. 时长 = 0（无）时，特效还会不会播？

**答案：会播 —— 而且是一帧都不省地播完整条。跳过的是"等待"，不是"特效"。**（确证）

- 0 时长阶段**非法？不是**：`src/validator/checks.ts:503-507` 只要求 `duration` 是 `>= 0` 或 `=== -1`，**0 合法**。
- 0 时长阶段的推进：`src/sim/cast.ts:1255`（`cast.elapsed += world.dt`）
  → `1264`（`if (cast.elapsed < phase.duration * cast.speedScale) return`，此时 `0 < 0` 为假，**不返回**）
  → `1266`（照常 `runRules(..., 'phaseComplete', ...)`）→ `1269`（`advancePhase`）。
  ⇒ **特效规则照跑一次**，`deliveryFired` 照发（`src/sim/pipeline.ts:1475`），
  客户端照 `spawnDelivery` / `spawnSprite`（`web/src/main.ts:442-458`），
  并按写死的 `LIVES` / `frames÷fps` **完整播完**。
- 换句话说：0 时长 = **"把这一段的等待抹掉"**，不是"把这一段连特效一起删掉"。
  这一点和定价那边的叫法一致：`src/pricing.ts:2179` 注释就写着 `duration === 0` 是「0 档：这一段被取消了」。

**但有两个真实现象（确证 + 一处推断）**：

1. ⚠ **多段同时归零 → 同帧齐射**（确证）：`advancePhase`（`src/sim/cast.ts:1285` 起）
   是 `while` 循环，一个 tick 里能把连续几个 0 时长段全部走完。
   于是这些段的 `phaseComplete` 全在**同一个 tick** 触发，事件在客户端同一帧被 `drainEvents` 处理
   ⇒ 多个 `sprites` / `deliveries` 起点几乎重合、飘字同点叠加（`web/src/main.ts:379-385` 的飘字）。
   前摇 0 + 命中 0 + 后摇 0 的"瞬发"技能会**闪一下**，而不是什么都不放。
2. 推断（**未确证**，属既有语义）：0 时长段等于"不可能被打断"——
   `interrupt: 'damage'` 的判定（`src/sim/cast.ts:1221-1239`）发生在本 tick 的推进之前，
   而 0 时长段在同一 tick 就结束了，所以它带给表现层的观感是"这一下无法被掐掉"。
   这一条我只从代码结构推断，没有跑测试验证。

## 3. 拉到 9 倍时，特效会怎样？

**答案：特效还是只播一次、只播原长；拉长出来的是"空隙"。不是拉伸，也不是重复播。**（确证）

- 时间轴：`src/sim/cast.ts:1255-1269` —— `elapsed` 要攒到 `duration × speedScale` 才走完这一段。
  拉成 9 倍 ⇒ `phaseComplete` 发生得晚 9 倍 ⇒ **特效晚 9 倍才放**。
- 放出之后，`web/src/fx.ts:209-219` 的 `LIVES` 一个字节都没变
  ⇒ 挥砍刀光仍然是 `0.26s` 播完（其中 `0.26 × 0.38 ≈ 0.1s` 扫完，见 `fx.ts:472-473, 501`），
  光束仍然 `0.18s`，光环仍然 `0.5s`。**不会拉长，不会循环。**
- 作者素材同理：`web/src/fx.ts:853` 的 `spriteDone` 只看 `frames × (1/fps)`，
  `main.ts:503` 的 `pingPong: false` **写死**（`web/src/fx.ts:846-849` 的 ping-pong 分支因此永不生效）
  ⇒ 序列帧播完最后一帧就 `splice` 掉（`main.ts:591-595`），后面空着。
  ⚠ 顺带一条确证：`FxAsset.duration`（`web/src/fx.ts:787`、`assets.ts:98`）**没有任何读取方**
  （`grep 'asset.duration' web/src` 无命中）—— "素材总长"这个字段是死的，实际由 `frames`/`frameTime` 现算。
- **表现层唯一会"跟着变长"的东西**：施法条。
  `web/src/main.ts:2559-2565` 的 `frac = cast.elapsed / ph.duration` 会随时间填满
  ⇒ 9 倍前摇的画面是「**早期闪一下刀光 / 蓄力声，然后施法条慢慢爬很久**」。

### ⚠ 与 9 倍直接相关的一个"未来观感风险"（确证代码事实）

瞬时载体的**起点**是事件里的 `from`，而那取的是**执行那一刻**的施法者位置
（`src/sim/pipeline.ts:1480`：`from: { x: ctx.actor.pos.x, y: ctx.actor.pos.y }`），
方向取 `ctx.cast?.facing ?? ctx.actor.facing`（`pipeline.ts:1474`）。
前摇拉到 9 倍时，玩家有足够时间走位 / 转头
⇒ 「刀光在施法时的位置炸，伤害打在 9 秒后的目标身上」这种**画面与判定分家**会变得常见。
注意：这不是特效字段的问题，是既有实现的几何取法；拉长前摇只是把它**放大到肉眼可见**。

## 4. 有没有别的地方偷偷假设了"出厂时长"？

用**魔法数字**和**时长专用常数**两路扫。逐条列证据与判断：

### 4.1 客户端（`web/src/**`）——两处，其中一处是真的不一致（确证）

| # | 位置 | 事实 | 判断 |
| --- | --- | --- | --- |
| A | `web/src/main.ts:2563` | 蓄力阶段施法条：`Math.min(1, cast.charge / 2)` —— `charge` 是秒（`src/sim/cast.ts:1251`），**分母 `2` 是写死的 2 秒** | **确证**：这是"假设蓄力 2 秒就满"的表现层常数。玩家把蓄力拖长/拖短，进度条与真实蓄力量脱钩 |
| B | `web/src/main.ts:2564` | 普通阶段施法条：`Math.min(1, cast.elapsed / ph.duration)` —— 模拟用的是 `ph.duration * cast.speedScale`（`src/sim/cast.ts:1264`），**这里漏了 `speedScale`** | **确证**：武器 `weapon.windup > 1`（铁剑 1.15，见 `content/weapons/iron-sword.json` 与 `src/sim/cast.ts:188-190`）时，进度条**永远追不上真实进度**，会在真正命中之后才填满。<br>⚠ 这是**既有**问题（与拖时长无关，但拖时长会让人更容易注意到） |

### 4.2 其它扫到的魔法数字 —— 逐条判定"不构成风险"（确证）

- `web/src/fx.ts:284` `?? 0.25`、`fx.ts:210-219` `LIVES`、`fx.ts:270-272` 的默认宽度、
  `fx.ts:467-469` 的 `fade`、`main.ts:105-107`（`FLOATER_LIFE = 0.75` / `PARTICLE_LIFE = 0.4` / `MAX_SHAKE = 9`）：
  **都在特效 / 飘字 / 震屏自己的时间基上，与阶段时长无关**。拖时长不改变它们的取值。
- `web/src/leaves.ts:116` `duration: [-1, 0.1, 0.2, 0.3, 0.5, 1]`：
  ⚠ 这是**编辑器点表的候选档**（`validator/index.ts:1155` 的注释同样点明"编辑器今天的时长控件还是线性秒数滑块"），
  不是任何运行时常数。**拖出格子外时账算不出来**（见 §4.4），但特效不受影响。
- `web/src/editor.ts:546`（`p.duration < 0 ? '按住不放' : \`${fmt(p.duration)} 秒\``）与
  `editor.ts:953` 的注释（"前摇 0.3 秒 → 命中 → 后摇 0.2 秒"）：**前者是纯显示、后者是注释**，改动无害。⚠ 本次审计**未读取编辑器 UI 的实现正文**（用户硬命令：UI 在他下令前一个字都不许动），只按 grep 命中行作判断。
- `main.ts:2215` `Math.min((now - last) / 1000, 0.25)`：帧率保护，与阶段时长无关。

### 4.3 模拟 / 工具侧（只看是否误吃"出厂时长"，确证）

- `src/sim/ai.ts:42`：`own.charge >= (e.ai.chargeTime ?? 1.5)` —— **AI 的松手阈值**，是 AI 自己的参数，
  不是"出厂时长"。但它意味着**把蓄力拖很长时，AI 会在 1.5 秒后松手**（真人玩家可以一直按）。
  这是行为层，不是表现层。
- `src/cli/run.ts:189-211`：命令行时间轴显示按 `t += p.duration` 累加 —— **纯显示**。
- `src/cli/battle.ts:139`：`--duration` 缺省 60 秒 —— 命令行跑多久，与特效无关。
- `src/describe.ts:240/255/523/561`：文案里的"持续 N 秒" —— **纯文案**。
- `src/effects.ts:37` `EFFECT_ORDER_BASE = -1000`：规则排序，与时间无关。

### 4.4 唯一一处**真的假设了"出厂时长"**的地方 —— 在账上，不在画面上（确证）

- `src/pricing.ts:1723-1732` `tierOf(base, now, table)`：档位是 **`now / base` 与表行的比值**比出来的
  （`base` = **这一段的出厂时长**，见 `pricing.ts:1741`）。
- `src/validator/index.ts:1159-1174`：只要这个比值落在表外，就报
  `PHASE_TIER_NOT_IN_TABLE`（文案明确要求"把时长拖回四个档位之一"，并点名"编辑器里四档选择是欠账"，见 `validator/index.ts:1170-1171`）。
- `src/pricing.ts:1638-1648` `DEFAULT_TIER_TABLES`：档位是 `0 / 1 / 3 / 9`（`points: -6 / 0 / 2 / 4`）。
- ⇒ **玩家拖到 5 秒（不在 0/1/3/9 档）时：账算不出来会报错，但特效照旧按 §2/§3 的规则播。**
  ⚠ 这正是背景里那句话（"每个取值各填一个数"）要解决的欠账：**它卡的是点数，不是特效。**

**小结（§4）**：表现层没有偷偷假设"出厂时长"的门面；
真正与"出厂时长"绑定的只有**档位查表算账**（`pricing.ts:1723` / `validator/index.ts:1163`），
以及两处**施法条的分母**（`main.ts:2563`、`main.ts:2564`）。

## 5. 结论：有问题吗？

**结论：特效本身没问题（不会坏、不会消失、不会报错）；有问题的是三处"观感落差"与两处"施法条不一致"。**

| # | 现象 | 触发条件 | 会怎么表现 | 证据 | 性质 |
| --- | --- | --- | --- | --- | --- |
| 1 | 同帧齐射 | 连续多段（含前摇 / 命中 / 后摇）被拖到 **0 秒** | 同一帧里多条特效起点重合、伤害飘字叠在一起；"闪一下"而不是"什么都没有" | `src/sim/cast.ts:1255-1269`、`1285`；`web/src/main.ts:379-385, 442-458` | 确证的代码事实 + 观感判断 |
| 2 | 早期一闪 + 长静止 | 前摇 / 后摇被拉到 **3× / 9×** | 特效只播一次原长（挥砍 0.26s / 光束 0.18s / 光环 0.5s），之后到命中前画面无反馈；只有施法条在爬 | `web/src/fx.ts:209-219, 472-473, 853`；`web/src/main.ts:2559-2565` | 确证 |
| 3 | 画面与判定分家 | 前摇很长且玩家在此期间移动 / 转身 | 特效炸在**施法那一刻**的位置与朝向，伤害打在别处 | `src/sim/pipeline.ts:1474, 1480`（`from` = 执行刻的 pos） | 确证代码事实；"会变常见"是**推断** |
| 4 | 施法条不跟攻速 | 任何 `weapon.windup ≠ 1` 的武器 | 进度条落后于真实进度，命中发生时条还没满 | `web/src/main.ts:2564` vs `src/sim/cast.ts:1264` | **确证（既有不一致，与拖时长无关）** |
| 5 | 蓄力条分母写死 2 秒 | 蓄力阶段被拖长 / 拖短 | 进度条与真实蓄力量脱钩（2 秒就满格） | `web/src/main.ts:2563` vs `src/sim/cast.ts:1251` | **确证** |
| 6 | ⚠ 蓄力语义退化 | 把 `duration: -1` 的蓄力段拖成 **0** | 这一段的"按住不放"消失：`releaseCharge` 直接拒绝（`src/sim/cast.ts:1391`），蓄力值恒为 0，`ref: 'charge'` 读出来是 0 ⇒ 蓄力技变成"瞬发 + 空蓄力" | `src/sim/cast.ts:1250-1253, 1391`；`src/validator/checks.ts:503-553` | 确证（模拟层，不是特效层；**如果表把 `-1` 也当可编辑取值就必须处理**） |

**风险清单**：以上 6 条即为本次**确证**的风险（无一处会导致崩溃、白屏、特效缺失或校验器崩溃）。
⚠ 我**没有**为了凑产出虚构风险 —— 例如"特效会拉伸/会重复播/会消失"这些猜测，
经 §1/§2/§3 的证据**逐条否掉**了。

### ⚠ 明确区分

**我确证的**（有文件 + 行号）：
- 特效寿命是常数、与阶段时长无数据通路（§1 全表，尤其 `web/src/fx.ts:209-219, 282-303`）。
- 0 时长**照播**（`src/sim/cast.ts:1255-1269`）。
- 9 倍**只延后、不拉伸不重复**（`src/sim/cast.ts:1255-1269` + `web/src/fx.ts:853`）。
- 施法条两处分母问题（`web/src/main.ts:2563`、`2564`）。
- 客户端**不处理** `castPhase`（`web/src/main.ts:373` 的 switch 无此分支）。
- `FxAsset.duration` 是死字段（`web/src/fx.ts:787`，`assets.ts:98`，无读取方）。
- 档位查表依赖**这一段的出厂时长**（`src/pricing.ts:1723-1732, 1741`；`validator/index.ts:1163`）。

**我推断的**（未跑测试、未做运行时验证，标 ⚠）：
- ⚠ 「0 时长段实际不可被打断」——只从 `src/sim/cast.ts:1221-1239` 与本 tick 推进的**顺序**推断。
- ⚠ 「同帧齐射的观感会很糟」——是观感判断，没有截图/录屏验证。
- ⚠ 「9 倍前摇下画判分家会变常见」——`from` 取执行刻位置是确证的，但"常见到什么程度"没有实测。
