## 一、三个被混在一起的概念（先分开，后面才顺）

| | 回答什么 | 住在哪一层 | 例子 |
| --- | --- | --- | --- |
| **激活方式** | 玩家**怎么按** | **术式层** | 按一下 / 蓄力放开 / 按住 / 开关 |
| **触发时机** | 效果在**什么事件**上发生 | **技能内部的规则** | 命中时 / 暴击时 / 每 tick / 血量低 |
| **施法形态** | 这次释放**要不要一条时间轴**、要多长 | **技能层** | 瞬发 / 蓄力 / 持续 / 常驻 |

⚠ 玩家嘴里的"触发方式/触发类型"两个都指过。**说清楚是哪一个**，否则会讨论到岔路上去。

### 为什么"被动 + 法球"会出错（机制根因）

⚠ 出错的**不是判定，是语义本身不成立**。原因链：

1. 今天**技能自己不声明"需不需要一次施法"** —— `Skill` 里没有这个东西
2. 而激活方式是**整个术式**的一个属性（`Technique.activation`）
3. 编译器只能把术式里的技能**串成一条时间轴**（`CompiledTechnique`）
4. 「无下限」这类常驻技能**没有时间轴** → 串不进去

⇒ 于是"按下去到底该发生什么"**没有答案**。这类组合必须从**数据上说不出来**，
而不是等它在运行时出错 —— 这就是下面第二节"技能自己声明形态"的理由。

## 二、四类施法形态（技能层，机制事实）

| 形态 | 机制特征 | 内容里的例子 |
| --- | --- | --- |
| **瞬发** | 有时间轴，跑完就结束 | 横砍、魔法飞弹、裂地斩、瞬影 |
| **蓄力** | 时间轴里有一段**由玩家控制时长**（`duration: -1`），必须有"按下→松开"才成立 | 贯日 |
| **持续** | 时间轴一直挂着，直到输入说"结束" | 引导光束、光环、火焰喷射 |
| **常驻** | **没有时间轴**，装上就生效（靠事件或每 tick） | 无下限、血契记账器、猎手直觉、背水 |

⚠ **形态是相对施法者而言的**（玩家原话）。所以"放一个图腾/召唤物"是**瞬发** ——
放下去那一下有完整时间轴 ✓；图腾之后怎么活着是**它自己的事**，不是这个技能的形态。
（同一个技能只能有一个形态：既被动又主动的东西**拆成两个技能**。）

## 三、序列 = **一次输入**

这是整套模型的地基：**一条序列就是接受一次输入的单位**。

| 序列的形态 | 里面能放什么 | 输入怎么走 |
| --- | --- | --- |
| **瞬发序列** | **多个**瞬发技能（没有数量限制）+ 修饰技能 | 按一下（或"放开"的瞬间）→ 依次打出 |
| **蓄力序列** | **蓄力技能必须在最前面**，后面可以跟瞬发技能 + 修饰技能 | 按下 = 开始 → 松开 = 结束 |
| **持续序列** | **持续技能必须在最前面**，后面可以跟瞬发技能 + 修饰技能 | 按下 = 开始 → 松开/再按 = 结束 |
| **常驻序列** | **多个**常驻技能（顺序无意义）+ 修饰技能 | **不参与激活，直接跳过** |

⚠ **"独占序列"的正确含义**（这一点在讨论里被读岔过一次，写清楚）：

> 蓄力/持续技能**必须是序列的第一个技能**（前面不能有技能）——
> **不是**"这条序列里只有它"。后面完全可以跟瞬发技能
> （由触发类修饰决定**什么时候、在哪儿**把那些瞬发技能打出来）。

⚠ 也不能反过来读成"瞬发技能独占序列"：**一条瞬发序列里可以有多个瞬发技能**，
从左到右依次打出 —— 这正是旧模型里"一条技能链"（`skills` + `links`）的位置。

- **常驻序列**：里面的技能**同时生效**、**顺序没有意义** → 界面上这条**不该排号**，
  应该显示成一堆芯片，而不是 ①②③ 的横条
- **修饰技能不受形态约束**：可以进任何一种序列（见第八节）

## 五、形态与激活方式的**相容表**

| 序列的形态 | 能进哪些激活方式 |
| --- | --- |
| 瞬发 | 按一下 / 蓄力放开 |
| 蓄力 | **只能**蓄力放开（按一下的话那段永远跑不完 ✗） |
| 持续 | 按住 / 开关 |
| 常驻 | 不进激活循环（被跳过）✓ |

两条规矩：

1. **一条序列里不能混形态** ⚠ 玩家原话："在同一条序列中不能，我觉得会有 bug"。
   这个直觉是对的：一条时间轴里既有"由玩家控制时长的蓄力段"又有"马上打出去的瞬发技能"，
   "瞬发那个到底什么时候打"就没有答案了。
2. **同一门术式的不同序列可以**是不同形态 ✓ —— 前提是每一段都和术式的激活方式相容
   （例：一门"蓄力放开"的术式，可以同时有蓄力序列和瞬发序列 ✓；但不能有"持续"序列 ✗）

## 七、术式分类

```
武器术式                     （武器系技能 + 修饰技能；全是瞬发）
魔法术式
├ 常驻术式                   （**只含常驻技能**的术式）
└ 主动术式                   （其余**全部**魔法术式 —— 只是分类上的名字）
```

⚠ 命名说明：这一类在讨论里一度被叫成「**触发术式**」，**那个名字会误导** ——
它其实包含所有非纯常驻的魔法术式，和"有没有触发条件"没关系。定稿用**主动术式**。
（同理：讨论里出现的"触发技能"是**修饰技能**的口误，见第八节。）

## 八、修饰技能

**是什么**：机制上的一类零件。它**不能独立存在**，只能在序列里修饰别的技能。

⚠ **它和"技能修正"是两件事，别混**：

| | 是什么 | 谁来做 |
| --- | --- | --- |
| **技能修正** | 改伤害、改 CD 这类**数值调整** | **技能编辑器**（技能自己身上的事） |
| **修饰技能** | 改"**什么时候、在哪里、怎么打**"这类**机制** | 序列里可拖的零件 |

### 规矩

- **不分类**：修饰技能机制各异、**参数异构**（位置 / 数量 / 时长 / 条件…），
  ⚠ 所以**不要**去搞一套统一的参数表（那是"为了整齐而整齐"）
- **靠位置**：修饰技能修饰的是**紧邻它后面的那个技能** —— 拖进去的顺序**就是语义** ⚠ **用户 2026-09-30（界面那一侧）**：**这一轮先用按钮排**（＋加一个 / 删掉 / 上移下移）✓ **拖拽以后再说**（拖拽属于**表现层**的事）✓ —— ⚠ 本条"**位置 / 顺序就是语义**"**一个字没变** ✓，变的只是**用什么手势去排**；两边的对照写在本文件对面的 [`editor-ui-brief.md`](editor-ui-brief.md) 的「动工前的决定（用户 2026-09-30）」条 ⑥ ✓
- **可进任何序列**：不受第二节那些形态规则约束
- **一条序列里不叠同类** ⚠ 两个「多重释放」会立刻炸成 4 个、8 个，点数也算不清 ⚠ **用户 2026-09-30 定（份数类）**：**两个"能变多"的零件叠在同一个技能前面 = 相乘** ✓（一分为 3 + 多重释放 2 ⇒ **6 份**）；**消耗也跟着相乘**（每份各付各的）✓；**组合本身暂不加价**（那个"组合费"旋钮 `stackPenaltyPerPoint` **留着**、现在 = 0）✓。⚠ 这**改掉了**旧算法"**相加 `X + N − 1`**"（[日志 51 §6.1](log/2026-09-30-51-multifire-and-split.md) 专门论证过"相乘会把同一个技能数两遍"、还拿"相乘会说 6 份"当反例 + `sim/trigger.ts` 的 `groupPlanOf`）—— 旧说法**并列保留、一个字没删** ✓，**以用户 2026-09-30 为准** ✓；⚠ "**不叠同类**"这条本身**不变**（叠的是**不同类**的份数动词）✓，完整那 15 条见 [`editor-ui-brief.md`](editor-ui-brief.md) 的「动工前的决定（用户 2026-09-30）」条 ④ ✓
- **编辑界面是它自己的一套** ⚠ 和普通技能不同：普通技能讲"前摇 / 命中 / 后摇"，
  修饰技能讲的是"一条改写规则" ⚠ **用户 2026-09-30 定**：**修饰零件的参数在界面上可改** ✓ —— 交互路径 = **在术式界面点中修饰零件 → 进入修饰零件自己的编辑界面修改** ✓（改的是**术式里的副本** `SequenceSegment.mods` 的参数；⚠ 下面"**原型**只能看、不能建、也不能改"那一句**并列保留** —— 对象不同，原型那一侧的口径没变 ✓）
- **副本只属于这份术式**：从技能库拖进序列 = **得到一个副本**（原型没填条件，所以不能用）；
  这个副本**不进技能库**、**别的术式引用不到** ⚠ **数据结构与分享码都要跟着带上它**；
  **术式"另存为"时副本跟着深拷贝，且之后两份互相独立**
  （普通技能相反：序列里存的是**引用**，另存为不深拷贝）

### 两个已定的具体零件

**「多重释放」（原「双重释放」）**

- N **可调**，**默认 2**，**上限 10**
- **点数随 N** 变（不是固定值）
- **只作用于瞬发技能**
- ⚠ **不能放在蓄力/持续技能前面**（那两种必须在序列最前面，见第三节）
- 同时放出去的那几个技能**共用一个意图**（见第九节）

**「触发器」**

- 语义：**前一个技能被触发之后，激活它后一个技能**
- **触发条件可编辑**（条件那一套和技能里的规则共用）
- **要能设置那个技能生成在哪里** → **四选一**：
  1. 施法者身上
  2. 瞄准落点 —— ⚠ **用户 2026-09-30 定为**：**取"玩家按下这个技能那一刻"的瞄准** ✓（**不是**实时的鼠标位置 ✗ —— 那要新增一条每帧输入通道 + 联机同步，**以后再说** ✓）。⚠ 旧说法（今天**静默退化成"最近的敌人那个方向"**：`modifier-verbs-draft.md` L90 + 日志 48 §待裁定 3；"置灰 / 维持退化"那两案写在 `editor-ui-brief.md` §七 / §八 L474）**并列保留、已作废** ✗ —— **以用户 2026-09-30 为准** ✓
  3. **触发它的那个技能的命中位置**
  4. 失效位置 ⚠（这一项的确切含义还没定，见欠账）—— ⚠ **用户 2026-09-30 已定**：**失效位置 = 触发它的那个实体"没掉"的地方** ✓（火球落地炸开处 ✓ 召唤物被打死处 ✓）；"没掉"今天有机制可依 —— 那个载体**不在世界里了**（到期 / 被打掉 / 撞墙都算，见 [日志 55](log/2026-09-30-55-carrier-expiry.md)）✓。⚠ 上面那句"还没定"是**旧的**、**并列保留** ✓，**以用户 2026-09-30 为准** ✓。⚠⚠ 同一次还定了**界线**：**触发器只能被"实体类"触发** ✓（投射物 / 落点区域 / 召唤物 —— 会自己在世界上活着的东西 ✓）；**"自身状态"（血量 / 护盾 / 身上的状态）归监测器** ✓ ⇒ 所以「**护盾碎掉 → 触发后面的技能**」要写成**监测器** ✓、**不是触发器** ✗。⚠ **并列保留、不替谁圆**：既有分类句"**监测器 = 触发器的一种**"（[日志 48](log/2026-09-27-48-modifier-trigger.md) / `STRUCTURE.md` 条 70 / 条 133）—— **分类**以用户 2026-09-30 的界线为准 ✓；那句"同一个执行器"（`sim/trigger.ts` 的 `fireModifier`）该读成"实现共用"还是作废，**留待实现那一轮**，本文不裁定 ✗。✅ 既有一致：出厂「背水」（低血 → 撑盾）本来就落在**监测器**那一侧 ✓。⚠ 顺带（同一次决定）：**监测器加"每隔 X 秒最多触发一次"，默认关** ✓ —— 旧文把它列成"待用户签字 / 未裁定"（`editor-ui-brief.md` §八 L480 + 日志 48 §待裁定 5），**以用户 2026-09-30 为准** ✓；界面上那个秒数控件的落点见 [`editor-ui-brief.md`](editor-ui-brief.md) 的「动工前的决定（用户 2026-09-30）」条 ⑫ ✓

### 第三个已定的具体零件：「等待 X 秒」（**定稿 2026-09-21**）

**是什么**：**序列里的一段空档** ✓ —— 插在某一格**前面** ✓，
让**后面的技能晚 X 秒才发生** ✓。

⚠ **它不是"两件事同时进行"** ✗：它**不并行**、**不叠任何效果**，
唯一的作用就是**把时间往后推**。（想做"同时放"用「多重释放」，见上面那一节 ✓。）

**期间施法者被占用** ✓ → **不能继续释放技能 / 术式** ✓ ——
它和**施法时的硬直是同一套机制** ✓（引擎里就是"阶段锁"，`Phase.locks`，见下）。

#### ⚠ 玩家 2026-09-21 定的三条细节

**① "锁哪些能力"做成这个修饰的参数** ✓

- 移动 / 攻击 / 施法 / 转身 —— **四项可勾** ✓

## 九、意图（Intent）

**定义**：意图就是玩家**这一次激活**给出的那**一个**"指向"（朝哪儿 / 点在哪儿 / 打谁）。

三个存在理由：

1. **一次输入只有一个指向** —— 玩家按一下，不可能同时给出两个方向
2. **技能各自解释它，而不是各自获得它** —— 同一个意图，"横砍"读成朝向、
   "火墙"读成落点 ✓（这也解释了为什么同时放出去的几个技能**共用一个意图** ✓）
3. **联机时要把它发给对方** —— 它是"玩家这一次想干什么"的最小数据
   （见 [`lan-feasibility.md`](lan-feasibility.md)：输入是网络上要传的东西）

⚠ **意图 ≠ 瞄准方式**：瞄准方式（`directional` / `auto` / `locked` / `areapoint`…）
住在**技能**上，是"这个技能怎么解释意图"；意图是**玩家这一次给的那一个指向**。
混起来的表现是"两个技能都想自己拿一个意图"，而一次输入只有一份。

### 三条判据（按**这一段的序列**是常驻还是主动分 —— **不是**按系别、也不是按"有没有序列"）

| 术式 | 合计 | 血契 |
| --- | --- | --- |
| **纯主动术式**（只有主动序列） | **可以为负** ✓ 为负 → **释放时消耗血契** ✓ | 能吃 ✓ |
| **纯常驻术式**（只有常驻序列） | **不能为负** ✗（报错）；**为正 → 黄色警告**（"为正没有什么用"，白给了额度） | **不能吃** ✗ |
| **混合术式**（两种序列都有） | ⚠ **只有常驻那一边受约束**：**常驻序列的点数和 ≥ 0** ✓（不许为负 ✗）；**主动序列照旧可以为负** ✓（**不要求**主动那半配平） | 能吃 ✓：`max(0, −主动和)`（**常驻那边的正额度不能补贴主动**，见下面那节） |

**为什么混合术式里"常驻那半边必须自己平"**（用户原话的意思）：不平的话有一条白嫖路径 ——
**一条超模的常驻序列 + 一条亏模的主动序列**，两者合计正好平；而玩家**从不使用**
那条亏模的主动序列，于是超模的常驻部分是**净赚**的。
⇒ 要求"常驻那半边自己 ≥ 0"就把这条路堵死了 ✓。

⚠ **而主动那半边照旧自由**：主动序列**可以**为负、**照旧**消耗血契，**不要求**它配平。
也就是说混合术式**仍然能吃血契** ✓（早先一版写成"混合术式再也不能吃血契"，
**那个版本作废**）。

**同时"超模常驻依然允许存在"** ✓ —— 只要在**常驻那一边**用另一条亏模常驻抵消。
