# 时间控制（JOJO 的「世界」）可行性

- **日期**：2026-09-21
- **为什么有这份文件**：玩家说「时间控制可以最后加，但**要保证可行**」。
  所以这里论证的不是"怎么做得漂亮"，而是**"现在这套架构会不会挡住它"**。

## 结论：可行，而且**不需要新机制**

需要的只有一件事：**把"按 dt 推进"的每一处，乘上这个实体自己的时间倍率。**

```ts
char.timeScale   1 = 正常，0 = 时间停止，2 = 加速
```

这个属性走**已有的修饰符系统**（`modifiers` + `op: 'mul'/'set'`），
所以"开世界"就是给自己挂一个 `timeScale: 1` 的状态，
给其他所有人挂一个 `timeScale: 0` 的状态 —— **内容就能写出来，引擎不加新概念。**

## 为什么说它不会挡住

| 担心的事 | 实际情况 |
|---|---|
| 会不会破坏确定性（同种子必须逐字节一致）？ | **不会。** 时间倍率是**模拟状态**算出来的，不是墙上的钟。`world.dt` 仍然是唯一的时间源，只是被一个确定性的系数乘了一下 |
| 要不要引入新的时间源（真实时间 / performance.now）？ | **不要。** 那是纪律 4 明令禁止的（`tests/purity.ts` 盯着），而且会直接破坏重放 |
| 现在的顿帧是不是挡路？ | 不是。`world.hitstop` 是**全局**的（整个世界停一下），它是另一码事。要做的是**按实体**的倍率，两者不冲突，可以共存 |
| AI 怎么办？ | AI 的思考间隔（`aiThinkAt`）也要乘倍率。不乘的话，被停住的人还会"想事情"——虽然动不了，但会在停住期间把技能都 CD 好 |

## 真正的工作量在哪

**不是架构，是"漏一处"的风险。** 每有一个"按 dt 推进"的地方，
就得记得乘倍率。数一下现在有多少处：

```
状态倒计时 tickStatuses      冷却 tickCooldowns        施法 tickCasts
能量回复 regenerate          存在时间 tickLifetime     位置积分 integrate
常驻 onTick                  状态 onTick 钩子          AI 思考间隔 aiThinkAt
```

**漏一处的后果是"时间停了但血还在回"**这类局部漏洞 —— 不致命，但很难查，
因为这个 bug 只有在"时间停止"那一瞬间才看得见。

## 所以做的时候要配一条测试

不是"断言某个函数返回了 0"，而是：

1. 停住世界，跑 120 tick，断言**被停住的人**：位置没变、冷却没走、
   血和能量没回、身上的状态剩余时间没减
2. 断言**开了同样技能的人**：上面每一样都照常
3. 断言**同种子两次跑出来逐字节一致**（`tests/sim.ts` 那条的延伸）——
   这条最重要：时间控制是最容易把重放搞坏的一类功能

## 一个要提前定的设计问题

**"时间停止"是被停的人看不见你，还是你也打不动他们？**

现在的引擎里没有"谁在什么时间层"这个概念，两边都能表达，
但它们对玩法的影响完全相反：
- **只停人、不停伤害** → 时间停止变成纯粹的爆发窗口（强）
- **连伤害一起停** → 它更像"脱离战场重新部署"（弱，但更自洽）

这个问题等真要做的时候该由玩家定，**不该由代码顺手决定**。
