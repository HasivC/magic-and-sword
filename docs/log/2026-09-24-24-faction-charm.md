# 改阵营（魅惑）：`factionOf` 是唯一的判据

- **日期**：2026-09-21
- **触发**：玩家在优先级清单里选了第 4 项「改阵营」。原话需求（更早那条构想清单）：
  > 植物大战僵尸的魅惑机制，把敌人变成队友
- **动了哪些文件**：
  `schema/skill-schema.ts`、`src/sim/{types,status,world,targeting,attributes,conditions,projectile,pipeline}.ts`、
  `src/pricing.ts`、`src/validator/checks.ts`、`src/cli/{battle,run}.ts`、`web/src/main.ts`、
  `content/skills/charm.json`（新）、`content/techniques/charm.json`（新）、`content/manifest.json`、
  `tests/scenario.ts`

## 一、缺口是什么

`faction` **只在 spawn 的时候定**，之后再也没有任何一条路能改它 ——
`attribute` 载荷只能改存储属性和管线伪属性，而 `faction` 是个枚举。

而 schema 里那句注释「魅惑就是改这个字段」已经写了很久。**能改它的机制一直没做。**

## 二、做法：把它做成**状态字段**，不是"改阵营的动作"

```ts
StatusDef.faction?: 'caster' | 'player' | 'enemy' | 'neutral'
```

选状态而不是动作，是因为魅惑在玩法上天生是两件事，
而**状态本来就把这两件事都解决了**：

- **临时的** → 时长到了自己还原，一点额外机制都不用加
- **能被驱散** → 净化类技能按标签就能摘掉它

想写永久的叛变，`duration: -1` 就是了。

### `'caster'` = 跟"挂上这个状态的人"同阵营

这一条是**最值钱的地方**：同一份技能，玩家放出来敌人变友军、
敌人放出来玩家变敌军 —— **一份内容两边都对，不用写两份**。
这就是纪律 1（一切按阵营动态查询）在内容层的兑现。

它在**施加的那一刻**就解析成具体阵营（`applyStatus` 里查一下来源实体）。
不这么做的话，`factionOf()` 就得拿着 world 满地图查来源，
而它是被 `matchesValid` 这类热点函数调用的。

## 三、真正的工程量在"别漏"

光加个字段没用 —— 引擎里到处都在直接读 `entity.faction`。
**漏一处的表现是"被魅惑的敌人还在打你，只是颜色变了"。**

所以新增了唯一一个查询函数：

```ts
export function factionOf(entity: Entity): Faction
// 规则：**最后挂上的那个带阵营的状态说了算**
```

然后把**所有**直接读阵营的地方换成它（一共 9 处）：

| 文件 | 原来在读什么 |
|---|---|
| `targeting.ts` | 命中判定 `isHostile`、`matchesValid` 的友军判断 |
| `world.ts` | `findHostile` / `findAlly` / 快照 |
| `attributes.ts` / `conditions.ts` | "谁是友军"这类查询 |
| `projectile.ts` | 投射物归谁的 |
| `pipeline.ts` | 召唤物跟召唤者同阵营 |
| `cli/battle.ts` / `cli/run.ts` | 战报里的阵营标签 |
| `web/src/main.ts` | HUD 的**敌人计数**和配色 |

最后那条特别容易漏：HUD 数敌人用的是 `e.faction === 'enemy'`。
不换的话，被魅惑的敌人**还在敌人的计数里** —— 界面在骗人。

**为什么"最后挂上"而不是"第一个"：**
被策反回来又被策反过去，当前状态该是后者。取第一个的话，
第二次策反会**静默失效**（有测试钉这一条）。而且它依赖的是状态数组的顺序，
**确定**，不碰任何集合遍历顺序（可重放是底线）。

## 四、顺带补的计价项

`faction` 以前**不参与定价**。而"把敌人变成队友"是这个引擎里最强的一类效果
（对方少一个输出、你多一个）—— 不定价的话，**魅惑就是白送**，账上看不出来。

新增 `factionOverridePerSecond`（按**秒**算，因为魅惑 3 秒和 30 秒完全不是一回事）。
方向沿用整本账的老规矩，由 `toSelf` 决定：

- 把**敌人**变成自己人 → 对施法者是收益 → 消耗额度（负）
- 把**自己**变成敌人那边（精神被控）→ 代价 → 提供额度（正）

标定后 `策反` 的账：`收声` +3.57、`低语` +1.94、状态 **-4.00**，合计 **+1.51**（容差内）。

## 五、出厂内容

`tech.charm`「策反」：锁定 6 米内的敌人，把它变成你的人 10 秒
（`faction: 'caster'`，`duration: 10`）。

⚠ 它**没进演武场的默认 10 格** —— 和上一轮的「血祭斩」一样：
每一格都被测试盯着，而换键现在是玩家的活（编辑器里装到任意一格就行）。

## 六、验证

```
npm test          890 个断言全过（13 个测试文件）
                  └─ tests/scenario.ts 第 40 节（147 → 160 断言）
                       阵营被盖掉 → 不再是敌人、锁定不到你、算你的友军
                       到期自动还原 → 又锁定得到你
                       最后挂上的说了算；摘掉之后回落到前一个
npm run validate  54 个文件 · 54 通过 · 0 失败 · 14 警告
npm run typecheck 干净（两份 tsconfig）
npm run calibrate 最大残差 1.53 ≤ 容差 2
duel（12 秒）      逐字节不变 ← **这一条是这次重构的关键回归信号**
                  它证明"把 9 处读法换成 factionOf"没有改变任何非魅惑单位的行为
build:web + 页面   通过 / 200
```

`duel` 那条值得单独说：改阵营这事儿最容易出的错就是"顺手改坏别人的行为"。
逐字节不变说明这次只是**加了一条路**，没有动原有的路。

## 欠账

- **魅惑之后原有的状态怎么办，没有规则。** 玩家给敌人挂的减速、
  敌人自己身上的护盾 —— 换阵营时它们不会变。
  现在的内容里没有会因此出问题的组合，但"诅咒一个敌人再魅惑它"迟早会撞上。
- **`factionOf` 的"最后挂上说了算"是任意定的**（虽然合理）。
  如果以后要"强的压制弱的"（比如永久叛变压过临时策反），
  就得换一套优先级规则 —— 那就不是"最后一个"了。
- **`AFFECTS_OTHERS` / `SIGN_CHANGING` 两张表仍然内容重复**
  （上一轮记下的欠账，还没收拾）。
- **召唤物的阵营在 spawn 时就定死了**（`faction: 'caster'` 解析成具体值），
  所以"把召唤者魅惑了，它的召唤物跟着换边吗" —— **不会**。
  那是另一个语义问题，现在的答案是"不换"，但没有任何地方写下来。
