## 一、负值术式（原来叫"超模术式"）

名字换成玩家定的那个。改的不只是名字 —— 一整条链从"账面上的警告"变成了
**能放出来的东西**：

| 环节 | 之前 | 现在 |
|---|---|---|
| 点数合计为负 | 警告"超模技能，要拿血契付" | **警告"负值术式，每次释放消耗 N 血契"** |
| 血契 | 只是账上一个**算出来的数**，没有任何地方读它 | **一条真实的存储属性** `char.bloodPact.current` |
| 释放时 | 照放，不扣任何东西 | **不够就放不出来**（`reason: 'bloodPact'`），够就精确扣掉 |
| 界面 | 看不出哪一招要花血契 | 技能栏那格标出消耗和**还差多少**，HUD 一直显示血契 |

### 怎么扣、什么时候扣

`canActivate` 加了一条判据，`activate` 在**施法开始的那一瞬间**一次性扣清。
不摊到阶段里扣 —— 它是整个术式的代价，"放完第一段就被打断"再退一半资源
反而说不清规则。

血契消耗这个数是**算出来的**（`|点数合计|`），而算出它的 `src/pricing.ts`
**不在 sim 里**（sim 不认识"点数"）。所以由调用方在编译时传进去，
编译产物带一个数字，`cast.ts` 只读它：

```ts
compileTechnique(tech, lookup, { bloodPactCost })   // 调用方从 priceTechnique 拿来
```

⚠ 这里有个**静默失败**的风险：漏传的话负值术式不扣血契，等于白送一整套爆发，
而且没有任何地方会报错。所以：
- 拼装逻辑只有一份（`pricing.ts` 的 `bloodPactCostOf` + `priceOptionsFor`）
- 浏览器里**平衡配置必须先于内容加载**读进来 —— `loadContent()` 末尾就要重编译，
  顺序反了第一局全部 `bloodPactCost = 0`

## 二、血契从哪来：玩家给的抽象是"进入危机的行为"

> 是让玩家"进入"危机的行为（无论是玩家主动还是被动），例如血量降到极低时、
> 获取了某个负面 buff、在商店拿属性上限抵押等来获取若干血契

引擎只提供**能力**（加一条属性 + 一个新的触发时机），数额全在内容里：

```json
// content/skills/blood-pact.json —— 挂成常驻术式的"记账器"
when: onLowHp            → char.bloodPact.current += 3
when: onStatusApplied    → 如果身上有 debuff / curse 标签 → += 2
```

新增的触发时机 `onStatusApplied` 是这条渠道唯一需要的新机制。两个设计约束：

- **只在第一次挂上时触发**，刷新时长和叠层不触发。否则一个每秒重挂一次的
  debuff 就是血契刷子 —— `status.ts` 只在新建时入队。
- **晚一 tick 结算**。`applyStatus` 跑在伤害管线**里面**，而规则又可能施加新状态 ——
  当场触发就是递归，深度还取决于内容怎么写。排队到 `stepWorld` 的固定位置再跑，
  深度恒为 1。代价是 16ms，不可感知。

⚠ 血契**没有任何 regen**。这是它和能量的本质区别：能量是节奏，等一会儿就回来；
血契是这一局攒出来的资本，只能拿危机换。测试里专门有一条钉这个
（用一个**没有敌人**的世界跑 5 秒 —— 借演武场测的话敌人真的在打你，
血契会因为真实收入而涨，测不出"有没有 regen"）。

## 三、量和局：一局攒一发

玩家定的：**日常在 10 上下，偶尔冲到 100**；一局里一直不用，攒到最后一关
放一发秒 Boss 的终极。

所以内容里的数额是：残血 +3、挂上负面状态 +2 —— 一关大概 10~15 点，
五关一局 70~90，**一整局不花**才够一次 100 的终极。具体数字以后按手感调。

**局 vs 关卡**（玩家特别提醒要区分，而且选了"先做血契本身、关卡串联下一轮"）：

```
R  重开本关   打失败了再来一次，攒的血契**留着**（不然每次失误都在惩罚积累）
N  新的一局   从头开始，血契**归零**（局内资源，不跨局）
```

实现上刻意**不加参数**：`newRun()` 先把玩家身上的血契抹成 0，再走正常的
`restart()`（它第一步就是把当前血契揣兜里）。两个动作共用一条代码路径，
区别只在于抹不抹那一下。加一个 `restart(fresh: boolean)` 的话，
十几个调用点每个都得想一遍该传什么。

⚠ **关卡串联还没做**，所以现在"最后一关"这件事还不存在 ——
血契能攒能花，但跨关卡累积要等下一轮。

## 四、射程计价：相对于载体自己的标准值

玩家定的形状：

> 不同的技能有不同的标准值（近战技能近，远程技能远），多了则计价、
> 少了则补贴点数。这样近战技能想打得远就要付出代价。

所以这是**唯一一条相对的轴**（别的都是绝对值相加）：

```
每个载体类型有自己的标准射程（取的是出厂内容里这类载体的典型值）
  扇形 2.5 米   突刺 6 米   光束 8 米
偏离标准的部分才计价：长了 = 收费（负），短了 = 补贴（正）
```

这是玩家最早提的那个例子本身 ——"**牺牲射程换伤害**"。在它存在之前，
射程是**免费**的：裂地斩的扇形半径从 2.5 米拖到 12 米，账面纹丝不动。
（定价表以前根本不看 `delivery` 这个字段，这次才发现。）

**范围收窄**：玩家选的范围是"扇形半径 / 光束长度 / 突刺长度"这三个。所以
`area` / `aura` 的 radius（那是**范围大小**，不是打得多远）和 `projectile`
的飞行距离**不在**这条轴上。范围大小该不该单独计价还没定，是个欠账。

标定后 `rangePerMeter = 0.295`，最大残差 **1.78 ≤ 容差 2**。

## 五、标定器：不该拿"故意歪的零件"去拟合汇率

加完两个新技能之后 `npm run calibrate` 的最大残差从 1.57 跳到 **3.23**。
原因不是汇率错了，是**目标集错了**：标定器默认"每个技能都该配平到 0"，
而新模型下技能是**零件**，可以故意歪 —— 拿两个自由参数去拉整张表，
数学上误差更小，实际是把别的技能的账全带偏。

所以加了 `NOT_FITTED`（带理由）：

```
skill.blood-offering  负值零件：故意不平衡，歪多少是设计定的
skill.blood-pact      收入被动：它发的是血契，而血契还没有计价项
```

它们仍然被校验器检查（负值术式必须能算出血契消耗），只是不参与
"汇率该是多少"。

## 六、踩到的两个坑

**1. 编辑器点表把血契判成"格子外"。**
血契的数额（3 / 2）落在通用兜底表 `[-4,-3,0,1]` 之外，`tests/editor.ts` 立刻红灯。
这不是内容错了，是**表错了** —— 血契是一门**货币**（玩家的量级是 10、偶尔 100），
和"扣 3 点能量"那种加减法不是一个量纲。补了一张 `BLOOD_PACT_AMOUNTS`
（1/2/3/5/8/15/30/60/100）走 `walk` 的 `override` 机制。

顺带踩了两个小坑：常量声明在 `VALUE_SETS` 之后 → **TDZ**；
以及第一版想在 `path` 上判 `bloodPact`，但路径里的那段是完整的属性名
`char.bloodPact.current`，`Array.includes` 精确匹配**静默匹配不上**。

**2. 血契不在 `stored` 里 → 一改就抛异常。**
`spawn()` 默认只给 `char.hp.current` / `char.energy.current`，
而"这个属性能不能被动作改"的判据是 `owner.stored.has(path)`。
不在里面 → 攒血契的那条规则一跑到就抛。测试当场抓住了。
现在 `spawn` 默认给上它（任何实体都能收血契，将来"敌人也攒血契"不用再动）。

## 欠账

- **关卡串联**（玩家选的"下一轮"）。现在"攒一整局、最后一关放终极"这句话
  还缺"最后一关"那一半。
- **血契经济没有实测**。收入 +3/+2 和消耗 ~8 都是我的估计，
  真正的量级要等你玩过之后按手感调 —— 而且它跨局累积，不玩是算不出来的。
- **`area` / `aura` 的半径还没有计价项**。它是"范围大小"，不是"射程"，
  该不该单独一条轴没定。
- **投射物的飞行距离不在这条轴上**（玩家选的范围不含它）。一个 36 米外
  飞过去的狙击箭，射程仍然是免费的。
- **`onStatusApplied` 只在常驻术式的规则上跑**，状态自己的钩子还不能挂它。
- **`links` 仍然没有计价项**（带条件的段和无条件段同价）。
- **Electron 外壳**（玩家选了 Electron）。这一轮没动 —— 它是独立的一块，
  而且**换外壳不会让界面变好看**（那是 CSS + 素材的事，我已经跟玩家说过）。
