## 1. 账怎么变成整数的（这是这一片的正身）

### 1.1 两条规格 + 它们在哪里打架

| # | 规格（用户的话） | 落地 |
| --- | --- | --- |
| ① | 逐条取整 + 余数累积（**最大余数法**） | `pricing.ts` 的 `integerPointsOf` |
| ② | 每条都是整数，而**各条之和仍然等于合计** | 合计 = **各条加出来的那一个数**（不再单独取整） |
| ③ | **每个非零条目至少 1 点**（不许"账面上几乎免费"） | 取 `floor` **之前**先把非零条目钳到 `±1` 起步 |
| ④ | **合计 ≥ 0 能用 / < 0 要付血契**，产品容差**删掉** | `kindOf(total)` = `total < -POINT_EPS ? 'negative' : 'normal'` |

### 1.2 算法一步一步（`integerPointsOf`）

```
输入：一串**原料值**（小数，正负都有）
1. 每条判"是不是 0"：|v| < POINT_EPS(1e-9) ⇒ 当作 0（**浮点噪声不会变成一笔账**）
2. 非零的钳到"至少 1 点"：0.12 → 1、−0.85 → −1（⚠ **这一步先做**）
3. 每条取 floor（**向 −∞**）：正负一视同仁 ⇒ 余数永远落在 [0,1)
4. 要补几格：delta = round(Σ钳过的值) − Σ地板      （⚠ **这个 round 是对合计做的**）
5. 补格子的顺序：余数从大到小；**余数相同按下标**（稳定 ⇒ 每次算出来逐位相同）
```

⚠ 为什么用 `floor` 而不是 `trunc`：`trunc` 会让**负条目**的余数是负的，
于是"补格子"在正负条目之间变成抢格子 —— 那正是用户点名要问的那一条
（"负条目和正条目混在一起时余数怎么分"）。用 `floor` 之后
`delta` **恒 ≥ 0 且 ≤ 余数 > 0 的条目数**，所以地板上的数**只会被抬高** ——
"钳过 ±1 的条目不会再掉回 0"就是这么证明的。

### 1.3 ⚠⚠ 两条规格真的会打架（**判断项，等用户裁定**）

`integerPointsOf([0.4, 0.4, 0.4])`：

- 原料合计 = 1.2 ⇒ "对合计取整"该给 **1**；
- 但"每个非零条目至少 1 点"要求三条各 **1** ⇒ 合计只能是 **3**。

**本实现选后者**（用户点名的那条更硬：不许有"几乎免费"的条目；而且
**账的定义就是各条之和**）。⇒ 差别只出现在"某一条的原料小于 1 点"的时候，量级 ≤ 1 点 × 条数。
⚠ **如果用户想要"合计永远等于原料合计的取整"，说一声** —— 那就得允许某些非零条目印成 0。

### 1.4 整数化**只在出口**做（一个很容易做错、错了不报警的地方）

相对账是"现在 − 出厂"。如果**两头各自先取整**，那 `0.3 秒 → 0.9 秒` 这种小改动
会在两头各自被 ±1 的地板抹平，相减得 **0** ——
"用户改了一件事、账上一个字都没有"。

⇒ **原料在 `absoluteEntries` 里相减，最后对本账条目取一次整。** 实测：
`0.9 − 0.3 = 0.6` 还在，取整之后是 **+1 点**（看得见）。
这一条是**实现事实**，写在这里免得下一个人以为是 bug。

### 1.5 出厂内容：**0 取整还是 0**

`skillLedger(s, s)` 两头是**同一份技能**、走**同一条确定性路径** ⇒ 逐条差值恒为 0 ⇒
空账、合计 0。⚠ 这一条是"出厂全 0"那个常驻断言的机械依据，没有例外。

## 6. 待裁定项（⚠ 规格没写清、我没有自己定的地方）

1. **两条规格打架时听谁的**（§1.3）：三笔 0.4 点 ⇒ 账上 1/1/1（合计 3），
   而"原料合计取整"是 1。**本实现选了"每条至少 1 点"**（账 = 各条之和）。
2. **epsilon 取多少**：我取了 **1e-9**（`POINT_EPS`）。整数化之后它几乎用不上，
   只当浮点护栏（噪声不造账 / 真整数不掉格）。
3. **`floor` 还是 `trunc`**：取 `floor`（向 −∞），理由是"余数永远非负"（§1.2）。
   ⚠ 副作用：`−1.5` 的 `round` 是 `−1`（JS 的 `Math.round` 是"向 +∞ 取半"），
   也就是**正负在 .5 上不对称** —— 要不要改成"半值远离 0"，请裁。
4. **绝对账要不要也上"至少 1 点"的地板**（§3 末）：现在**上了**，
   代价是 `calibrate` 的残差 1.47 → **7**。若只要"玩家看到的那本账"整数化，
   撤掉 `priceSkill` 那一个出口的整数化即可。
5. **几条小增量在整数账上被吃掉**（§5 末）：排布的"每米 / 镜像角"跨不动一格。
6. **`calibrate` 的新阈值**：我把"残差 ≤ 容差 2"换成"**≤ 1 格（1 点）**"。
   规格没写标定该拿几格当合格。
7. **`BalanceConfig.balanceTolerance` / `PriceOptions.tolerance` 两个字段**：
   **只留在类型里、没有任何地方读**（理由是 `web/src/**` 当轮冻结，它读这两个字段）。
   ⚠ 能改 UI 的那一轮应该**把它们和 `_balanceTolerance_removed` 那段说明一起删干净**。
