## 改了什么 / 为什么

### ① 编译问题**结构化**（用户点名的 UI 前提）✓

`CompileProblem` 原来是**扁平**的 `{ techniqueId, skillId, message }` —— **段号只写在文字里**
（"序列段「第二段」上的修饰副本…"）。界面要把提示画在**有问题的那一条序列下方**，
就得去**解析自己写的中文**：那是拿文案当数据结构，文案一改界面就瞎。

⇒ 新增四个**可选**字段（**文案一个字都没改**）：`segmentIndex` / `skillIndex` / `modIndex` / `paramKey`。

- **三个下标同时缺席 = "整门术式那一层"**（容器自己没有段号）—— 用 `undefined` 说这件事，
  **不用 `-1` / `0` 冒充**（`0` 是第一段，`-1` 是"界面必须特判的魔法数"）。
- `skillIndex` 用**原始下标**（含查不到的技能 —— 和 `SegmentMod.at` 同一个坐标系），
  因为界面画的是**数据里那一行**，而编译后的 `skillIds` 会把查不到的技能跳掉（少一个就整体错位一格）。
- `modIndex` 有它才画得到"**是哪个副本**写错了"（一段里可以挂好几个副本，只要不同类）。
- `paramKey` **只在"某一个参数坏掉"时才有**（`radius` / `turnRate` / `proto` / `at`…）；
  "整个副本不存在"那种也有一个落点：`proto` 这个字段本身。
- ⚠ **多段的问题锚在第一个出问题的段上**（"常驻包装在非 press 术式里"那条一句话管好几段）——
  `message` 里仍然把段号列全，这里只给界面一个落点。
- 产出点 **11 处**全改：容器技能链（`UNKNOWN_SKILL`）、段技能链（同一个函数，多传一个段号）、
  常驻包装那条、以及 `compileMods` 里那 8 条（原型不存在 / `at` 越界 / 份数夹住 / 等待夹住 /
  摆法认不出 / 三个角度 / 半径 / 追踪两个数 / 弹射两个数）。

### ② 「环绕」对"从施法者身上长出来的载体"**不生效** ✓

用户定的：载体的位置**就是施法者**（`meleeArc` / `self` / `aura` / `beam` / `capsule`）⇒
环绕**什么都不做**（它做的唯一一件事是把"载体中心"摆到半径 R 的那一圈上，对它们没有意义）。
⚠ **不是警告**（用户明确划的）—— 照「追踪」/「弹射」那条规矩，提示由**界面**画在那条序列下方，
引擎不出声。

- ⚠⚠ **判据一行都没新写**：读的还是 `school.ts` 的 `carrierFliesInWorld`
  （和追踪 / 弹射的警告、账本"不收钱"**同一个函数**）。
  新增的只是一个**收集器**（把技能里的 `delivery.kind` 收出来，**一个判断都不做**）——
  这一份住 `src/sim/compile.ts`：`sim` 不许 import 校验器（分层），
  和 `validator/` / `pricing.ts` 里那两份是**同一个形状的三份**，而**判据仍然只有一处**。
- ⚠ **落点在编译期**（`CompiledMod.layout.carrierFlies`）：sim 里没有内容层，
  运行时的 `layoutPlanOf` 拿不到 `Skill` —— 这和 `count` / `waitSeconds` 是同一个理由
  （编译期读好，运行时只读产物）。
- ⚠ 读的是**副本修饰的那个技能**（`skillList[mod.at]`），和校验器那两条警告**读同一个位置**；
  两处读不同的技能会出现"校验器说它起作用、引擎什么都不做"。
- ⚠ **只有 `ring` 那一档受它管**：`fan` / `mirror` 改的是**方向**，
  长在施法者身上的载体照样转得动（一记横扫本来就该能散射 / 镜像）。
  用户点的是「**环绕**」那一档，不是整个零件 —— `tests/scenario.ts` 第 52b 节有一条**门闩**盯着它。

### ③ "没目标就什么都不发生"**通用化** ✓

以前只有**位移**那条是这样（`anchor: 'target'` 选不到目标 ⇒ 直接 `return`）。
推广到**所有"需要目标"的动作**：删掉 `sim/pipeline.ts` 里那两句
`ctx.target ?? ctx.actor`（`resolveActionTarget` 和 `pickActionTargets` 各一句）。

为什么那两句必须清掉：瞄准的目标不在了，动作会**静默地落到施法者自己头上** ——
打人变成**自伤**、给敌人挂状态变成**给自己挂**，而且一声不吭。

- ⚠ **"本来就打自己"的内容不会误伤**：`runTechniqueRules` 先判
  `tech.targeting.valid` 是不是**清一色 self** —— 是的话 `ctx.target` **就是**施法者（那条路没动）。
  拦下的只是"合法目标不含自己、又没选到任何目标"那一种。
- ⚠ 想"无论如何都打自己"的动作请**显式写** `target: 'self'`（定稿口径：落点是**每条动作一处**）。
- ⚠⚠ **状态钩子的 `onTick` 是例外，而且是"明写"的例外**：`tickStatusHooks` 的 ctx
  原来**不填 `target`**，持续伤害全靠那句兜底 ⇒ 兜底一清，`soul-rend` 的裂魂创伤**当场变成白挂**
  （`tests/battle.ts` 那三条 DoT 断言会红）。⇒ 现在**显式**填持有者，
  理由写在那个函数里：持续伤害 / 持续扣能量的**语义**就是"这个状态折磨挂着它的那个人"，
  而且账本那一侧早就这么认了（`pricing.ts` 的 `defaultTargetOf(when, inHook)` 对钩子里的
  `onTick` 返回 `'self'` —— 那一行现在和代码**逐字对上**）。
- ⚠ **顺带要清的那条旧层残留**（"动作不写载体就继承术式的载体"）**跳过**：
  照 `docs/sequence-and-modifier-model.md` §275 那句话去找落点，**引擎里已经没有这个东西**了 ——
  术式那一层**没有 `delivery` 字段**（瞄准 2026-09-21 就搬到技能层了，日志 47），
  `pickActionTargets` 的"退回单体"退的是 `ctx.target`（这次命中里"对面那个"，`onHit` 那类
  反应动作**正需要它**），不是"术式的载体"。⇒ 文档那句话**已经过期**，把它标在报告里，
  没有硬去改一处不存在的东西（`grep delivery src/schema.ts` 0 命中）。

### ④ CD 名牌按技能 —— **跳过**（落点不清）

用户给的口径是"改成按**技能**记（`cd.<skillId>`）"，动机是"带序列的术式那一格在 HUD 上空着"。
**两条读法都能自圆其说，但各撞一堵墙**，所以按纪律**没硬做**：

| 读法 | 会撞到什么 |
|---|---|
| **A. 键 = 绑在键上的那个术式（容器）** —— 键用 `cast.homeTechnique.id` | 界面上那一格**真的会亮**起来，但 **`blink` 的二段机制当场坏掉**：两段的冷却合成一个键，"第一段不进 CD、第二段进 CD"（`tests/blink.ts` 钉着）不成立 —— 瞬影之后 8 秒里连标记都挂不上 |
| **B. 键 = `skillIds[0]`**（就是用户写的 `cd.<skillId>`） | `blink` 照旧对（两段的技能本来就不同），但 **HUD 读的是 `getStored(player, 'cd.' + row.id)`**（`web/src/main.ts:3137`，`row.id` = **术式 id**）⇒ **普通术式的读秒会一起消失**（所有格子都读 0），而**用户的目的（带序列那一格显示读秒）依然达不到** —— 那需要动 HUD，而 **UI 被用户冻结** |

⇒ 结论：**第 4 件的引擎侧落点是清楚的，但它和 HUD 是同一件事** —— 单独改键只会把
"现在能看见的读秒"换成"以后能看见的读秒"，而**任何一版都改不动那一格**（那在 UI 里）。
**建议**：等用户下 UI 那一道令时**一起做**（`cd.<skillId>` + HUD 读下一段的技能）；
要现在就做的话只需要一句话确认走 B（并接受"普通术式暂时不显示读秒"）。
