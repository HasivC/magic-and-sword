# 日志 51 · 两个「份数」类修饰动词：**多重释放** 与 **一分为 X**

日期：2026-09-21 ｜ 切片：修饰技能（日志 48 那一套原型 / 副本 / 执行器）的第二片

**一句话**：往一条序列的某个技能前面挂一个副本，就能让它**一次激活打出好几份** ——
「多重释放」打出后面 N 个**不同**的瞬发技能，「一分为 X」把**同一个技能**掰成 X 份；
份数各付各的能量和冷却（**份数不是免费的**），点数随份数变（汇率在 `content/balance.json`）。

⚠ 这一片**只做这两个动词**。「连锁」（弹给最近的敌人）没做 —— 它不是份数，是另一个机制。
⚠ **没有动编辑器 UI、没有动瞄准、没有动 CD 名牌**。

## 2. 两个动词怎么落地（编译期 / 运行期各做了什么）

### 编译期（`compileMods` → `CompiledMod`）

1. 原型表解析出 `kind`（`multi` / `split` 是这一片新加的两个）；
2. 读份数：**副本的 `params.count` 优先，原型兜底**，再夹到 `[2, params.max]`
   （上限**住在原型里** —— 玩家说的"N 上限 10 / X 上限默认 4"里那个"默认"就是这个意思）；
3. 夹过就**报一条 `CompileProblem`**（手改的存档 / 老分享码绕过校验器直接进世界，不能静默）；
4. 结果落在 `CompiledMod.count` 上 ⇒ **运行时不查原型表**（sim 里没有内容层，
   "运行时忘了传原型表"会静默地把一份修饰当成不存在）。

### 运行期（`startSequence` → `activateGroup`）

判据只有一条：**这一段编译产物的 `mods` 里有没有 `targetIndex === 0` 的 `multi` / `split`**。
有 → 不走"整段一条时间轴"，改走"一起打几份"；没有 → **和以前一模一样**（一个字节都没变）。

要打哪几份（`groupPlanOf`，和玩家那段规格一一对应）：

- **一分为 X**：把 `skillIds[0]` 排 **X** 遍；
- **多重释放**：从 `skillIds[0]` 起数 **N 个互不相同**的技能，只把**另外 N−1 个**接在后面；
- 两个都在 ⇒ 一共 **X + (N − 1)** 份（**相加**，不是相乘 —— 见 §6 待裁定项 1）。

怎么打出去（`activateGroup`）：

| 要做的事 | 为什么 |
| --- | --- |
| **每一份各起一个施法**（同一个 tick） | 阶段机是**一条线**，"同时"在它里面说不出来；N 个施法实例才是"一起打出去" |
| 每一份都用**同一个 `opts`** | **共用同一个意图**（定稿 §九）：一个朝向 / 落点 / 锁定目标，各自解释它 |
| 每一份的 `technique.id` = **段自己的键** | 冷却、HUD、`peekSequence` 认的都是段那一格；一份一个键 ⇒ **这一段永远不冷却** |
| 代价**先加起来判一次**（能量 + 血契） | **全有或全无**：不够就一份都不放，不给"三份里出来两份" |
| 每一份挂同一个 `activation` 记号 | "这一段什么时候算结束"一次激活只能发生一次：**只有最后一份**推进连段链 / 消费缓冲 |
| 第一份走完整道门，其余 `sameActivation` | 冷却 / `busy` / `locked` 问的是"**别人**占着"；同一次激活的份数不是别人。⚠ 资源和生死**一份都不跳** |
| 蓝耗**不需要专门写一行** | X 份就是 X 次激活，各付各的 —— "蓝耗按份数乘"是这条实现方式**自然**的结果 |

⚠ 两处**没做**（记在 §6）：`at > 0`（引擎只认"紧邻的第一个技能被修饰"，和触发器同一个限制，
校验器会给警告而不是静默）；跨段的份数。

## 3. 建议的点数汇率（⚠ **待玩家签字**）

| 旋钮 | 在哪 | 建议值 | 状态 |
| --- | --- | --- | --- |
| `modifierRates.extraCopyPerPoint` | `content/balance.json` | **2 点 / 每多一份** | ⚠ **待玩家签字** |
| `modifierRates.stackPenaltyPerPoint` | 同上 | **0**（不额外收） | ⚠ 待玩家裁定（见 §6.1） |

**理由（为什么是 2）**

- **参照系**：配平容差是 **2 点**，而"一个出厂技能的净值量级"≈ 2~4 点
  （`damagePerPoint` 27.6、`phaseSecondPerPoint` 0.863）⇒ **多一份 ≈ 半个技能**；
- **它必须被容差看得见**：给 1 点的话，"要不要多打一个"落进容差里，
  编辑器里永远绿灯（**永远绿灯等于没有灯**）；
- **两个动词共用一把尺**：多重释放买的（多打出 N−1 个不同的技能）和一分为 X 买的（多掰出 X−1 份）
  都是"同一次激活里多一份输出"，今天没有把它们分成两条轴的依据。

**收钱的口径**：**多出来的份数**（N−1 / X−1），记在**术式**的账上（`from: 'technique'`），
每个零件各记一笔（编辑器要按零件分组显示）。份数 1 = 没有这个修饰，
而账跟的是**引擎实际会打出的份数**（`modifierCountOf` 夹过之后的那个数）——
账和引擎必须是同一个数，否则"账上收 1 份、打出 2 份"会同时成立。

⚠ **它故意不在 `rates` 里**：`tools/calibrate.ts` 的拟合变量就是
`Object.keys(DEFAULT_RATES)` —— 往那张表里加一个键，标定输出**立刻变**，
而这一次的硬要求是"标定逐行不变（修饰不进战斗）"。所以它单开一栏 `modifierRates`，
形状仍然是**数据**（改它不用改代码）。校验器会在它缺失时警告
（缺了的话那份好处就是**白送**，而"白送"和"没计价"在账面上长得一样）。

## 6. 待裁定项（⚠ 这一片**自己定**的只有第 1 条，其余是**没写清的地方**，我没有自己定）

### 6.1 ⚠ **两者叠加怎么算** —— 我定了，**待玩家裁定**

同一个技能前面同时放「多重释放」（N）和「一分为 X」（X）时：

- **执行**：一分为 X 先把它掰成 **X 份**，多重释放再把**另外 N−1 个不同的**技能带上
  ⇒ 一次激活一共打出 **X + (N − 1)** 份；
- **点数**：按**实际打出的份数**收 ⇒ `(X + N − 2) × 汇率`。

**为什么是相加而不是相乘（N × X）**：第一个技能在"N 个**不同**技能"里**已经算过一份**了，
相乘会把同一个技能数两遍 —— 而"份数"和"几个不同的技能"是**两条轴**，
不是同一件事的两个乘数。例：N=2、X=3、技能是 [飞弹, 猎杀] ⇒ 3 份飞弹 + 1 份猎杀 = **4 份**
（相乘会说 6 份，而第 6 份是同一个飞弹被数了两次）。
`balance.json` 里留了一个 `stackPenaltyPerPoint`（今天 = 0）——
玩家要是说"两个凑一起该更贵"，改那个数就行，不用改代码。

### 6.2 ⚠ 「一分为 X」能不能放在**蓄力 / 持续**技能前面 —— **没有规定**

玩家只对「多重释放」说了"只作用于瞬发技能"（校验器也照这句拦），
对「一分为 X」**一个字都没说**。所以这一片**不拦它**（拦了就是自己定规矩），
原样记在这里。X 份蓄力技能 = X 条**同时蓄力**的时间轴，引擎不会崩，
但那是不是想要的，得玩家说。

### 6.3 ⚠ X 份 / N 份之间要不要**散开** —— 没有规定，而这一片**不敢动**

玩家明确说了"不要动瞄准"，所以今天几份**完全重合**（同一个意图 = 同一个落点）。
"份数要不要有展开角"是瞄准那一层的事，等那句话。

### 6.4 ⚠ `at > 0`（副本排在它修饰的技能**前面**但不在第一位）

引擎落地这件事的地方（`activateGroup`）今天只认 **`at: 0`**（"紧邻的第一个技能被修饰"），
和触发器 / 监测器**同一个限制**。写在别处**不生效**，所以校验器给一条
`MODIFIER_GROUP_AT_NOT_WIRED` **警告**（不静默，也不判死）。
⚠ 引擎为什么不做 `at > 0`：那要"先按顺序跑 `at` 之前那几个技能、
再把 `at` 起的那几个**一起**打出去"，也就是**一次激活里两条时间轴** —— 那是另一件事。
**这是待办，不是这一片漏了。**

### 6.5 ⚠ 多重释放的 N 个技能**跨不跨段**

今天只在**本段**里数（`at` 本来就是段内下标，`skills` 是段自己的技能表）。
"跨到下一段一起去"是一种可能的读法，但现有模型里没有它的落点 —— 记在这里。

### 6.6 ⚠ 武器侧术式上的份数修饰**不进账**

份数的钱记在**术式**账上，而"武器侧术式不算账"是现行规矩（`priceless`，日志 46 的欠账）
⇒ 一把武器上普攻挂了「多重释放」，今天账上看不见。这不是这一片引入的，
是那份欠账的延伸。

### 6.7 ⚠ HUD 预判与实际打出的份数**不是同一个集合**

`peekSequence` 问的是"**整段**能不能放"（整段所有技能的能量总和），
而份数实际打的是**子集** ⇒ 可能出现"界面说能量不够、按下去其实能放"（**保守**方向：
不会出现"界面说能放、按下去放不出来"）。要精确的话得让 HUD 也算一遍份数计划 ——
那要动 HUD，这一片没做。

### 6.8 ⚠ 份数修饰的代价规则（我按**现有先例**做的，没有别的读法）

多重释放打出的 N 个技能**各付各的能量和冷却**（`cd` 记在段那一格、取各份的最大值），
一分为 X 的 X 份**各付各的** —— 也就是"蓝耗按份数乘"。
这和触发器那句"触发出来的技能照常付自己的能量和冷却"是**同一条规矩**（`activate()` 是唯一的路），
所以我没有把它做成一个选项。**如果玩家要的是"一次激活只付一份"，那是一条要单独裁定的设计。**

### 6.9 ⚠ 不传原型表 = 一笔账都不记（调用方必须传）

`priceOptionsFor` 不传 `modifiers` 时，份数那笔账**一条都不记**（"白送"和"没计价"账面一样）。
今天三个调用方（`bridge.ts` / `validator` / 命令行）都传了，测试也钉住了症状。
"要不要在定价这一层也报一条警告"记在这里（今天没报，因为定价层没有"问题"这个出口）。
