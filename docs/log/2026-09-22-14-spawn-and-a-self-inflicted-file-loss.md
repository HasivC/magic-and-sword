- **触发**：承接（三）。七个载荷里只剩 `spawn` 没实现，
  它需要一个新内容层（实体预设）。做完它，"每个已实现的引擎机制都有内容"这条就齐了。
- **动了哪些文件**：见每一节末尾

## 一、`spawn`：先发现 schema 里**早就写好**了预设类型

动手前先查了一遍，差点犯错：我新建了一个 `schema/entity-schema.ts` 写 `EntityDef` ——
然后 typecheck 报「`EntityDef` 已经被 `skill-schema.ts` 导出了」。

原来 `skill-schema.ts` 第十一节**早就声明了** `EntityDef`（实体/武器/敌人共用），
字段和我要写的几乎一样，还多了两个我没想的：

| 字段 | 为什么好 |
|---|---|
| `hooks?: PipelineHook[]` | 实体**天生**带的管线钩子 —— "亡灵生物治疗反转"可以挂在实体上而不是状态上 |
| `baseZ?: number` | 视觉 z 基准（浮空单位） |

也就是说 `EntityDef` 一直是**零引用**的：声明在那儿、校验器认它、
`describe.ts` 会说「生成 entity.skeleton」，但没有任何代码读它 ——
因为 `spawn` 会 throw。

**这是同一个病的第四个变体**（前三个：`visibility`、`hasStatusTag`、`immuneTags`）：
**schema 比引擎走得快，而且没人告诉你**。

所以做法是删掉我新建的那份、用回既有的，只补三个字段：
- `faction` 加 `'caster'`（跟召唤者同阵营）
- `radius`（碰撞半径 —— 它不只是画面大小，目标选择/击退/命中判定都读它）
- `activeTechniques`（被召唤时就挂上的被动）

## 二、阵营：`'caster'` 是纪律 1 在内容层的兑现

预设里 `faction: 'caster'` 表示"跟召唤它的人同一阵营"。

写死 `'enemy'` 的话，敌人召唤出来的骷髅会**帮着玩家打** —— 写死 `'player'` 反过来。
测试里两个方向都断言了：玩家召的锁敌人、敌人召的锁玩家，**用的是同一份预设**。

和「魅惑」是同一件事的两面，两边都靠同一个 `isHostile` ——
`ai.ts` 顶上那条注释（"为了魅惑做对这件事，白送了召唤"）在这里兑现。

## 三、摆位置踩了两个坑

**坑一：不要用 sin/cos。** 纪律 4 禁掉了它们（跨 JS 引擎不保证逐位一致，会破坏重放）。
改用八个手写的单位方向向量轮取 —— 纯常量，零计算。

**坑二（测试抓出来的）：连续召唤会叠在一起。** 最初按 `i`（本次召唤内的序号）取方向，
于是**第二次召唤的第一个**又落在方向 0 上，和上一次那个完全重叠 ——
测试量出来 `0.00 米`。

修法：起点先数一下主人名下已有的同类召唤物，从下一个方向开始排。

## 四、定价：实现的同时把价格补上

⚠ 这是**特意**的：位移以前实现完了却忘了定价，于是"一个纯击退技能在账上是免费的"，
看起来像数值没调好，实际是效果没进账。做 `spawn` 的同一轮就把定价写了。

估值模型：一具召唤物的**血量池**就是它替你吃掉的伤害，
所以按 `hp / hpPerPoint` 算 —— **和"一个同血量的护盾"同一个价钱**。
这个锚是现成的（护盾 150 点 ≈ 10 点额度），不用另发明一套。
再加一笔 `summonBase` 表示"它在场上还会打人"（**粗估**，见欠账）。

### 配平逼出了一个设计决定

两具 60 血的永久骷髅在账上值 **18.4 点**，而这个技能能付出的代价上限
（能量 40 + 冷却 20 + 两段前摇）只有 **~10.5 点**。

当时的直觉是「把骷髅调脆」（改成 30 血）—— **那是错的**：
30 血的召唤物挨一下就没了，那不叫召唤，那叫放个烟花。

正确的做法是**减数量、保质量**：一具 60 血的骷髅，正好 +1.28 配平。
`count` 字段本身由单元测试覆盖（fires 两次 → 两具，且不重叠）。

## 五、引用检查扩成通用的（`checkRefs`）

`statusId` 和 `entityId` 是同一类东西：**按 id 引用别处的定义**，
引用不到时都是**运行期**才炸。所以它们必须是同一个检查。

`checkStatusRefs` 保留成薄封装（不破坏已有调用方），新代码用 `checkRefs`。
第一次没把实体预设算进"已知"，于是 `content/entities/` 里自己定义的东西
被误报成悬空 —— 和状态库那一轮踩的是同一个坑，**这次是第二次**。

## 七、我自己把 `tests/smoke.ts` 弄坏了，然后重写了它

**这一节是记录一次真实事故。**

我想批量改一个函数名，用了：

```powershell
(Get-Content tests\smoke.ts -Raw) -replace '...','...' | Set-Content tests\smoke.ts -Encoding utf8
```

PowerShell 5.1 的 `Get-Content` **不带 `-Encoding` 时按系统 ANSI（本机是 GBK）解码**。
于是 UTF-8 的中文被当成 GBK 读成乱码，再以 UTF-8 写回去。
GBK 是双字节编码，遇到非法字节对会**吃掉后面的字节** ——
被吃掉的那些正好是换行符，于是代码和注释粘在一起，语法都坏了。

**96 处不可恢复**。

好在**代码本身没坏**（坏的是中文注释和字符串字面量），
所以能靠"读出代码骨架 + 重写中文"复原。恢复步骤记下来备用：

```powershell
# 反向转换：把当前 UTF-8 内容按 GBK 写回，得到原始字节
$s = Get-Content -Raw -Encoding UTF8 tests\smoke.ts
[System.IO.File]::WriteAllText("out.ts", $s, [System.Text.Encoding]::GetEncoding(936))
```

这次只恢复了 ~95%（有 96 处丢了字节），所以最后是**照着代码骨架重写**的。

**教训**：这条纪律我早就写在日志里了（"用 Node 改 JSON，别做字符串手术"），
但当时只覆盖了 JSON。**现在它覆盖所有源文件**：
批量改文本一律用 Node 脚本（`.scratch/*.mjs`），
PowerShell 只用来跑命令、看输出。

顺带：重写的时候把 CRLF/编码都过了一遍，并给 `check-json.mjs` 加上了
`content/entities` —— 那个脚本这一轮又抓到一次 ASCII 引号写进 JSON 注释
（**连续第四次**，位置精确到第几行第几列）。

## 八、`npm run play` 会挂住，以及一个"查不出来"的诚实处理

收尾验证时 `npm run play` **挂满 120 秒的命令超时**。两个独立的毛病：

**（a）服务用 `stdio: 'inherit'` 起，把调用方也拖住了。**
子进程继承了调用方的控制台句柄；脚本自己 `detached` + `unref` 退出了，
但 PowerShell 一直等那个句柄关闭。改成 `stdio: 'ignore'` ——
服务的启动结果照样看得见（下面轮询 5 秒确认它能应答），
看不见的只是它的日志。3.5 秒返回。

**（b）`detached` 出去的服务活不过这条命令。**
在受管理的环境里，进程树会跟着命令一起被回收 ——
于是脚本打印"✓ 窗口应该已经开了"，而窗口里是白的。

我一开始加了个"开完窗口回头确认服务还在"的检查。**它不会触发**：
回收发生在命令**退出之后**，退出前 500ms 服务还是活的。
一个不会触发的检查比没有更糟 —— 它给人"检查过了"的假安心。

所以改成**直接说清楚**：如果服务是这条命令起的，就补一句
"它可能活不过命令退出，白屏的话单独开一个终端跑 `npm run serve`"。
**查不出来就别说查过了。**

（实际验证时是把服务作为常驻后台任务起的，那样窗口一直有得连。）
