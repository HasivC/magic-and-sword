## 一、搬家前后（结构）

```
搬家前                                 搬家后
──────────────────────────────────    ──────────────────────────────────
Technique.targeting        （必填）    ✗ 删掉
SequenceSegment.targeting  （可选）    ✗ 删掉
Skill.targeting            （没有）    ✓ 新增（可选；默认鼠标方向）
```

⚠ **运行时那几处一行都没改** —— 这是这次能保持"行为逐位不变"的**全部理由**：

`resolveAim` / 动作的默认目标（`runTechniqueRules` 的 `selfOnly`）/ AI 挑术式 /
接触判定（`markContactHit`）读的**都不是术式**，而是**一份编译产物**
（`CompiledTechnique.targeting`）。所以做法是：

> 编译时把那份瞄准**从技能身上取来**（`src/sim/compile.ts` 的 `targetingOfChain`），
> 放进编译产物 —— 后面所有读它的人看到的还是**同一份数据**，只是来源换了个地方。

```
技能（Skill.targeting）
   │  编译时取（targetingOfChain：链上第一个声明了瞄准的技能）
   ▼
CompiledTechnique.targeting  ──►  resolveAim / selfOnly / AI / markContactHit
                                （这四处**一个字都没改**）
```

### 取法的两条细则（都是被测试逼出来的，见 §五）

1. **段的瞄准**：取**这一段里**第一个带瞄准的技能（`targetingOfChain(seg.skills)`）。
2. **容器（挂了序列的术式）的瞄准**：先看自己的 `skills`，再**按顺序看每一段**的
   —— `targetingOfTechnique(tech, lookup)`。
   ⚠ 少了"看段"这一步的话，**只挂序列的术式**会得到一份空表，而
   **接触判定**（`markContactHit`）拿的正是容器的 `targeting.valid`：
   表现是"位移撞到人却永远算没碰到"，`tests/scenario.ts` 第 31 节当场红
   （**这就是它抓出来的**）。

## 三、客户端：意图永远是"鼠标位置那一个点"

⚠ 定稿 §九：**意图 = 玩家这一次激活给出的那一个指向**；一次输入只有一个指向，
而"这一次"能给的只有一样东西：**鼠标位置那一个点**（方向、落点都从它推出来）。

**改之前**（客户端在替技能做判断 ✗）：

```ts
const intent: AimIntent = tech.targeting.mode === 'areapoint'
  ? { kind: 'point', ...(pointerWorldPoint() ?? player.pos) }
  : { kind: 'direction', dir }
```

**改之后**（一个收集函数，`pressCast` 和 `pressWeapon` 共用）：

```ts
function aimIntent(): AimIntent {
  const dir = aimDirection()
  player.facing = dir                      // 画面的事：人转向鼠标
  const point = pointerWorldPoint() ?? player.pos
  return { kind: 'point', x: point.x, y: point.y, dir }
}
```

### 为什么行为不变（一个字都没变）

⚠ 这是这一片**最容易出错**的地方，所以写清楚：

1. **`dir` 是原来那一份**：还是 `aimDirection()`（`web/src/aim.ts` 的纯函数，
   算不出来时沿用它上一次的方向 = 角色当前朝向）。所以"朝哪打"没有任何变化。
2. **`kind: 'point'` 多带了一个方向**（`AimIntent` 的 `point` 变体加了可选 `dir`）：
   · `areapoint` 技能读 `x` / `y`（落点）—— 和改之前**同一份** `pointerWorldPoint()`；
   · 其余模式读 `dir`（朝向）—— 和改之前**同一份** `aimDirection()`。
   两种技能拿到的都是原来那一份，只是**从同一个意图里各取一半**。
3. **`dirOf` 多认了 `point.dir`**（`src/sim/targeting.ts`）：
   `direction` → 用 `dir`；`point` 且有 `dir` → 用 `dir`；否则 → 施法者当前朝向。
   ⚠ 最后那条兜底**一个字都不能改**：AI 在调 `pressSequence` 之前刚把 `e.facing`
   设成"朝着目标"，老行为正是拿它当朝向。
4. ⚠ **为什么不让引擎从那个点反推方向**：反推在两种情况下会得到**假方向** ——
   `areapoint` 的落点可能是"朝向前方 range 米"（不是鼠标位置），
   而"方向算不出来"时那个点会退化成角色自己的位置（反推得到 `(1,0)` 而不是
   "沿用它上一次的方向"）。所以方向和落点是**同一份意图的两半**，一起给。

⚠ `areapoint` 的**钳制/朝向**逻辑本来就从那个点算（`normalize2({x: intent.x - here.x, …})`），
所以那一条路连"读 `dir`"都不需要 —— 它还是原来那几行。

## 四、校验器：两条防回潮 + 技能那一侧的形状检查

| 检查 | 报什么 | 为什么 |
| --- | --- | --- |
| 术式里写 `targeting` | **`TARGETING_MOVED_TO_SKILL`**（错误） | 写了**不会生效**（引擎读的是编译产物里从技能取来的那份），而且**一处都不报错** —— 这个项目里最贵的一类坑。更坏的是这是**回潮**：老内容里本来就有它，照抄一份旧文件就会带回来 |
| 序列段里写 `targeting` | **`TARGETING_MOVED_TO_SKILL`**（错误，`path` 指到 `sequences[j].targeting`） | 同上；而且日志 46 时**每一段都还写着它**，照抄一段就会带回来 |
| 技能上的 `targeting` 形状 | `BAD_TARGETING`（不是对象）/ `BAD_ENUM`（mode 非法）/ `EMPTY_VALID`（`valid` 空）/ `AREAPOINT_NO_RANGE`（`areapoint` 没写 range） | 这四条**从 `validateTechnique` 搬到了 `checkTargeting`（技能那一侧）**，判据一字未变 —— 这次是搬家，不是重新设计瞄准 |

⚠ **不写 `targeting` 不报错也不警告**：默认是"鼠标方向"是玩家定的规矩。
要求每个技能都写的话，就是"对着唯一正确的写法报警告"—— 这个坑这项目踩过好几次
（见 `validateSkill` 里那段注释）。所以"32 份技能显式写"是**内容纪律**，不是校验器规矩。

⚠ 顺带：`src/validator/index.ts` 里那句 `selfOnly`（"只对自己有效吗"）
**必须和引擎用同一份数据**。它以前读 `tech.targeting`，现在**顺着 `tech.skills` 查技能表**
取同一份 —— 两边读法不一致的话，报出来的错误本身就是错的。

## 七、我不确定 / 需要裁定的地方（**照实列出来**）

1. **一条链上两个技能的瞄准不一样时，这次施法听谁的** ——
   ⚠ **今天的内容里不会出现**（迁移时逐条搬的，一条链上的技能瞄准都一样），
   但规矩上没定。编译层现在的做法是**取链上第一个声明了瞄准的技能**
   （容器 / 段都是），理由是 `cast.facing` 在施法瞬间只解算**一次**。
   ⇒ 真出现那种内容时，正确的做法很可能是**按技能分别解析**
   （`runTechniqueRules` 那一刻用"这条规则所属技能"的瞄准），
   那是一次**会改行为**的改动，不该混在"搬家"里。
2. **`playerIdle` / 容器的 `range` 到底表示什么** ——
   `tech.iron-sword-basic` 的容器写 `range: 3`、`tech.longsword-basic` 写 `5`，
   而两段的 `tech.ws-slash` 都是 `4`。容器不跑时间轴、也不跑规则，
   所以那个数**今天没有任何读者**（AI 不拿武器术式、玩家走 `pressSequence`）。
   ⚠ 我按"段生效的那一份（4）"定了 `skill.ws-slash`，
   但**如果那个 3 / 5 本来是想表达"这把武器的普攻射程"**，那它得另有一处落点 ——
   这件事这一片没查出来。
3. **`skill.slow-field` 的 `self` + `valid: [enemy]` 和 `skill.infinity` 同型** ——
   它是**原样照搬**（术式 `tech.slow-field` 就是这么写的），不是这次新造的。
   ⚠ 但这个组合读起来矛盾（"对自己施法、只对敌人有效"），
   它靠的是规则里那条 `onEnter` 的 `valid` 覆盖。要不要收紧成一条规矩，
   需要玩家/作者裁定。
4. **18 份"出厂内容里没有术式引用"的技能，那份对照表是我按机制判的** ——
   其中 **2 份第一版判错、被测试抓出来**（`charge-dash` / `holy-light`，见 §二 C）。
   ⇒ 剩下那 16 份我**没有测试能证明**它们判对了（它们没有消费者）。
   ⚠ 建议：等哪份术式第一次引用它们时，回来核一遍那张表。
5. **老分享码的拒绝粒度** —— 玩家裁定"TS1 / TS2 老码不用兼容"。
   我实现成：**只要前缀不是 `TS2.`** 就拒绝（`TS1.` 给"老格式"那句人话，
   `TS3.` 以上给"这是第 N 代"）。⚠ 我**没有**去解析老码的内容
   （老码里那份术式就算能解出来也会因为带 `targeting` 撞上防回潮那条规则）——
   如果将来还想认某一代老码，得先想清"那份术式上的 `targeting` 怎么剥"。
