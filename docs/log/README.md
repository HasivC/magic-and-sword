# 修改日志

**规则：每次改完东西，在这里加一个文件。** 不用长，但下面几项要有。

## 命名

```
YYYY-MM-DD-NN-短横线小写标题.md
           ↑ 同一天的第几次，从 01 开始
```

例：`2026-09-19-03-ledger-sign-and-interrupt-levels.md`

⚠ **文件名里的日期 = 创建它的那一天**（**新写的按机器时钟**；**已存在的按各自创建日**），**不要照抄上一条的日期** ✗。
（踩过：新日志照着上一条的日期写，于是文件名说的是过去、内容说的是现在 ——
按日期找东西就会找错。）日期拿不准就去看系统时间，**别猜**。
同理，正文里"玩家 X 年 X 月 X 日定的"这种**归属日期**也别抄：
写**你确认的那一天**，或者干脆只写"玩家定"、不写日期。

## 每篇写什么

```markdown
# 标题（做了什么）

- **日期**：2026-09-19
- **触发**：谁提的、为什么要改（玩家报的 bug / 我自己发现的 / 设计推进）
- **动了哪些文件**

## 改了什么
（按文件或按主题，几行就够）

## 为什么
（这一项最重要。**只写"改了什么"的日志等于没写** ——
 半年后你会需要知道"为什么当时是这么定的"）

## 验证
（跑了什么、结果如何。至少要有 `npm test` 的结果）

## 欠账
（这次没做但该做的，以及为什么先不做）
```

## 什么时候不该写

- 只改错别字、只调格式 → 不用写
- 一次改动跨了好几天 → 按"能一次说清的最小单位"拆，不按天拆

## 为什么不写进 commit message

因为这里面有一半是**决策**而不是**改动**：
"为什么不用引擎"、"为什么把整本账翻回来"这种，commit message 放不下，
而它们恰恰是几个月后最需要的东西。
