# 局域网联机可行性（换成桌面壳之后）

- **日期**：2026-09-21
- **为什么有这份文件**：玩家

  > 之所以最开始用浏览器跑，是想做局域网联机，目前更改架构还能做到这样吗？
  > 只讨论可行性，不实行。

  所以这里论证的不是"怎么做得漂亮"，而是**"改成 .exe 会不会把联机这条路的门关上"**。

## 结论：**不仅没关上，反而比浏览器更容易**

一句话理由：**浏览器恰好是最不适合做局域网的那一层。**

| 浏览器做不到的 | .exe（Electron / Tauri）能不能做 |
| --- | --- |
| 开 UDP / 监听端口（网页里没有 socket API） | 能（Node 的 `dgram`/`net`，Rust 的 `std::net`/tokio） |
| 局域网自动发现（mDNS / 广播） | 能（有成熟的库） |
| 不装浏览器插件就让别人连进来 | 能（房主直接监听） |
| WebRTC 点对点 | 也能，但**需要信令服务器**，而且 ICE/STUN 在纯局域网里是多余的复杂度 |

⚠ 而且这个项目的模拟核**从第一天就是按"以后要联机"建的**：headless、固定 60Hz、
确定性、纯净性纪律。那不是巧合 —— 那是**联机的前提**，现在只是还没接上那层网。

## 一、已经站在起跑线上的五件事（都有代码）

| 已经有了 | 为什么它是联机的前提 |
| --- | --- |
| `core-sim` headless + **固定 60Hz**（`world.dt` 是唯一时间源，`world.tick` 是唯一进度） | 联机同步的是 tick，不是"墙上的钟" |
| **纯净性纪律**（`tests/purity.ts`）：`src/sim/**` 禁 `Date` / `Math.random` / `performance` / `window` | 时间源和随机源必须是**模拟状态**，不能是环境 |
| **Math 白名单**：只许 `sqrt / abs / floor / ceil / round / min / max / imul / sign / trunc`；**禁** `sin/cos/tan/atan2/pow/hypot/exp/log…` | 允许的那些是 **IEEE 精确**的；禁掉的那些正是"不同引擎/平台结果可能不同"的。**跨机器逐字节一致的关键就在这条** |
| `snapshot()` + 同种子逐字节一致的测试（`battle duel` 12 秒是金标准） | 联机要的"不同步检测"= 比对 snapshot 哈希 —— **工具已经有了** |
| 内容加载顺序确定（`collectJsonFiles` 用 `readdirSync(...).sort()`） | 两台机器上"同一个世界"的另一个前提 |

## 二、两种联机做法，这套架构两种都撑得住

| | **锁步**（每端各自模拟，只交换输入） | **主机权威**（房主模拟，其他人收快照） |
| --- | --- | --- |
| 带宽 | 极小（每 tick 几十字节 × 人数） | 中（每 tick 一份快照） |
| 需要的引擎能力 | **已经有了**（确定性 + 输入） | 需要"快照序列化 + 客户端插值"（**没有**） |
| 不同步怎么办 | 哈希比对 + 重跑/回滚 | 不存在（只有一个真相） |
| 重放 | **白送**（输入流就是重放） | 要额外存快照 |
| 适合 | 2~4 人局域网（延迟 <5ms） | 更多人 / 以后想上公网 |

**局域网推荐锁步**：延迟小到可以用"**输入延迟 3~6 tick**"顶掉，
于是**不需要插值** —— 而插值是这一块最费工的（也是画面抖动的来源）。
代价是"**任何一处不确定都会让两边漂开**"；上表那五条已经把不确定性关掉了。

## 三、真正要写的（不是架构，是一层"网" + 五件事）

1. **传输层**：桌面壳里开 UDP（或 TCP）—— Electron 用 Node，Tauri 用 Rust
2. **握手**：算一个**内容哈希**，不一样直接拒绝加入。
   ⚠ 这条**必须做**：不然两边跑的是两个游戏（一个改了技能、一个没改），而表现是"莫名不同步"
3. **输入包**：`{tick, 键鼠意图}`。客户端现在的 `applyInput()` 只做一件事（把键鼠写进实体），
   把它换成"从本地或从网来"就行 —— **模拟核一行不用改**
4. **哈希比对**：每 N tick 交换 snapshot 哈希；不一致就**停下来报出来**（别静默继续）
5. **两个"本地会话"概念要分家**（这是设计，不是技术）：
   - 现在校验器**只允许一个 `controlledBy: 'human'`**（`src/scenario.ts`："一个键盘只能驱动一个"）→ 联机要放宽
   - `Tab` 打开编辑器会**暂停整个世界**；`R` 重开关 / `N` 新的一局 / 血契跨关累积 ——
     联机里这些都得变成"**房主说了算**"

## 四、和桌面壳选哪条路有关系吗

| | Electron | Tauri |
| --- | --- | --- |
| 写网络代码的语言 | **JS/TS**（和游戏同一套）✓ | **Rust** ✗（多一门语言，网络栈更稳） |
| 局域网发现（mDNS/广播） | 有 npm 包 ✓ | Rust 生态更成熟 ✓ |
| 浏览器玩家也能加入吗 | 能：主进程开一个 WebSocket 服务，浏览器端连它 ✓（⚠ 页面在 `app://` 安全上下文下 `ws://` 会被拦，要走 `http://` 或自签 `wss://`） | 同样能 ✓ |

**结论：两条都能做，而且联机的架构和壳无关** —— 这个选择不用现在定。
Electron 写起来快（同语言），Tauri 的网络侧更稳。

## 五、要提前定的设计问题（真做的时候由玩家定）

1. **锁步还是主机权威**（第二节；局域网我建议锁步）
2. **暂停权**：房主能暂停 / 谁都pause不了 / 投票
3. **不同步时的表现**：弹一句"你们跑偏了"然后重开这一局（诚实，但打断）？
   还是静默以房主为准（不打断，但要能解释）
4. **PvE 还是 PvP**：PvE 的话，两个人**共用一个血契池**还是各攒各的？

## 五之二、预留：具体插在哪几处（2026-09-21 定）

玩家 2026-09-21 定的：**联机只预留方案和框架，现在先做 .exe。**
所以这里把"将来要动的地方"钉下来 —— 但**不写占位代码**：

> ⚠ 这个项目自己把"声明了但没人用的东西"列为**最危险的一类**
> （见 [`framework-audit.md`](framework-audit.md) 的"发现一：惰性字段"）。
> 所以"预留"= **保持接缝干净 + 把插入点写下来**，不是塞一堆 `net/` 空壳进去。

| 将来要动的 | 在哪 | 现在是什么状态 |
| --- | --- | --- |
| **输入来源**（本地键鼠 → 也可以来自网络） | `web/src/main.ts` 的 `applyInput()` | 它只做一件事：把键鼠写进实体。联机时换成"从本地或从网拿一份意图"就行 —— **模拟核一行不用改** |
| **谁是权威** | 现在每个客户端各自 `stepWorld()` | 锁步时不动它（每端都模拟）；主机权威时把 `stepWorld` 挪进壳的主进程或 Web Worker |
| **内容哈希握手** | 加载完内容之后算一次 | **要加**（拒绝两边内容不同的玩家；不然表现是"莫名不同步"） |
| **哈希比对 / 不同步检测** | `snapshot()` 已经有了 | 只差"每 N tick 交换一次哈希" |
| **"只有一个人类"** | `src/scenario.ts` 的校验（`controlledBy: 'human'` 只许一个） | 联机时要放宽；客户端里 `player` 这个单例也要变成"我这一个" |
| **本地会话概念** | `paused`（`Tab` 暂停）、`restart()`（`R`/`N`）、血契跨关累积 | 联机时都得变成"房主说了算" |
| **传输层** | **壳的主进程**（`desktop/main.js` 这一侧） | 现在什么都不做；将来 UDP/TCP 开在这里（Electron 是 Node，Tauri 是 Rust） |

⚠ 两条**已经在守**的纪律（联机的前提，别让它们被破坏）：

1. `src/sim/**` 里不许出现 `Date` / `Math.random` / `performance` —— `tests/purity.ts` 盯着
2. `src/sim/**` 里的数学只用 IEEE 精确的那些（白名单见上）——
   写一句 `Math.hypot` 会让联机在不同机器上漂开，而 `tests/purity.ts` 会**当场抓到你**

## 六、风险清单（诚实版）

- **跨机器一致靠纪律守，不是一次性保证**：以后谁在 `src/sim` 里写一句 `Math.hypot`，
  `tests/purity.ts` 会红 ✓（这条自动）。但"**新增了状态却忘了进 `snapshot()`**"那种漏法
  只能靠联机时的哈希比对暴露 —— 所以要补一条**单机测试替代不了**的测试：
  **两个进程互相喂输入、跑 1000 tick、快照逐字节一致**（现在还没有；`battle` 是单机的同类）
- **输入延迟的手感要调**（3~6 tick 是起点，局域网里应该感觉不到）
- **大厅 / 发现 / 进房那一套 UI** 是**编辑器之外的另一块 UI** ——
  和玩家正在设计的编辑器 UI 一样，属于"要设计"的活，不是"要实现"的活
- ⚠ 浏览器那条路**不是废的**：桌面壳当房主、浏览器当客户端（走 WebSocket）是可行的混合玩法，
  但**浏览器不能当房主**（监听端口这件事它做不到）

## 联机路线（用户 2026-09-30 定）

- **先乙，再丙。**
  **乙 = 主机权威**：客户端**直接发输入**、主机**广播状态**、客户端**插值** —— **不做预测**。
  代价就是**一个来回的延迟**（局域网上约 **5ms**，可以先这么走）。
  **丙 = 在乙之上加本地预测** + 收到主机状态后**修正 / 回滚**；⚠ 工程大，需要一套新的
  **「快照 / 回滚」机制**。
- ⚠ 两件必须写清楚的：① **这是方向、尚未实现**（不是已经落地的实现）；
  ② **无论哪条路，「能重算」都是前提** —— 固定 60Hz、无随机、纯逻辑（就是上面那几条纪律，
  它们已经在了）；但**不要求跨机器浮点一致** ✗（那是**锁步**才要的）。
- ⚠ 这一条是**用户与助手讨论后**定的方向（2026-09-30），**不是已落地的实现**。
