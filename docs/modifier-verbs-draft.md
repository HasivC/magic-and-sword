> **它回答什么**：玩家问的那句 ——
> 「修饰技能应该有很多，都是机制类的，**要不要先讨论好所有可能加入的修饰技能**？」
>
> **答案**：**不必**讨论全部修饰技能（那是**内容** ✓ 会很多 ✓ 以后慢慢出 ✓）。
> **必须现在定的是「修饰技能能对被包裹的技能做哪些种类的事」这张动词表** ✓ ——
> 只要动词表**数据驱动、可以加动词**，以后加新修饰技能就只是**加内容** ✓；
> 否则每加一种都要动引擎 ✗。

  摊成一张**动词**表。
- **⚠ 动词 ≠ 零件**：「触发器」「多重释放」是**零件**（内容，会越来越多）；
  本文列的是**动词**（机制形状，要少而稳）。一个新零件 = 挑一个动词 + 填它的参数。
- **⚠ 只作灵感**：修辞上参考了 Noita 那类"法术修饰"，但**名字一个都没照搬**，机制按本项目的措辞走。

## 一、先读这四句（不然这张表会被用错）

1. **动词是"对一个技能能做的一件事"，不是"一个修饰技能"。**
   一个修饰技能 = 一个动词 + 一组参数（可以再加一层条件）。
2. **一条动词一节，第 5 条只写"今天能不能做"** ——
   ⚠ 这一列**必须诚实**：写"缺机制"比含糊过去强，含糊的代价是以后有人以为它已经能用了。
3. **⚠ 这张表不负责"分类"**（玩家明说了不必给修饰技能分类 ✗）。
   第 2 节那张总览表只是**交叉索引**，用途只有一个：**看有没有漏**。
4. **⚠ 表里的英文 id 是"建议"**，不是已定字段名 —— 定字段名是实现那一轮的事。

## 三、逐条动词

每节六行：**做什么 / 参数 / 引擎要支持什么 / 今天 / 边界 / 备注**。
⚠ 参数表里的"类型"沿用现有 schema 的词（`number` / `enum` / `condition` / `event` / `boolean` / `ValueSpec`）。

### 1. 条件触发 `trigger.on-event`

- **做什么**：盯着**一个时机**；那个时机一到，就把它后面那个技能放出来。
- **参数**

  | 参数 | 类型 | 默认 | 范围 | 可调 |
  | --- | --- | --- | --- | --- |
  | `when` | `event` | 原型自定 | **必须是 `TriggerEvent` 里已有的值** | ✓ |
  | `condition` | `condition` | `{}`（空 = 不看） | 技能里那**同一套**条件 | ✓ |
  | `crossing` | `boolean` | `false` | — | ✓ |
  | `origin` | `enum` | `aim` | `caster` / `aim` / `prevHitPoint` / `prevEndPoint` | ✓ |

- **引擎要支持什么**：**在一个时机点上问一遍修饰副本**。
  今天的事实：`trigger.ts` 的 `WIRED_TRIGGER_EVENTS` **只接了三个时机** ——
  `onLowHp` / `onTick` / `onCast`；其余（`onHit` / `onMiss` / `onExpire` / `onRemoved` /
  `onStatusApplied` …）**写上去不报错也不生效**（校验器给 `MODIFIER_TRIGGER_NOT_WIRED` 警告）。
  ⚠ 这不是"参数表缺一格"，是**调用点缺**：得有一个地方知道"这一刻该问谁"。
- **今天能不能做**：**半有** —— 骨架通了（触发 → 激活后面那个技能 → 代价照付），
  **时机清单只兑现了三个**。
- **边界**：技能**自己**的规则（前摇里排的 `phaseEnter` / `onHit` 动作）**不是**修饰技能 ——
  那是技能的时间轴，属于技能本身 ✓。修饰只能**加一层"什么时候放"**。
- **备注**：⚠ `origin: 'aim'` 在触发这条路上没有玩家意图，今天退化成"最近的敌人那个方向"
  （见 §6 待裁定 2）。

### 2. 条件监测 `monitor.watch`

- **做什么**：一直盯着一个条件（血量 / 层数 / 距离 / 目标数）；它**成立的那一刻**放出后面那个技能。
- **参数**：与 §1 **同一张表**（`when` 默认取 `onTick`、`condition` 必填、`crossing` 默认 `true`）。

  | 参数 | 类型 | 默认 | 范围 | 可调 |
  | --- | --- | --- | --- | --- |
  | `when` | `event` | `onTick` | 同上 | ✓ |
  | `condition` | `condition` | 必填 | 技能里那同一套 | ✓ |
  | `crossing` | `boolean` | `true` | — | ✓ |
  | `origin` | `enum` | `caster` | 四选一 | ✓ |

- **引擎要支持什么**：**同一个执行器 + 每 tick 被问一次**（`world.ts` 第 6 步）+ **边沿检测**
  （`mod-state.ts` 的 `markFired`）。**今天全都在** ✓
- **今天能不能做**：**能** ✓（出厂零件「命悬监测」就是它）。
- **边界**：⚠ "每 tick 看条件"**不是**"自己定时"——它跟着 tick 走，不引入新的时钟。
- **备注**：⚠ **边沿检测的已知代价**：触发过之后**不会自己复位**
  （条件离开再回来也不重置），所以"残血期间反复挨打"只放一次盾。
  想要"每隔 N 秒也能再来一次"的话，那是一条**新参数**（`everySeconds`），记进 §6 待裁定 3。

### 3. 常驻包装 `wrap.persistent`

- **做什么**：把这一个技能（以及包装自己）从"按键激活"里拿出来，**挂上就一直在**。
- **参数**

  | 参数 | 类型 | 默认 | 范围 | 可调 |
  | --- | --- | --- | --- | --- |
  | `effect` | `enum` | `persistent` | 今天只有这一个取值 | ✓ |

- **引擎要支持什么**：**编译期把这一段判成常驻**（`school.ts` 的 `hasConstantWrapper`：
  判据是 **`at === 0` 的那个副本是不是 `wrap`**）+ 常驻术式随 `activeTechniques` 走。
  **两样今天都在** ✓
- **今天能不能做**：**能** ✓（出厂零件「常驻包装」就是它）。
- **边界**：⚠ 它**不改数值、也不送免费** —— "常驻 ≠ 免费"落在
  **每次触发照付自己的能量和冷却**上（`fireModifier` 里那一句 `activate()`
  就是唯一的门）。所以"少付一点"**不是这条动词**，见 §4 的"成本类"。
- **备注**：⚠ 只有 `at: 0` 才是"包住这一段的开头"；
  一个 `at: 1` 的 wrap 不把整段判成常驻（`hasConstantWrapper` 钉着这一条）。

### 4. 多重释放 `multi.fire`

- **做什么**：让它后面那**一个**技能**同时打出 N 份**。
- **参数**

  | 参数 | 类型 | 默认 | 范围 | 可调 |
  | --- | --- | --- | --- | --- |
  | `count` | `number` | `2` | 2 – 10（整数） | ✓ |
  | `spread` | `number`（度） | `0` | 待定 | ✓ |
  | `costScale` | `number`（倍率） | `1` | 待定 | ⚠ 给"能量也 ×N"留的位置，**不是**已定 |

- **引擎要支持什么**：⚠ **缺机制** —— 今天做不到，缺的是三样**形状上的**东西：
  1. **一次放 N 个**：`cast.ts` 的激活路径是"一次一个技能"，
     `pipeline.ts` 里那个 `count` 数的是**载荷的发射数量**（`spec.count`），
     **不是"这个技能放几遍"** —— 两者同名不同物，别混 ✗；
  2. **N 份共用一个意图**（§八原话）：意图今天是一个对象，
     "分发给 N 份"这件事没有地方表达；
  3. **点数随 N**：修饰技能的点数怎么算**玩家还没给规则**，
     而**参数一旦可变就必须进账**（不能像今天这样"没 points 字段"）。
  ⚠ **"不能放在蓄力/持续技能前面"** 这一条同时要**校验器**出力 —— 那是形态规则，不是运行时判据。
- **今天能不能做**：**不能**。缺"一次放出 N 个"、缺"共享意图"、缺"点数随 N 的算法"。
- **边界**：⚠ **"打出 3 支箭"和"把这个技能放 3 遍"是两件事**。
  单纯"发射数量"是**载体字段**（`spec.count`）⇒ 那是**技能修正 / 技能本身**的事；
  只有"**把整个技能多放一遍**（连前摇后摇一起）"才是修饰动词。
- **备注**：⚠ 这是**唯一一条同时动"次数 + 点数账"**的动词，所以它在 §5 里被判为**现在必须有**。

### 5. 连锁释放 `chain.bounce`

- **做什么**：命中之后，把这个技能**再弹给离命中点最近的**那个敌人。
- **参数**

  | 参数 | 类型 | 默认 | 范围 | 可调 |
  | --- | --- | --- | --- | --- |
  | `bounces` | `number` | `1` | 待定（上限要定，否则一层弹到死） | ✓ |
  | `radius` | `number` | 待定 | 米 | ✓ |
  | `falloff` | `ValueSpec` | 待定 | — | ✓ |
  | `sameTargetTwice` | `boolean` | `false` | — | ✓ |

- **引擎要支持什么**：⚠ **缺机制** —— 两样没有：
  1. **弹射 / 选下一个目标**：`pipeline.ts` 的嵌套命中确实带 `depth`（反伤、连锁都走它，
     注释里就写着"连锁"），但**没有任何字段说"弹到哪、弹几次"**；
     选"最近的敌人"今天只有 `world.ts` 的 `findAlly`（那是**同类**），
     找**最近的敌人**没有那一个函数；
  2. **一次命中触发一条派生规则**：`TriggerEvent` 里有 `onHit`，
     但**没接线**（§1）；而且触发路上缺"**这一次命中是谁打的 / 打在谁身上**"的上下文
     ⇒ 弹射的起点读不到。
- **今天能不能做**：**不能**。`trigger.ts` 文件头自己写着"**没做**：多重释放 / 连锁"。
- **边界**：⚠ **不是**"命中后多打一次伤害"（那是载荷叠一次 = 技能修正）；
  连锁动的是**位置 + 目标选择**（"弹给**谁**"），所以它是修饰。
- **备注**：⚠ **上限必须与"depth"同一条规矩**，否则自反馈会炸（`pipeline.ts` 的 `depth` 是唯一防线）。

### 6. 延迟释放 `delay.release`

- **做什么**：把后面那个技能**压后**一段时间再放（或压到"某个时机之后"再放）。
- **参数**

  | 参数 | 类型 | 默认 | 范围 | 可调 |
  | --- | --- | --- | --- | --- |
  | `delaySeconds` | `number` | `0` | 待定 | ✓ |
  | `origin` | `enum` | `caster` | 四选一（同 §1） | ✓ |
  | `interruptible` | `boolean` | 待定 | — | ✓ |

- **引擎要支持什么**：⚠ **缺机制** —— 缺一个**延迟调度**：
  今天修饰层状态里只有"已触发过"和"上一个点"（`mod-state.ts`），
  **没有计时器**；`onTick` 只能表达"现在成不成立"，不能表达"再过 1.5 秒".
  ⚠ 这条**不需要新的时钟**（`world.tick` 就够），缺的是**在修饰副本上存一个到期时刻**。
- **今天能不能做**：**不能**（但**代价小**：加一个字段 + 一条每 tick 的判定，不动任何现有形状）。
- **边界**：⚠ "**技能自己的前摇**"是技能的阶段时长（技能修正能改它）；
  延迟释放动的是"**这个技能什么时候被放出来**"，是**释放时机**，不是前摇。两件事别并成一件。

### 7. 载体置换 `delivery.swap`

- **做什么**：换掉这个技能"**飞出去的那个东西**"的形状 —— 箭变成线、球变成环。
- **参数**

  | 参数 | 类型 | 默认 | 范围 | 可调 |
  | --- | --- | --- | --- | --- |
  | `toKind` | `enum` | 无（必填） | `DeliveryKind` 里已有的那八个 | ✓ |
  | `keepVfx` | `boolean` | `true` | — | ✓ |

- **引擎要支持什么**：**改 `DeliverySpec.kind`，其余字段从原技能继承**。
  ⚠ 今天没有任何一条修饰路径会去改 `delivery`（`compileMods` 只读
  `when` / `condition` / `crossing` / `origin`）⇒ **机制在，入口不在**（加一条读参数的支路）。
- **今天能不能做**：**算"能"** —— 数据结构支持，缺的只是把参数读进来那一小段。
- **边界**：⚠ **改 kind = 修饰 ✓；改半径 / 张角 / 长度 / 速度 = 几何 ⇒ 技能修正 ✗**。
  所以这条动词的名字里带 `swap`（**置换**），**不带 `tune`（调）** ——
  一旦它开始接受"半径乘 1.2"，它就把整个技能修正系统吞掉了（见 §4）。

### 8. 施放副产品 `on-cast.byproduct`

- **做什么**：这个技能**被放出来的那一刻**，在指定位置顺带放出**另一个**技能。
- **参数**

  | 参数 | 类型 | 默认 | 范围 | 可调 |
  | --- | --- | --- | --- | --- |
  | `skill` | 技能引用 | 无（必填） | 技能库里的技能 | ✓ |
  | `origin` | `enum` | `caster` | 四选一（同 §1） | ✓ |
  | `condition` | `condition` | `{}` | 技能里那同一套 | ✓ |

- **引擎要支持什么**：**它今天就能用现成的两样拼出来** ——
  `when: 'onCast'`（已接线）+ `origin`（已接线）+ 指定技能（`fireModifier` 已经在
  `activate()` 那个技能了）。**没有新机制** ✓
- **今天能不能做**：**能** ✓（只需一份新内容 `content/modifiers/*.json`）。
- **边界**：⚠ 别和 §1 混：**触发器的 `when` 是"被触发之后"**（§八原话），
  而这条是"**被放出来的那一刻**"。同一张参数表、不同的默认时机。
- **备注**：它是**第一个证明"加动词只加内容"的样本** —— 今天不用改引擎就能有它。

### 9. 存活改写 `delivery.survive`

- **做什么**：让飞出去的那个东西**多活一会儿 / 飞得快一点 / 能穿人**。
- **参数**：⚠ **这一节故意留空** —— 它的参数就是 `DeliverySpec` 里那几个字段
  （`lifetime` / `speed` / `pierce` / `homing`），
  而**"改那些字段"已经被判给技能修正了**（见 §4）。
  本文把它列出来，是为了让玩家**可以推翻这条界线**（§6 待裁定 4）。
- **引擎要支持什么**：数据字段全在；**入口不在**（同 §7）。
- **今天能不能做**：**数据上能，判据上不该** —— 它是本文标的**边界案例**。
- **边界**：⚠ **这条是"看起来像修饰、其实该由技能修正表达"的头号嫌疑**。
  若玩家把它收进动词表，动词表就开始吞数值 / 几何（§4 那个后果）。
- **备注**：⚠ 一个**真可能该算修饰**的例外：**"命中后不消失、继续飞"** ——
  它改的是**命中之后的行为**（时机），不是飞得多快（数值）。

### 10. 命中回响 `on-hit.echo`

- **做什么**：它后面那个技能**打中了**，就再放一次（或放出另一个技能）。
- **参数**

  | 参数 | 类型 | 默认 | 范围 | 可调 |
  | --- | --- | --- | --- | --- |
  | `condition` | `condition` | `{}` | 技能里那同一套（可写 `isCrit` / `hitKindIs`） | ✓ |
  | `origin` | `enum` | `prevHitPoint` | 四选一（同 §1） | ✓ |
  | `times` | `number` | `1` | **上限必须定**（否则自反馈） | ✓ |

- **引擎要支持什么**：⚠ **缺机制**，而且是**本文最该警惕的一条缺口**：
  缺的不是 `onHit` 这个**名字**（它在 `TriggerEvent` 里），
  而是缺"**这一次命中是谁打的、打在谁身上、打了几下**"这份**上下文**
  ⇒ 任何"命中之后做点什么"的动词（5 / 10 / 11）都被**同一个缺口**卡住。
  ⚠ **这是一个缺口卡住三条动词**，所以它比"缺一个字段"严重。
- **今天能不能做**：**不能**。
- **边界**：⚠ "打中两次伤害"是载荷叠一次（技能修正），
  **"再放一次这个技能"**（连它的前摇后摇一起）才是修饰 —— 与 §4 同一条界线。

### 11. 幸存响应 `on-miss.else`

- **做什么**：它后面那个技能**没打中**（或被打断 / 失效）的时候，改放**另一个**技能。
- **参数**

  | 参数 | 类型 | 默认 | 范围 | 可调 |
  | --- | --- | --- | --- | --- |
  | `on` | `enum` | `miss` | `miss` / `interrupt` / `expire` | ✓ |
  | `skill` | 技能引用 | 无（必填） | 技能库 | ✓ |
  | `origin` | `enum` | `caster` | 四选一 | ✓ |

- **引擎要支持什么**：⚠ **缺机制** —— `onMiss` / `onExpire` 都没接线（同 §1），
  而且它们要的是**同一个"施法结果"上下文**（这次成没成、打到谁）⇒ 和 §10 是**同一个缺口**。
- **今天能不能做**：**不能**。
- **边界**：⚠ **不是**"条件不成立就往后跳"**（旧 `links.elseTo` 那个语义）** ——
  那个是**序列里换下一个技能**（流程），这条是**换成一个技能去放**（机制）。
  ⚠ `elseTo` 在新模型里怎么表达**还没定**（§十三欠账），别拿这条动词冒充它。

### 12. 状态绑定触发 `trigger.on-status`

- **做什么**：它后面那个技能**被挂上某个状态 / 状态掉层 / 状态消失**的时候，再放一次。
- **参数**

  | 参数 | 类型 | 默认 | 范围 | 可调 |
  | --- | --- | --- | --- | --- |
  | `on` | `enum` | `applied` | `applied` / `stacked` / `removed` | ✓ |
  | `status` | `string` | 必填 | 状态 id | ✓ |
  | `stacks` | `number` | `1` | ≥1 | ✓ |

- **引擎要支持什么**：⚠ **缺机制** —— `onStatusApplied` 只在状态**第一次挂上**时发
  （刷新和叠层**不发**，schema 里写死了这条理由：血契不能被重挂刷子），
  所以 `stacked` / `removed` **两个取值今天没有任何地方会发**。
  ⇒ 只做 `applied` 的话今天能做；`stacked` / `removed` 要**新的事件发布点**。
- **今天能不能做**：**部分能**（`applied` 靠已存在的事件，只缺"接线"，同 §1）。
- **边界**：⚠ "挂上状态"是**载荷**的事（`StatusPayload` = 技能自己做什么）；
  这条动词只回答"**挂上之后，谁被放出来**"，不回答"挂什么状态"。

## 四、⚠ 边界一节：哪些**看起来像修饰技能，其实不是**

⚠ 这一节的存在理由是**防止动词表把整个技能系统吞掉** ✗。
判据一句话：**改"什么时候 / 在哪里 / 怎么打" ⇒ 修饰 ✓；改"多大 / 多疼 / 打谁" ⇒ 技能修正 ✗**

| 你想做的事 | 谁来做 | 为什么 |
| --- | --- | --- |
| 伤害 ×1.5、CD −2 秒、能量 −3 | **技能修正** | 纯数值。放进来之后，动词表会变成"第二个技能编辑器" ✗ |
| 半径 +20%、张角变宽、光束变长 | **技能修正** | 纯几何。和上一条同理（这就是 §9 的争议点） |
| 发射 3 支箭（同一个技能，载体多吐几个） | **技能修正 / 技能本身** | 那是 `DeliverySpec.count` —— **载体字段**，不是"把技能放 3 遍" |
| 这次施法改打另一个目标（锁定改自动） | **技能本身**（`targeting`） | 玩家在"怎么选中人"里定过。⚠ 有争议，见 §6 待裁定 4 |
| 命中后多打一次伤害 | **技能修正**（载荷叠一次） | 没换技能、没换时机，只是数值多一份 |
| 技能自己的前摇 / 命中 / 后摇排什么 | **技能本身** | 那是**一次释放的时间轴**（§八明说：编辑界面是两套） |
| 这条序列里放哪几个技能、按什么顺序 | **序列** | 序列管"放哪几个"，修饰管"怎么放它们" |

⚠ **一个反例，写在这里免得被上面那张表误伤**：
**"命中后不消失、继续飞"** 看着像数值，其实动的是**命中之后的时机** ⇒ 它是修饰 ✓。
所以判据不是"字段在哪个结构里"，而是"**它回答的是哪一类问题**"。

## 五、⭐ 现在必须有的动词 vs 以后加只算加内容

**判据只有一条**（回答玩家那句"以后会不会被限制"）：
> **某个动词如果现在缺，将来加它要不要动引擎的核心形状？**
> 要动 ⇒ **现在必须有**；只是加一条表、一个调用点 ⇒ **以后加 = 加内容** ✓

### A. 现在必须有（4 条）

| 动词 | 为什么现在必须有（它动的是什么形状） |
| --- | --- |
| **1 条件触发** | 它决定**修饰层的调用点形状**："谁在什么时刻问一遍修饰副本"。⚠ 如果只有"每 tick 看"（即只有 §2），以后所有**事件型**触发（命中/失效/状态）都要**回头改调用点** —— 而调用点一改，重放 / 同步都要跟着看一遍 |
| **2 条件监测** | 它决定**边沿语义**和**每 tick 的判定入口**（`crossing` 今天只有一处实现）。它是**触发器的另一种驱动**，两者共用同一张参数表 ⇒ 这张表现在就得对 |
| **3 常驻包装** | 它决定**"修饰能不能改变一段的激活方式"**（`at: 0` + 常驻序列）。**这一条是"修饰不是数值"的实证** —— 缺了它，修饰层会退化成"技能修正的第二套语法" ✗ |
| **4 多重释放** | ⚠ 唯一一条动**"一次释放的份数" + "点数账随参数变"**的动词。缺了它，**点数怎么算修饰技能**这件事就永远没有形状；而这件事一旦晚定，**已有内容的账全部要重算** |

### B. 以后加只算加内容（8 条）

| 动词 | 为什么可以晚（加它只是加内容 / 加一条支路） |
| --- | --- |
| **5 连锁释放** | ⚠ **判它是"可以晚"，但要先补一个形状**：弹射要复用 `pipeline.ts` 那条 `depth` 防线。**先补 depth 的规矩，弹射本身以后加** ✓ |
| **6 延迟释放** | 只是给修饰副本加一个"到期时刻"字段 + 一条每 tick 判定。**不动任何现有形状** ✓ |
| **7 载体置换** | **机制已经在**（`DeliverySpec.kind` 就在那儿），缺的只是"把参数读进来"那一条支路 |
| **8 施放副产品** | **今天不用改引擎就能有它**（`onCast` + `origin` 都接好了）⇒ 是"加内容"的**样本** ✓ |
| **9 存活改写** | ⚠ 它本身就**被判给了技能修正**（§4）。真要收进来，也只是加字段支路 |
| **10 命中回响** | 卡在"施法结果上下文"这个**共用缺口**上（见下 §C），不是卡在它自己 |
| **11 幸存响应** | 同上，和 10 同一个缺口 |
| **12 状态绑定触发** | `applied` 那半边只缺接线；`stacked` / `removed` 要新事件发布点，但那也是"加发布点"，不是改形状 |

### C. ⚠ 三条**元条件**（比上面四条更重要）

「以后加动词只算加内容」这句话**只有在下面三件事成立时才为真** ——
**这才是对"以后会不会被限制"的真正回答**：

1. **动词表数据驱动、可以加动词**（加动词 = 加一行 + 一个执行支路，**不改已有动词的形状**）；
2. **修饰层能被"成本"和"派生"两个钩子拦住**：
   · 今天**没有**成本钩子 ⇒ 任何"少付 / 改成别的资源付"的动词都要**回头改资源结算**（这是隐患 ⚠）；
   · **命中 / 未命中 / 失效 / 状态变化**要能派生成修饰事件（今天只有 3 个时机）——
   ⚠ **这一条不补，"加内容"就是空话**：§10 / §11 / §5 / §12 全被同一个缺口卡着；
3. **时机清单是"可扩展的表"而不是散落的 `if`**（`WIRED_TRIGGER_EVENTS` 已经是这个形状 ✓ ——
   **这个形状必须保住**）。

⇒ **玩家的担心是对的，但担心的对象错了**：会被限制的**不是"修饰技能的种类"**，
而是**这三条元条件**。它们今天一条都不完整。

1. **动词表按"机制"分节还是按"零件"分节？**

     而**零件表回答不了这个问题，动词表能**。

   - 乙案：**加一条 `everySeconds`**（"每隔 N 秒也可以触发一次"）。
   - **我的倾向：甲案先定、乙案写进待办。** 理由：先有"一次"的语义，才有"每隔 N 秒"的对照；
     反过来定会让"残血期间无限刷盾"变成默认行为。

4. **修饰技能能不能动"目标选择"（`targeting`：锁定 / 自动 / 地面点）？**
   - 甲案：**不能**，那是"技能本身"的事（§4 那张表里）。
   - 乙案：**能**，作为一条动词 `targeting.swap`（"强制改成打最近的人"）。
   - **我的倾向：甲案。** ⚠ 理由：一旦能改目标选择，"改打谁"就成了修饰的常规表达，
     而**它和"怎么选中人"是同一件事的两半** —— 会立刻和技能层打架。
   - ⚠ 但**连锁（§5）确实要"换一个目标"** —— 所以更准的说法是：
     **连锁自带它自己的目标选择，而不是"修饰技能普遍能改目标选择"**。

5. **"少付一点"这类动词要不要进表（今天一条都没有）？**
   - 甲案：**不进**（"能量减免"看起来就是技能修正）。
   - 乙案：**进一条 `cost.rewrite`**（"触发时改从另一个池子付"——这明显是机制不是数值）。
   - **我的倾向：乙案，但排在 §C 那个成本钩子之后。** 理由：
     "换个资源付"是机制 ✓、不是数值；但它**会动资源结算** ⇒ 属于"将来要动引擎"那一类，
     得让玩家知道**这条动词迟早要动核心**。

6. **"点数怎么算修饰技能"——今天还没有规则。**
   - 本文**不替它定** ⚠，但把已知的两条约束写在这里：
     · 参数可调的动词（4 多重释放）**必须进账**，否则"随 N 变"无处可挂；
     · 参数不可调的动词（3 常驻包装）今天**没有 points 字段**，是有意为之。
