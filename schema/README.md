# 术式系统 Schema v1 · 说明

**这个文件是规格。代码里的类型只有一份，就在 `skill-schema.ts` 里 —— 这个文件讲"为什么长这样"。**

配套：

- `skill-schema.ts` —— 完整类型定义，也是唯一的真相来源
- `../technique-system/` —— 实现（加载器 / 校验器 / 模拟核 / 命令行 / 编辑器）
- `../docs/STRUCTURE.md` —— 代码结构全图

---

## 一、两层模型

**释放的是术式，修改的是技能。** 这一句是数据模型的全部。

```
技能 Skill           零件。有阶段、有规则、有代价。**玩家编辑的是它。**
   ↓ 被 `Technique.skills` 引用，被 `links` 连起来
术式 Technique       编排。哪几个技能、按什么条件进下一段、绑哪个键。**释放的是它。**
   ↓ 编译（compileTechnique）
CompiledTechnique    一条接起来的时间轴 + 每段的进入条件。**引擎唯一认的形态。**
```

⚠ **没有"组合技"这个概念。** 曾经设计过一个 `Combo` 类型（"可保存、可分享的技能组 ≈ 函数"），
2026-09-21 整个删掉了 —— 因为**术式自己就是"若干技能编程组合出来的东西"**：

```
skills: ["skill.charge-dash", "skill.impact-burst"]
links:  [ { if: [{ type: 'prevHit' }] } ]     ← 冲到了才炸
```

这就是"编程组合"。在它上面再叠一层"组合技"，只是同一个东西的第二个名字。
**分享码将来发的是术式**，不是别的什么东西。

### 为什么要编译这一步

引擎不需要知道有两层，它只要一条时间轴。编译器把术式里每个技能的阶段**接起来**，
并给 id 加上 `技能id#` 前缀（两个技能都可能有一个叫 `cast` 的阶段）：

```
skill.magic-bolt#cast
skill.cleave#windup
skill.cleave#swing
```

规则里的 `phaseId` 跟着一起改写，所以两边永远对得上。
**这样 `cast.ts` / `ai.ts` / `pipeline.ts` 一行都不用改。**

`links` 也会被搬进编译产物，而且**下标要对齐编译后的位置**：
术式里 `links[i]` 管的是第 `i+1` 个技能，编译后它管的是"第 `i+1` 个技能的第一个阶段"。
下标错一格，"冲到了才炸"就会变成"炸完了才判断"。

前缀只在引擎内部存在。给人看的地方（运行器的输出、编辑器的规则列表）用
`localId()` 去掉它。

### 谁查什么

| 层 | 查什么 | 在哪 |
|---|---|---|
| 技能 | 结构、阶段、规则、**点数** | `validateSkill` |
| 术式 | 编排：激活方式、目标、引用了哪些技能 | `validateTechnique` |
| 引用是否存在 | **编译期**的事（需要整个内容库） | `compileTechnique` |

## 二、核心比喻

> **技能 = 一条时间轴上，按顺序执行的规则集合。**
> **规则 = 当【时机】若【条件】则【动作】**
> **动作 = 载体 + 载荷**

八个分类维度对应到字段：

| 维度 | 字段 | 可选值 |
|---|---|---|
| 载体 | `Action.delivery.kind` | self / projectile / beam / meleeArc / capsule / area / aura / spawn |
| 载荷 | `Action.payload.kind` | damage / heal / **attribute** / status / displacement / perception / spawn |
| 触发时机 | `Rule.when` | onCast / onHit / onMiss / onCrit / onNonCrit / onKill / onExpire / onRemoved / onEnter / onLeave / onDamaged / onLethalDamage / onLowHp / onTick / phaseEnter / phaseComplete / phaseInterrupt |
| 激活方式 | `Technique.activation` | press / release / hold / toggle / auto |
| 目标 | **`Skill.targeting`** | mode（怎么选）+ valid（对谁有效）。⚠ 2026-09-21 日志 47 起它在**技能**上 —— 术式和序列段**都不带**瞄准了 |
| 执行形态 | `Phase.occupiesCaster` | true = 持续技 / false = 脱手技 |
| **打断等级** | `Phase.interrupt` | damage（挨打就断）/ control（只被控制打断）/ none（无法打断） |
| 来源 | `SkillSource.kind` | character / weapon / trinket / talent / buff |

### 只有七种载荷

**控制、护盾、霸体、龟壳、隐身、亡灵反转 —— 全都是 `StatusDef` 的变体，不是独立载荷。**

| 经典效果 | 其实是 |
|---|---|
| 冻结 / 沉默 / 缴械 / 定身 | `disables: ['move','attack','cast']` 等组合 |
| 护盾 / 次数盾 | `hooks: [{ stage: 'absorb', absorb: {...} }]` |
| 霸体 | `immuneTags: ['hardCC']` |
| 龟壳（伤转治疗） | `hooks: [{ stage: 'modify' }]` |
| 隐身 | `visibility: 0` |
| 亡灵受治疗受伤 | 标签覆写规则 + `tags: ['undead']` |
| 自我减益当代价 | 同一份状态的 `target: 'self'`（定价符号相反） |

**检验标准：加一个新控制效果（比如"嘲讽"）应该只需要写一个 JSON 文件，不改代码。**

### 打断为什么不是布尔值

只有"能/不能"两档的时候，一个**"扛得住小伤害、但吃硬控"的释放帧**表达不出来 ——
而那恰恰是动作游戏里最常见的那种帧。近战的挥砍如果被任何一点蹭伤打断，就根本没法玩。

所以是三档，而且三档都是**收益**（越扛得住越值钱）。

## 三、七条架构纪律

**这七条比 schema 本身更重要。** schema 可以改，纪律违反一次要还几个月。

| # | 纪律 | 被谁逼出来的 |
|---|---|---|
| 1 | AI 一律按**阵营动态查询**目标，永不硬编码"追玩家" | 魅惑（也白送了召唤） |
| 2 | 伤害结算必须是**可拦截的管线**，不是一行 `hp -= dmg` | 名刀司命 |
| 3 | 技能实例必须有**来源（owner/source）**，技能栏是多来源聚合 | 武器铭刻 |
| 4 | `core-sim` **不引用任何外部 API**（无 window / Date.now / Math.random）；渲染只读模拟状态 | "以后升级美术" |
| 5 | Schema 从第一天带**版本号 + 迁移函数** | 同上 |
| 6 | 管线钩子有**两个来源**：技能图 + 状态。编译期要从两边收集并排序 | 护盾 / 龟壳 |
| 7 | 服务端要能**按客户端过滤状态**（隐身不能只做在渲染层） | 隐身精英 |

**第 1 条是复利的**：为了魅惑做对了阵营查询，召唤就几乎免费。

第 4 条是**自动执行**的：`npm run test:purity` 扫 `src/sim/**`，
找出 `Date` / `Math.random` / `console` / `Math.sin` 等 24 种东西，违反了直接红灯。
（`geom.ts` 里连 `Math.hypot` 都不用，因为只有 `sqrt` 是 IEEE 754 强制精确的。）

## 四、伤害管线（顺序固定）

```
1 raw        原始        计算基础值
2 intercept  拦截        名刀、免疫（阻止它发生）
3 modify     修正        增减伤、伤害转治疗、亡灵反转
4 absorb     吸收        护盾、次数盾
5 apply      应用        真正扣血
6 after      后置        吸血、反伤、onDamaged
```

- **六个步骤的先后由系统固定**，玩家不能改
- **玩家只能拖拽"同一个步骤内"的规则顺序**（`Rule.order`）
- 所以术语表里**没有"优先级"这个词** —— 玩家只需要拖规则

**伤害和治疗共用同一条管线**（只是符号不同），否则亡灵反转、禁疗、治疗加成都要写两遍。

## 五、点数系统：一本额度账

### 宗旨：每个可调值都有一个**配平为 0 的默认值**

玩家 2026-09-21 把它作为**宗旨**定下来，原话是：

> 所有点数相关的可调整的值，都具有一个默认值，在这个默认值下点数是配平为0的。

⚠ **这个"默认值"是每个技能自己的出厂数值**（玩家 2026-09-21 追问之后定的）：
`content/skills/*.json` 里写的那一套就是这个技能的默认值。
全局那张标准数值表（`docs/default-values.md`）只是**写内容时的强度标尺**，
**不参与**算账。

所以账算的是"**你改了多少**"，不是"这个东西值多少钱"：

```
账 = 现在的技能 − 出厂版本        （逐条贡献相减，见 src/pricing.ts 的 skillLedger）
```

推论，每一条都重要：

- **出厂内容全部是 0 点。** 没被玩家改过的技能，账是空的 —— 它表达的是
  "你拿到的这套东西本身就是配平的"。不会出现"两个数值相同而效果不同的火球"。
- **机制免费，数值有价。** "能位移"这件事不要钱，位移了**几米**才要钱
  （玩家原话：**"位移的机制本身是不应该有代价的，位移的距离有代价"**）。
- **编辑器里的每一个滑块都是从这个默认值出发做交易**：往强了拖 → 账上多出收益 →
  必须去别处补；往弱了拖 → 反而提供额度。
- **绝对账仍然存在**（`priceSkill`），但它的身份是**内部强度标尺**：
  回答"这个技能站在汇率表的哪个位置"。它**不判配平**。

⚠ **一个例外都没有。** 曾经有过一个 `Skill.factoryDebt`（"出厂就负债的零件"），
让裂魂和血祭斩从**绝对账**起算、好让出厂内容里也有"一放就吃血契"的术式。
**2026-09-21 当天就删了**，玩家的判断是"没什么必要"，两句话：

> **负债件的变体不一定是负债件。**
> （宗旨）应该是**铁的**。

⚠ 而且那个标记在**变体**上本来就说不通：实现判的是"模板标没标"，
所以变体是**一定**继承 —— 把裂魂改弱之后，用它的术式反而会拿到一大笔额度，
算法却还是"负债件"那一套。现在：

- **出厂内容全是 0 点**，一个例外都没有（`tests/pricing.ts` 逐个扫 30 个技能钉着它）。
- 想超模就**自己编变体**（把技能改强）→ 那份术式的合计变成负的 → **负值术式** →
  用血契付。血契要服务的就是这个。

### ⚠ 固有效果 vs 规则：这个技能"是什么"和它"额外做了什么"

玩家 2026-09-21 第 1 条：

> 技能本身的效果**不计入规则栏中**，也不具有点数盈亏。

| | 是什么 | 放哪儿 | 例子 |
| --- | --- | --- | --- |
| **固有效果** `Skill.effect` | 这个技能**是什么**：时间轴走到这一段就发生 | 单独一块 | 挥砍造成伤害 · 传送 · 竖一堵墙 |
| **规则** `Skill.rules` | 这个技能**额外做了什么**：挂在某个时机上的行为与反应 | 规则栏 | 命中时回能量 · 击杀时刷新冷却 · 被暴击时反伤 |

判据是**机械的**：`when === 'phaseComplete'` 的那些是固有效果，其余的是反应。

⚠ **引擎不需要知道这个区别**：编译时效果被折成一条 `when: 'phaseComplete'`
的规则（`src/effects.ts` 的 `effectAsRule`），所以这次搬家对行为和账
都是**零改动**（`duel` 逐位一致、`calibrate` 的残差一模一样）。

⚠ 但**别处很容易漏**：任何"遍历 `skill.rules`"的代码都会看不见效果，
而每一种漏法的表现都是静默的 —— 编译漏了是"打出去什么都没有"，
定价漏了是"效果里的数字变成真的免费"，引用检查漏了是"运行期才炸"。
所以规矩是：**"这个技能会做什么"只有 `allRulesOf()` 一个入口。**

### 符号约定

```
负数 = 效果消耗的额度（伤害、治疗、给敌人上 debuff、买规则位）
正数 = 代价提供的额度（扣能量/生命、冷却、自我限制、卖规则位）
```

### ⚠ 配平的责任在**术式**，不在技能

| | 是什么 | 要不要配平 |
|---|---|---|
| 技能 `Skill` | **零件**。默认 0 点，**玩家改过之后可以很歪** | **不用** |
| 术式 `Technique` | **成品** | **必须到 0。** 它所有改动加起来要收支相抵 |

"零件可以歪"这件事现在的来源是**玩家的编辑**，而不是出厂内容：
你可以把一段的冷却拉到 20 秒（赚一大笔额度），再拿它去付另一段的伤害翻倍。
这正是玩家最早要的那条交易（"牺牲射程换来伤害提高"）。

推论：**单个技能当术式用时，它自己就必须配平** —— 因为那时它就是成品。

**合计 < 0 = 花超了 = 负值术式** → 每次使用按 |合计| 消耗血契。
合计 > 0 = 额度没用完，不配平，等于白送（所以要拦）。

### ⚠ 技能分**两个库**，技能**不属于术式**

玩家 2026-09-21 纠正过一次（见日志 2026-09-26-32）：

> 技能是玩家拥有的东西，存在两个库：**基础技能库**（我们写的出厂配平为 0 的那些）、
> **自定义技能库**（玩家进行编辑后的技能另存一份副本在这里）。
> 技能可以存在多个变体，玩家给它们取名字……
> 技能不是独属于一个术式的，应该影响所有用到它的术式，但要注意
> **基础技能和它的变体是两样东西**……**自定义技能是独立的，它不属于术式**。

| | 是什么 | 谁改 | 存在哪 |
| --- | --- | --- | --- |
| **基础技能库** | 出厂内容（默认配平为 0 点），也是"创造一个技能"的**模板** | 不能改 | `content/skills/*.json` |
| **自定义技能库** | 玩家创造出来的变体（`Skill.basedOn` 指向模板） | 随便改、可改名、可删 | **存档**里 |

四条推论，每一条都重要：

1. **改技能 = 先"创造一个技能"**（挑一个基础技能当模板）→ 编辑 → **保存**。
   基础技能自己永远不会变 —— 所以**基础技能和它的变体是两样东西**（各有各的 id）。
2. **变体的账对着它的模板算**（`basedOn` 指的那个基础技能），
   不是对着上一份变体 —— 宗旨是"偏离出厂版多少"。从变体再"另存为"出来的，
   `basedOn` 仍然是**最初那个基础技能**。
3. **变体是全局的**：改它，**所有用到它的术式一起变**
   （它们的账和它们的伤害都跟着变，`src/main.ts` 会全量重编 + 重注册）。
4. **术式两个库都能引用**："玩家不只能从自定义技能库中组成术式，
   也能从基础技能库中选择"。

⚠ 查找技能只有一句话：**自定义库优先、基础库兜底**。
编译、定价、算血契、编辑器都走它。分成几处各写一遍的话，迟早有一处只查基础库 ——
而那种漏法是静默的（技能段用的是基础版的数值，账却按变体算）。

⚠ **分享码带着这份术式用到的变体**（第 2 代码）。收码的人不需要先有那些技能 ——
它们会被导进他的自定义技能库；有冲突时**问他**（用我的 / 导入码里的新副本），
不静默覆盖：他自己那份可能已经用在好几份术式上了。

⚠ **删变体先要清引用**（玩家选的）：还有术式在用它就不给删，
而且要明确告诉他**是哪几份术式**。

### 符合的代价：技能不是"术式的私有数据"

第一版把它做成了 `Technique.skillCopies`（每个术式私藏一份副本），**删掉了**。
三个说不通的地方：技能不是一个"你拥有的东西"、同一个技能在 N 份术式里
是 N 份互不相干的副本、删掉一份术式会把技能上的功夫一起带走。

### ⚠ 点数一个字都不存进 JSON

它是**内容的函数**：`technique-system/src/pricing.ts` 拿技能（阶段时长、打断等级、
代价、规则里的伤害/治疗/状态）算出每一笔。汇率表在 `content/balance.json` 的
`rates` 里 —— 改汇率不用改代码。

第一版把点数手写在 `Rule.points` / `Phase.points` / `StatusDef.points` 上，
结果玩家把"30 伤害"拖成"300 伤害"，点数纹丝不动。**全删了。**
（方向前后错过四次，都记在 `technique-system/README.md` 里。）

### 规则位 = 复杂度税

```
买 N 条（上限高过基准 4）→ 消耗 N × buyCost    → 负
卖 N 条（上限低于基准）  → 提供 N × sellGain   → 正
```

上限越高，能塞的东西越多，所以要付出；主动压低是自缚，所以给补偿。
点表里 `ruleSlots` 的档位就是 **0..8 每一档都有**（它是条数，跳档说不通）。

### 配平容差 —— ⚠⚠ **这一段已经作废（2026-09-30 日志 57）**

`balanceTolerance`（原来是 ±2）**已经从 `content/balance.json` 里删掉了**，
代码里**没有任何地方**读它。用户裁定原话：

> **点数之和大于 0 就能用，小于 0 就要支付血契才能用**
> （"既然正的容差没用，那**容差就不该存在**"）

⇒ 判据只剩一条：**合计 < 0 ⇒ 负值术式**（付血契）、**合计 ≥ 0 ⇒ 能用**。
同时账上每一笔都是**整数**（逐条取整 + 最大余数法）、**每个非零条目至少 1 点**，
唯一的"缓冲"是机器精度 `POINT_EPS`（1e-9，挡浮点噪声，**不是宽容度**）。
见 `technique-system/README.md` 的「点数改成整数」一节 + 日志 57。

（下面这几行是**作废前的理由**，保留作历史：账改成"相对出厂值"之后，
出厂术式按定义就是 0 —— 所以那个容差当时的意义是"玩家编辑出来的偏差小于多少就算了"。）

### ⚠ 代价时机的定价必须分开

| 代价 | 早付（挂在靠前的阶段）意味着 | 定价 |
|---|---|---|
| 能量 | 固定速率回复，没有"更早开始回复"的补偿 → **纯风险** | 提供额度（正） |
| 冷却 | CD 从进入阶段时倒计时 → 技能时长被算进冷却 → 实际冷却更短 | 提供额度，但收益比能量小 |

**被打断不退还** —— 那正是"早付"这个风险本身。
冷却挂在哪个阶段由玩家选（前摇 / 释放 / 后摇），编辑器里是三选一。

### 为什么定价永远不可能完美

`10 伤害 / 1 秒 CD` 和 `1000 伤害 / 100 秒 CD` 点数相同，
但强度取决于场景（站桩 Boss / 清小怪 / PvP 爆发）。
**所以平衡只能在"平均场景"下成立** —— 这就是必须有场景套件（第 7 步）的原因。

### 血契

负值术式每次使用消耗等量血契。**血契从战斗中的负面行为（自伤等）获得，不能为负。**
定价方式是用设计目标反推，不是算：

```
目标：一场 60 秒战斗能放 2 次超模技能
平均超模 ≈ -6 → 需要 12 血契
自伤最多占总血量损失的 30%，一场掉 60 血 → 自伤预算 18 血
→ 10% 血 ≈ 6.7 血契
```

## 六、已经定下来的（原「待定项」）

| 项 | 决定 | 理由 |
|---|---|---|
| `ruleSlots` 初始值 | **4** | 出厂技能都声明 4；基准定高了等于给每个技能发补贴 |
| 买 / 卖一条规则位 | **1.5 / 1** | 量级要和技能效果净值（几个点）匹配，原来是 5/3，太大 |
| 配平容差 | ~~**±2**~~ ⇒ **已删**（2026-09-30 日志 57） | 见上：**容差不该存在**。新口径 = 合计 ≥ 0 就能用、< 0 付血契；账上是整数、非零条目至少 1 点 |
| 血契上限 | 还没定 | 要等有血契获取渠道之后 |
| "负面行为"包含哪些 | 目前按自伤设计 | — |
| 单技能总点数是否封顶 | 不需要 | 收支天然相等，超模的那部分已经由血契收了 |
