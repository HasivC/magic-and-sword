## 先把两个词分清楚

这是整个数据模型的地基，也是**改了三次才对**的地方：

```
技能 Skill        零件。有阶段、有规则、有代价。**玩家编辑的是它。**
   ↓ 被引用
术式 Technique    编排。哪几个技能、按什么顺序、绑哪个键。**释放的是它。**
   ↓ 编译
编译产物          一条接起来的时间轴。**引擎唯一认的形态。**
```

一句话：**释放的是术式，修改的是技能，术式由若干技能组成**（Noita 那种
"把法术排成一列"的模型）。术式自己不带任何效果，所以它也没有自己的点数账 ——
它的账就是它那些技能的总和。

细节见下面的「技能 / 术式：两层模型」。

## 里程碑 0.5：在浏览器里看见它

```bash
npm run build:web     # 把 src/sim/ 编成浏览器能跑的 JS
npm run serve         # 起一个静态服务器（默认 5173）
# 打开 http://127.0.0.1:5173/
```

**这是第一次能用眼睛而不是日志去判断这套设计。**

WASD 移动、鼠标瞄准、`1`~`5` 放技能、`R` 重开。
场上有三个敌人，各自不同的手法：一个远程放风筝、一个贴脸砍、一个蓄激光。

### 它验证了什么

> **`core-sim` 真的能在浏览器里跑，而且跑出来的和命令行里一模一样。**

`web/src/main.ts` 没有复用 `src/cli/` 下的任何东西 —— 那些要读文件、要打印，
而浏览器只能 `fetch`。所以它是一个**完全独立的消费方**：
`src/sim/` 里如果混进了任何环境相关的东西，这里立刻就崩。

它自己不做三件事：

1. **不模拟** —— `stepWorld` 才是唯一的真相
2. **不做时间** —— 用累加器把渲染帧和固定 tick 解耦
3. **不改状态** —— 渲染只读

守住第 3 条，"以后换美术"就只是换掉 `draw()` 那几个函数。

### 浏览器不能跑 TypeScript，怎么解决

Node 24 直接跑 `.ts` 靠的是类型擦除，浏览器没这个待遇。所以单独编一份：

```jsonc
// tsconfig.web.json
"allowImportingTsExtensions": true,
"rewriteRelativeImportExtensions": true,   // 把 import 里的 .ts 改写成 .js
"rootDir": "..",                            // src/schema.ts 会转出仓库根的文件
"types": []                                 // 浏览器里没有 Node 的类型
```

**源码里的 `.ts` 后缀一个都不用动** —— `rewriteRelativeImportExtensions` 负责改写。

### 有一条测试专门盯着"两边一不一样"

`tests/web.ts` 会拿同一份场景，**一边用源码跑、一边用编译产物跑**，
然后比较 600 tick 之后的快照是否逐字节一致。

不一样的话，"浏览器里能跑"就只是句口号 —— 你在浏览器里看到的
和命令行里调出来的会是两套东西。它还顺手确认编译产物里没混进 Node API。

### 实测报出来的两个 bug

第一次真的玩起来之后，两个问题立刻暴露了。**它们都属于"命令行和测试都测不出来"那一类。**

**1. 玩家不会死。**

根因在内容：`skill.named-blade` 的 `onLethalDamage` 钩子**没有冷却**，
所以每一次致命伤都被它拦下来。砍了半天血一直是满的。

修法是用「已触发」状态当冷却：

```json
"if": [{ "type": "not", "of": [
  { "type": "hasStatus", "who": "self", "value": "status.namedBlade.spent" }
]}],
"then": [ 拦下, 给无敌, 挂一个 25 秒的「司命·冷却」 ]
```

顺便让玩家在界面上**看得见**它用掉了 —— 否则你只会觉得"怎么这次没拦住"。

**2. 无下限对子弹不生效。**

两层根因：

- 投射物的阵营是 `neutral`，而 `isHostileTo` 对 neutral 一律返回 false
  → 光环的 `valid: ['enemy']` 永远匹配不到子弹
- `integrate()` 里写了"只有 actor 吃 moveScale"。
  我当时的理由是"子弹不该因为**发射者**被减速而变慢" ——
  但减速是挂在子弹**自己**身上的，跟发射者无关。
  而且「靠近的东西自动减速」本来就该管子弹，**那是这个术式的全部意义**

两个都修了，`tests/battle.ts` 里有专门的复现测试。

**这两个 bug 教训是一样的：** 前四步的测试全是我按自己的理解写的，
而这两个只有**真的去玩**才会发现。这就是里程碑 0.5 存在的理由。

## 打击感

### 技能编辑器（阶段 2 的第一块）

**按 `Tab` 打开。** 它不另开页面，就长在游戏里 —— 改完立刻能在右边的场地里打。

这一块是**整个项目的生死线**：

> 如果陌生人不能在五分钟内捏出一个能用的技能，
> 那"极高自由度"这个卖点就不成立 —— 引擎做得再对也没用。

**它编的是「技能」，不是「术式」。** 下拉框里选的是技能（零件），
改完之后**用到它的术式会当场重新编译**，回到场地里按对应的键，
打出来的就是改之后的效果。选中一个技能时，面板顶上会写清楚
"被哪些术式用到" —— 技能自己不能放，得让玩家看见它挂在哪儿。

### 四个设计决定

**1. 编辑 → 试 → 再编辑，这个循环要尽可能短。**
不刷新、不切窗口。所以编辑器做成游戏里的一层浮层，不是单独的页面。

**2. 不针对任何一种效果写专用表单。**
而是**把技能 JSON 里所有数值叶子抽出来**做成滑块（`web/src/leaves.ts`）。

好处很直接：**加新效果不用改编辑器**。七个技能一共抽出 67 个可调数值，
其中没有一个是我为它专门写的。

面板上写的是「破甲 · 持续」，不是 `rules[1].then[0].payload.inline.duration`——
数组元素会带上自己的 `name` / `note`。

**3. 点数条下面必须写清楚"点数是什么"。**

第一版没写，玩家直接来问：**"蓄力 · 点数 和 贯通 · 点数是做什么的？"**
（那是「贯日」的两个**阶段名**，配上点数看起来像两个莫名其妙的词。）

现在的规矩：**编辑器里任何一个数字，玩家都得能回答"它是什么、往哪边调"**。
所以点数条下面有一块常驻说明：

> 账算的是**「你改了多少」**：**负数 = 你花的额度比出厂版多**，
> **正数 = 你省下来的额度**。你拿到的那个版本就是 **0 点**。
> ⚠ **技能不必自己配平**（改了之后可以很歪）；
> **必须配平到 0 的是术式**（它里面所有改动加起来）。
> 这块零件是负数 = 它比出厂版强这么多（要靠别的零件来付），
> 正数 = 它比出厂版弱这么多（拿去补别的零件）。

⚠ 这条规矩 2026-09-21 换过一次（见日志 2026-09-26-30）：
以前报的是"这个零件值多少点"（绝对账），
现在报的是"**你改了多少**"（相对出厂值）—— 因为宗旨把"默认值"定成了
**每个技能自己的出厂数值**。绝对账还在，但它是内部强度标尺，不给人看了。

明细里每一行也带来源（`阶段 · 蓄力` / `固有效果 · 近身横扫` / `规则 · 打中就破甲`），
规则行还有 `title` 提示"这一条比出厂版本花了 1.34 点"。

**3.5 「固有效果」是单独一块，不在规则栏里**（玩家 2026-09-21 第 1 条）。

```
Skill.effect  这个技能**是什么**（时间轴走到这一段就发生）→ 单独一块，排在规则前面
Skill.rules   这个技能**额外做了什么**（挂在某个时机上的反应）→ 规则栏
```

⚠ 引擎不知道这个区别：编译时效果被折成一条 `phaseComplete` 规则
（`src/effects.ts`）。所以搬家的**行为和账都是零改动** ——
换的只是数据形状和界面归属。

⚠ 但**别处很容易漏**：任何遍历 `skill.rules` 的代码都会看不见效果，
而每种漏法都是静默的（编译漏了 → 打出去什么都没有；定价漏了 →
效果里的数字变成真的免费）。规矩：**"这个技能会做什么"只有
`allRulesOf()` 一个入口。**

**4. 滑块是"点表"，不是区间。**

玩家原话：**"数值选择的滑条不必有那么多取值，大部分用三五个取值就够了，
最多也不要超过 10 个。"**

第一版给的是 `min/max/step`：0~300 的伤害滑块有 300 个取值，
拖一格差 1 点 —— **既调不准，也没有"选择"的感觉。**

现在每个数值字段配一张**点表**（`VALUE_SETS`）：

```
伤害      10 / 15 / 25 / 30 / 50 / 200
阶段时长  -1 / 0.1 / 0.2 / 0.3 / 0.5 / 1     （-1 = 蓄力）
状态时长  -1 / 0.5 / 1.5 / 3 / 5 / 10 / 25
冷却      1 / 2 / 3 / 8 / 20
```

实测：**平均 5.6 档，中位 5 档，85% 在 6 档以内，最多 7 档。**

三个细节：

- **倍率单独一张表。** `op: 'mul'` 的格子长在 1 附近（×0.9 = 削弱 10%），
  和加减法的格子（-4 点能量）不是一个量纲，混用两边都不合适。
  为此要把"我在一个倍率里"这个信息沿着子树传下去 ——
  数字在 `modifiers[0].value.const`，离写着 `op: 'mul'` 的对象还有两层。
- **阶段时长和状态时长也是两张表。** 阶段是"零点几秒"的动作节奏，
  状态是"几秒到半分钟"的持续时间。这个坑第一版就踩过（测试抓到的）。
- **格子外的值会被插进来，不静默改掉。** 否则"打开编辑器"这一个动作
  就会改内容。插进来的那格会标黄点，而且 `tests/editor.ts` 断言
  **出厂内容的 67 个数值一个都不在格子外**。

### 每个数值都带单位

玩家原话：**"属性设置应该加上 s、m 这样的单位。"**

面板上写着「挥砍 · 时长　0.2」和写着「挥砍 · 时长　`0.2 s`」，
理解成本完全不同 —— 前者要猜，后者不用。

```
时长 / 冷却 / 间隔  →  s
半径 / 长度 / 宽度  →  m
速度                →  m/s
张角                →  °
能量 / 生命         →  能量 / 生命
规则位上限          →  条
```

**距离和速度用米**，而且这个尺度是自洽的：场地半径 18 米、
人半径 0.5 米、挥砍半径 2.5 米、跑速 6 米/秒（≈ 人类短跑）。
不需要跟真实世界对齐，但**自己内部要对齐** —— 不然"12 米/秒 的飞弹"
读数就没有意义。

属性载荷里的数字（`payload.value.const`）路径里没有 `energy` 这种键名，
单位得**从它改的属性反推**（`char.energy.current` → 能量）。
这一类是玩家提的"属性设置"的主要部分。

### 「收招 · 冷却」是干嘛的

玩家原话：**"如果是冷却时间那没必要标注是收招，如果是选择进入冷却的阶段
那取值应该是阶段而不是秒数。"**

答案是**两件事都要说**，而这个 schema 里它们本来就是一件事的两面：

```jsonc
{ "id": "recovery", "name": "收招", "duration": 0.2,
  "cost": { "cooldown": 3 } }     // 这个技能有 3 秒冷却，
                                   // 而且**从「收招」结束时才开始走**
```

所以修法不是二选一，而是让它说人话：

- **单独分成「代价」组**（原来埋在阶段下面，看着像"收招这个阶段有多长"）
- **加一句说明**：`数值是"多少冷却"，「收招」是"什么时候付" ——
  这个阶段一结束，冷却才开始走。换个阶段就是换代价时机。`
- 单位仍然是 `s`（它确实是时长）

「代价时机是玩家的设计自由」是第 4 步就定下来的规则 ——
把冷却挂在前摇上，你放了技能立刻进 CD；挂在收招上，你得先挥完这一刀。
面板上必须把这件事讲出来，而不是让玩家从字段位置去猜。

### 数值说明是**生成的**，不是手写的

玩家原话：**"『命中时回复 8 点生命』，在调整数值之后这个 8 应该改变，但它没有。"**

根因和"点数手写在 JSON 上"**一模一样**：`Rule.note` 是手写的字符串，
里面的数字和真实数值是**两份会漂移的东西**。

所以规矩也一样：**说明是内容的函数**（`src/describe.ts`）。

```
JSON 里：{ "when": "onHit",
           "then": [{ "target": "self",
                      "payload": { "kind": "heal", "amount": { "const": 10 } } }] }
              ↓ describeRule()
面板上： 命中时 回复 10 点生命（自己）
```

拖成 20，那句话当场就是 20（`refreshLive()` 就地更新，不整块重画 ——
重画会让正在拖的那个 `<input>` 被换掉，浏览器立刻停止派发 `input` 事件）。

那 `note` 还要不要？**要，但它只写设计意图，不写数字：**

```jsonc
"note": "近身横扫"                       // 生成不出来的东西，留着（显示成小字）
"note": "扇形 120° 内造成 30 物理伤害"    // 生成得出来，删掉
```

校验器现在会拦这一条（`NOTE_WITH_NUMBER`）——
**手写的数字迟早会和数值脱节**，那就在写进 JSON 的时候拦下来，
而不是等玩家玩到才发现。

### 它用的是和命令行同一份代码

`src/validator/`、`src/pricing.ts`、`src/describe.ts` 都不依赖 node ——
所以**校验器、点数账本、说明生成器直接在浏览器里跑**。
编辑器看到的问题，和 `npm run validate` 说的是同一件事；
点数条是同一份 `priceSkill`，规则说明是同一份 `describeRule`。

### 编辑器能做什么

**按 `Tab` 打开，打开时自动暂停**（编辑的时候不该被敌人追着打）。

- **规则列表** —— 每条规则显示"当什么时机 / 做什么 / **这条值多少点**"，右边一个 `×` 删掉
- **调色板** —— `＋命中额外伤害`、`＋命中减速`、`＋命中持续伤害`、`＋命中吸血`、
  `＋击杀重置冷却`、`＋代价：扣能量`、`＋代价：扣生命`、`＋代价：加冷却`
- **数值滑块** —— 每个可调数字一条
- **阶段开关** —— 可打断 / 占用施法者
- **实时点数条 + 实时校验**
- **存回去** —— 下载 JSON / 复制 / 看一眼 / 还原（下载的文件放回 `content/skills/`）

**调色板里加的每一条都故意不配平。** 加一条效果，点数条立刻变红说
"差 3 点代价"—— **那正是我们想让他学会的事。**

调色板故意只放最常用的几种，不是穷举。**穷举等于把 schema 摊在玩家脸上。**
剩下的靠"加一条最接近的，再用滑块改成你要的"。

### 换引用，不就地改

编辑生效时换的是 `skills` 里的**对象引用**，不是就地改字段。

> 正在进行的施法持有 `cast.technique` 的引用。就地改的话，
> 一枚已经飞出去的子弹会在半路改数值。换引用的话，跑到一半的施法保持原样，
> 下一次才用新值 —— 这也更符合直觉。

### 测试抓到的两个真 bug

编辑器没法在 Node 里点，但**数值抽取那一层是纯函数** ——
而它恰恰最容易错。`tests/editor.ts` 对全部七个真技能做三件事：
每条路径读得到、写得回、**当前值落在滑块范围内**。

最后一条立刻抓到两个问题：

1. **`setByPath` 走错了节点** —— 我把整条路径走到底（拿到叶子那个数字），
   然后在数字上设属性。ESM 是严格模式，直接抛 TypeError。
2. **`duration` 这个键在两个地方含义不同** ——
   阶段时长是 0.05~1 秒的量级，状态时长能到 25 秒（名刀的冷却）。
   共用一个范围的话，要么阶段滑块太粗，要么状态值超出范围、一碰就跳。

顺带还发现 `-1` 是个**哨兵值**不是数字（阶段 = 蓄力，状态 = 永久），
滑块底部得留给它，面板上也要写清楚 —— 不然拖到底不知道会发生什么。

### 做调色板时撞出来的第三个 bug（这个更严重）

加「＋命中持续伤害」模板时，TypeScript 直接报错：
`'every' does not exist in type 'PipelineHook'`。

顺着查下去发现：**状态上的 `onTick` 钩子根本没跑过。**

管线里的 `matchWhen` 对 `onTick` 一律返回 `false` —— 只有 `onLethalDamage` /
`onDamaged` / `onHit` / `onCrit` / `onNonCrit` / `onMiss` 六种会被匹配。
所以状态钩子写 `when: 'onTick'` 等于没写。

**`soul-rend` 的裂魂创伤一直是白挂的**，只是它一击就把目标秒了，没人发现。

修法：加了 `tickStatusHooks()`，复用规则那套限速计时器，
不写 `every` 默认 1 秒。校验器也加了一条提醒。

做之前先分清楚**哪些属于模拟、哪些属于表现** —— 这决定了它们该写在哪：

| | 归属 | 为什么 |
|---|---|---|
| **顿帧** | **模拟** | 停的是世界，不是画面。渲染层假装停顿的话，模拟还在跑，停顿结束后敌人会"跳"一下 |
| **击退** | **模拟** | 真的改变位置，是玩法 |
| **闪白 / 飘字 / 粒子 / 抖屏 / 音效** | 表现 | 只读事件，不影响任何判定 |

### 模拟层：顿帧与击退

两个都按「这一下打掉了目标**多少比例**的血」算，不按绝对伤害：

> 对一只 40 血的小怪打 30 点，比对一个 2000 血的 Boss 打 30 点爽得多。
> 那也是对的。

```ts
MAX_HITSTOP = 0.12          // 最长停多久
HITSTOP_FRACTION = 0.6      // 打掉 X% 的血 → 停 X% × 0.6 秒
MIN_HITSTOP_DAMAGE = 12     // 低于这个不顿帧 —— DOT 每 0.5 秒跳一次，不然会卡成幻灯片
MAX_KNOCKBACK = 5           // 米/秒
```

**顿帧照样推进 tick** —— 停的是世界，不是时间。事件在顿帧期间被清空，
所以不会有新事件漏出去。

**击退用独立的 `push` 冲量**，不加到 `vel` 上。因为 AI 每 tick 都会覆写 `vel`，
直接加进去会当场被抹掉。`push` 自己按 0.85 每 tick 衰减。

### 表现层：全在客户端

删掉 `main.ts` 里的 fx 那一节，**游戏玩法一点不变，只是不好玩**。

- **受击闪白** —— 叠一层白。顿帧期间它停在最亮的那一帧上，这就是"打实了"的感觉
- **伤害飘字** —— 先弹出来再缩回去，数字才有"蹦"的感觉
- **命中粒子** —— 按伤害决定数量
- **屏幕抖动** —— 只偏移相机，不动世界坐标
- **音效** —— 用 WebAudio 现场合成，**不需要任何素材文件**。
  打得越疼音调越低越长；`M` 键静音

特效用的是**真实时间**，不是模拟时间。顿帧的时候世界停住，
但闪白要继续衰减、飘字要继续飞 —— **那正是让"停住"被看见的原因**。
特效跟着冻住就变成卡顿了。

### 一个连带影响

顿帧改变了节奏，所以**按时长写的测试会失效**。`tests/cast.ts` 里就有一条：

```
⚠ 要留够余量：命中会产生顿帧，顿帧期间世界不动但 tick 照走，
  所以"跑 40 tick"不等于"过了 40 tick 的模拟时间"。
```

这不是测试写错，是顿帧真的在改变节奏。

## 第 2 步：模拟核心

### 两类属性，别混

| | 例子 | 怎么变 |
|---|---|---|
| **存储属性** stored | `hp.current`、`energy.current` | 被**直接改写**。真的加减 |
| **派生属性** derived | `hp.max`、`energy.regen`、`speed` | 基础值 + 状态修饰，**算出来**的 |

**状态修饰不要用在存储属性上。** 想持续扣能量，用一条 `onTick` 规则的属性载荷。
校验器会检查这一条（`MODIFIER_ON_STORED`）。

### 属性求值顺序（不许改）

```
基础值 → 加算 add → 乘算 mul → set / reset 覆盖
```

`reset` 恢复成基础值 —— **露娜的大招刷新就是它**。

### 状态的四种装法

| 经典效果 | 装法 |
|---|---|
| 冻结 / 沉默 / 缴械 / 定身 | `disables` 的不同组合 |
| 霸体 | `immuneTags: ['hardCC']` |
| 隐身 | `visibility: 0` |
| 神锋无影的创伤 | `removal: { onlyBy: ['tech.purge'] }` |

### 固定 tick 的推进顺序（不许改）

```
1. 状态时长倒计时 → 2. 资源回复 → 3. 上限钳制
→ 4. 位置积分 → 5. 存在时间 → 6. 清理 → 7. tick++
```

### 为什么朝向存向量，不存角度

角度要变成方向就得用 `sin` / `cos`，而这两个函数**不保证跨 JS 引擎逐位一致**。
存单位向量就完全不需要三角函数。同理，距离用 `sqrt` 不用 `hypot`。

## 第 3 步：六步伤害管线

```
1 raw        原始     计算基础值
2 intercept  拦截     名刀、免疫（阻止它发生）
3 modify     修正     增减伤、伤害转治疗、亡灵反转
4 absorb     吸收     护盾、次数盾
5 apply      应用     真正扣血（引擎独占，钩子只能旁观）
6 after      后置     吸血、反伤、onDamaged
```

**为什么必须是管线而不是一行 `hp -= dmg`：** 名刀要"阻止这次伤害"，护盾要"先吃一部分"，
龟壳要"把伤害变成治疗" —— 这些都不是减法能表达的，而且它们必须**有序**。

**伤害和治疗共用这一条管线**，只是 `kind` 不同。否则禁疗、治疗加成、亡灵反转每条都要写两遍。

### 钩子的三个来源

技能图（第 4 步）、**状态**、**实体本身**。目前实现了后两个。

| 效果 | 怎么实现 |
|---|---|
| 名刀司命 | `stage: 'intercept'` + `when: 'onLethalDamage'` → 写 `pipeline.cancelled` |
| 护盾 | `stage: 'absorb'` + `absorb: { mode: 'damage', perStack: 500 }` |
| 次数盾 | 同上，`mode: 'hits'` —— **同一个位置，不同的消耗规则** |
| 龟壳 | `stage: 'modify'` → 写 `pipeline.reverse` |
| 亡灵受治疗受伤 | 挂在**实体**上的 `modify` 钩子 + `hitKindIs: 'heal'` |
| 反伤 | `stage: 'after'` + `side: 'target'` → 嵌套一次命中 |
| 吸血 | `stage: 'after'` + `side: 'source'` |

### 管线的四个伪属性

可以用现有的 `AttributePayload` 直接改，不需要新的载荷类型：

```
pipeline.amount      当前数值（add / mul / set）—— 减伤增伤就是它
pipeline.cancelled   设为非 0 = 拦截这次
pipeline.reverse     设为非 0 = 反转方向（伤害 ↔ 治疗）
pipeline.absorbed    已被吸收多少（只读）
```

### 触发链上限

`MAX_ACTION_DEPTH = 4`。没有它，"命中时附带子技能，子技能命中时又……"会无限递归，
一帧之内把栈打爆。双向反伤就是靠它才没炸。

### 动态参数（这一步才补上的）

```
ref: 'distance'      越近越疼
ref: 'missingHpPct'  残血增伤
ref: 'targetStacks'  按目标身上的层数加成
ref: 'elapsed'       按状态已经挂了多久
```

配合 `curve` 做映射。注意**动态参数本身只是一个数**，要变成倍率得靠曲线：
`{ ref: 'missingHpPct', curve: [[0, 1], [1, 2]] }` = 损失多少血就加多少倍。

## 第 4 步：阶段机

技能不是"按一下就打出去"，而是一条时间轴：

```
前摇 ──→ 释放 ──→ 后摇
 │        │        │
可打断   出效果    可取消
```

前摇、后摇、引导、蓄力**全是"阶段"的实例**，区别只有三个字段：

| 字段 | 作用 |
|---|---|
| `duration` | 多长。`-1` = 由玩家控制（蓄力） |
| `occupiesCaster` | 是否占用施法者 → 决定这是持续技还是脱手技 |
| `interrupt` | 打断等级：damage / control / none |

### 代价时机是玩家的设计自由

`Phase.cost` 挂在任意阶段上：

```
windup   0.1s  cost: { energy: 10 }      ← 早付：被打断就白付，便宜
release  0.05s
sustain  0.25s
recovery 0.1s  cost: { cooldown: 3 }     ← 晚付：绝对安全，贵
```

**被打断时代价不自动退还** —— 那正是"早付更便宜"这个定价的前提。
想退还就在 `phaseInterrupt` 规则里自己写一条（测试里有例子）。

### 打断

沉默 / 眩晕不只是"不能开始新技能"，还要**中断正在进行的技能**。
这条不做的话，控制效果对施法者几乎没用。

### 冷却存在存储属性上

`cd.<运行时执行的那个单位 id>`。这样"改冷却"就能用现有的 `AttributePayload` ——
`skill.cooldown` + `op: 'reset'` 就是**露娜的大招刷新**。

⚠ **"哪个 id"要看术式有没有挂序列**：普通术式 = **术式自己的 id**；
挂了序列 = **那一段的 id**（日志 46 的 `segmentKey()`，没写就 `<容器id>.seq<i>`），
所以序列术式的冷却记在**每一段**上、容器自己没有冷却。
⚠ 玩家 2026-09-21 指出**"CD 是技能的属性，键该挂在技能上"**（`cd.<技能id>`）——
判断是对的（现在这个键是**模型 A 的历史遗留**：那时每段本身就是一份独立术式），
但**这一轮没做**（要动 `compile.ts` 的段 id、`canActivate` 的遍历、
`pipeline.ts` 的 `skill.cooldown`、HUD 的读数、四个测试文件里写死的键名，
而且日志 46 把"段 id = 冷却键"记成**对外可观察的行为**）。
评估见 [日志 49](../docs/log/2026-09-27-49-cd-skip-and-hint.md)。

### 轮到的序列在冷却：不激活它，指针挪到下一条

玩家 2026-09-21 定的（日志 49）：

> 如果一条序列中有技能正在 CD，则不激活这条序列并给出提示，
> 然后指针指到下一条序列**等待按键触发**。

落点在 `cast.ts` 的 `pressSequence`：这一下**什么都不放**（不是"换一条打出去"——
一次按键打出去的技能换了人，玩家会以为按键乱放技能），`chain.next` +1，
**下一次按键**才试；一圈都在冷却 → **回到第一条在原位等待**（不空转、不无限找）。
**只有冷却走这条路**：能量 / 血契 / 沉默 / 忙碌**原样失败**，而且**不给冷却提示**
（给了玩家会以为"等一会儿就好"）。提示由 `PressResult.cooldown`（`CooldownNotice`）
带出"哪一条 + 还剩多久"，客户端只负责飘字（**不去闪任何一格**）。

### 技能图是管线钩子的第三个来源

一个 `activation: 'auto'` 的常驻术式，它的规则会变成管线钩子：

| 规则时机 | 映射到 |
|---|---|
| `onDamaged` | `modify` / 目标侧 |
| `onLethalDamage` | `intercept` / 目标侧 |
| `onHit` / `onCrit` / `onNonCrit` / `onMiss` | `after` / 施法者侧 |

名刀司命做成武器被动，走的就是这条路。

**`onDamaged` 映射到 `modify` 而不是 `after`** —— 玩家写 `onDamaged` 时想干的九成是
"减伤 / 转治疗 / 免疫"，这些必须在伤害落地**之前**改。放到 `after` 就来不及了。

### 动作打到谁身上：两套词汇别混

| | 回答什么 | 取值 |
|---|---|---|
| `Skill.targeting.mode` | 施法时**怎么选中**目标 | `self` / `directional` / `locked` / `auto` / `areapoint` |
| `Action.target` | 这条动作**作用在谁身上** | `'hit'`（默认，对面那个）/ `'self'` |

⚠ **瞄准在技能上**（2026-09-21 日志 47 起；以前是 `Technique.targeting`）：
每个技能各自解释玩家给的那**一个意图**（默认鼠标方向）。
术式和序列段都**不带瞄准**了 —— 校验器对着写回去的报
`TARGETING_MOVED_TO_SKILL`（防回潮），老存档里那份由 `store.ts` 读取时剥掉。

`skill.*` 属性永远属于**施法者**，不属于被打的人 —— 不这样做的话，
"击杀时重置本术式 CD" 会去改敌人身上的冷却。

## 投射物与 AI

### 投射物：第一种"会飞"的东西

前面所有载体都是"按下技能，伤害当场落地"。投射物带来三个新问题，
**这三件事在纸上讨论时一条都没提过**：

1. 命中发生在**未来某一刻**，那时候发射它的施法早就结束了
   → 所以它必须自己带着要执行的动作和归属（`ProjectileSpec`）
2. 飞行途中可能打空、可能飞过队友、可能飞过头
   → 所以每 tick 做碰撞判定
3. 穿透弹要记住已经打过谁 → `hitIds`

**投射物命中时没有 `cast`。** 所以它带的动作读不到 `skill.*` 和蓄力量 ——
那是设计如此，不是遗漏。想留信息就在发射时算好。

### AI：纪律 1 在这里兑现

> **目标选择一律按阵营动态查询，绝不写 `if (entity.id === playerId)`。**

现在的 AI 只有三条规则：找最近的敌人、按 `preferredRange` 保持距离、
间隔 `thinkInterval` 试一次技能。它是**确定性**的 —— 不用随机，
所以同一份场景跑一百次结果完全一样。

### 固定 tick 的顺序又长了两步

```
1 状态倒计时 → 2 资源回复 → 3 上限钳制 → 4 冷却 → 5 施法
→ 6 常驻 onTick → 7 AI 决策 → 8 位置积分 → 9 投射物碰撞
→ 10 存在时间 → 11 清理 → 12 tick++
```

**AI 排在移动前面**：先决定往哪走，再走。
**投射物碰撞排在移动后面**：先飞，再看撞到谁 —— 反过来会穿模。

### `tests/school.ts` —— 系别的推导规则 + 出厂内容核对

**系别**是派生章（技能按目录盖，见 `src/school.ts`），而术式的 `kind` 是显式字段 ——
老内容 / 老存档 / 老分享码里没有它，得由一条规则推出来。那条规则错起来是**静默的**：
一份术式被判成另一系，不给它算账、编辑器的技能库只给它一半技能，全程没有一处报错。

规则是**传递**的：**直接、或顺着 `sequences`（可能多级）引用了武器系技能 → weapon，
否则 magic**。⚠ 它**不是**"写了 `sequences` 就是武器术式" —— 那一句是旧世界的产物
（玩家 2026-09-21 拿「标记 · 瞬影」当场证伪：那是拿序列层做的**二段魔法技能**）。

这个文件钉三件事：规则的传递性（含**三层**序列、**内联的段**和**老形状的字符串**两半）、
**循环引用**不许爆栈也不许无限转、
以及**14 份出厂内容**用规则算出来的 `kind` 和文件里写的一个个对得上
（⚠ 日志 46：**17 → 13** —— 序列内联之后那四份子术式不再是独立文件；
⚠ 日志 48：**13 → 14** —— 拆「背水」多了一门常驻术式 `tech.last-stand`，
那两条写死的数（份数、magic 份数）**当场重数过**，不是"在旧值上加"）。

### `tests/smoke.ts` —— 校验器本身也要被测

校验器也是代码。没有测试的话，你会在"校验器说没问题"和"确实没问题"之间
失去区分能力 —— 那比没有校验器更危险。

技能用例和术式用例是**分开**的：分层之后两边的检查项完全不一样
（技能查结构和点数，术式查编排），混在一起测会以为"校验器漏报了"。

`tests/fixtures/broken.json` 里那个 `-1000 能量`是**故意写成天文数字**的：
这样无论汇率怎么调，它都是**很大一个正数**。
⚠ 2026-09-30（日志 57）：这一条原来写的是"合计落不进配平容差 ⇒ 测 `NOT_BALANCED`"，
而**容差和 `NOT_BALANCED` 都已经删掉了**（合计 ≥ 0 就能用）—— 用例还在，
测的是"点数算得出来、而且**不报错误**"那条路。

## 校验器的八组检查

| 组 | 查什么 |
|---|---|
| 结构 | 必填字段、枚举值、ruleSlots 是否够用 |
| 引用 | 规则的 phaseId 是否指向真实存在的阶段 |
| 阶段 | id 唯一、时长合法、蓄力阶段最多一个 |
| 规则 | id/order 唯一、onTick 有没有条件、条件是否可判断 |
| 动作与载荷 | 7 种载荷的必填字段、载体参数、数值是 const 还是 ref |
| 状态 | 标签、能力禁用、叠层、移除规则、管线钩子 |
| 目标 | 目标选择方式、有效目标标签 |
| 点数 | **技能**：只算账、不判对错（零件可以歪）<br>**术式**：必须配平到 0，花超了要拿血契付 |

## 写代码撞出来的 schema 缺口

这些问题在纸上讨论了十几轮都没暴露，写代码时全出来了。**这就是"先写代码再定稿"的价值。**

**第 1 步（校验器）：**

1. **`Phase` 缺 `points`** —— 账目里"前摇 0.4 秒"这一项没有地方存。
2. **`ResourcePayload` → `AttributePayload`** —— 原来"改能量"是独立载荷，
   但 CD 重置、暴击叠层、移速修改全都无处安放。**属性系统本该是核心，规则里却碰不到它。**
3. **`PointBalance` 去掉 `entries`** —— 明细改为推导，存档只留 `total` 和 `kind`。

**第 3 步（管线）：**

4. **`PipelineHook.side`** —— 钩子必须声明长在"被打"还是"打人"那一侧。
   **没有它，反伤会在自己打人时也触发**，无限弹到自己身上（真的踩到了，A 掉了 35 血）。
5. **`PipelineHook.absorb`** —— 护盾和次数盾是同一位置的不同消耗规则，需要一个字段声明池子形状。
6. **`EntityDef.hooks`** —— 亡灵反转是不需要状态的被动，钩子来源因此从两个变成三个。
7. **`Action.target`** —— 原来复用了 `Targeting`，但那是"怎么选目标"，
   和"这条动作打到谁身上"完全是两回事，`mode: 'target'` 根本不在枚举里。
8. **`ConditionType.hitKindIs`** —— 亡灵反转需要判断"这次是治疗还是伤害"。
9. **`PipelineHook.then` 改可选** —— 纯吸收型钩子（护盾）不需要动作，池子就是它的全部效果。

**第 4 步（阶段机）：**

10. **`enterPhase` 不能清空 `charge`** —— 清了的话，"释放阶段按蓄力量算伤害"永远只能读到 0。
11. **`onDamaged` 该映射到 `modify` 而不是 `after`** —— 减伤必须在伤害落地**之前**改。
12. **`skill.*` 属性永远属于施法者** —— 否则"击杀重置 CD"会去改敌人身上的冷却。
13. **打断后要立刻清理施法列表** —— 不然"已经中断了但还在数组里"。

**接桥时（第一次真跑内容）：**

14. **`Rule.every`：onTick 必须能限速** —— 不写 `every` 的话它是**每 tick 触发一次**，
    "每 0.5 秒扣 3 能量"会变成每秒扣 180 点。第一次跑熔岩护甲，能量直接掉到 **-518**。
15. **存储属性必须钳到 0 以上** —— 同上，负能量在别的系统里会连锁出怪事。
16. **属性路径要统一成 `char.*`** —— 规格里写 `char.energy.current`，
    模拟核里却是 `energy.current`，内容一加载就炸。
17. **`char.damageTaken` 必须是 1 不是 0** —— 它是"易伤/减伤"的挂载点（破甲 ×1.15）。
    而且管线里原本**根本不读它**，破甲挂了等于没挂。
18. **动作的默认目标要按技能的 `targeting` 决定** —— 只对 `self` 有效的技能，
    动作默认打自己。不这样分的话，熔岩护甲的"给自己挂减速"会挂到敌人头上。
    ⚠ 2026-09-21 日志 47 起这份瞄准在**技能**上（`Skill.targeting`），
    术式 / 序列段都不带它 —— 引擎读的仍然是**编译产物**里那一份
    （编译时从技能取，见 `sim/compile.ts` 的 `targetingOfChain`）。

**补内容时（让六个术式都真的跑起来）：**

19. **`Action.valid`：动作要能覆盖有效目标** —— 「无下限」术式本身是自我增益
    （`valid: ['self']`），但它的光环规则要打敌人。没有这个字段，光环挂到自己身上。
20. **`status` 载荷也得多目标** —— 只有 `damage`/`heal` 支持多目标时，
    `status` 会悄悄忽略 `delivery` 和 `valid`。同样表现为"光环挂给自己"。
21. **`char.moveScale`：移速得真的接进移动** —— 原来 `char.speed` 是个没人读的属性，
    减速状态挂了等于没挂。现在 `integrate()` 按 `char.moveScale` 缩放速度。
22. **状态修饰里的 `ref: 'distance'` 指的是"离施法者多远"** ——
    不这样定义的话，距离永远是 0，"越近越慢"会变成"永远最慢"。
23. **`auto` 被动的 `onCast` 要在挂上时跑一次** —— 否则它那些"装备代价"永远不落地，
    那部分点数是白赚的。
24. **查询属性必须带上下文** —— 有 `ref` 修饰的属性，不给 `ValueContext` 会直接抛错。
    这是故意的（静默算错更危险），但每个查询点都得记得传。

**补投射物与 AI 时：**

25. **投射物必须自己带着动作和归属** —— 命中时施法早就结束了，
    没人能告诉它"该执行什么、算谁的账"。
26. **带出去的动作要去掉 `delivery`** —— 否则命中时又"放一个投射物"，无限套娃。
27. **`tickProjectiles` 必须在位置积分之后** —— 先飞再判，反过来会穿模。
28. **AI 不会自己松蓄力键** —— 蓄力阶段（`duration: -1`）永远不会结束，
    结果就是 AI 举着剑站一辈子，蓄力技在它手里等于不存在。
    加了 `AiProfile.chargeTime`。

**做编辑器 + 拆两层模型时（这一批全是"玩家一问就暴露"）：**

29. **`Technique` 不该自带 phases 和 rules** —— 那等于每个术式只能有一个技能，
    "术式由若干技能组成"在数据结构上根本不成立。拆成 `Skill` + `Technique`
    之后才需要 `compileTechnique` 这一步（给阶段 id 加技能前缀，见上面）。
30. **`Rule.points` / `Phase.points` / `StatusDef.points` 全删** ——
    手写的价格表和数值是两份会漂移的东西。玩家把 30 伤害拖成 300，点数不动。
31. **状态的强度必须带符号，而且必须知道"挂给谁"** ——
    `Math.abs()` 让自我减益变成收益，于是"牺牲移速换伤害"整个循环是反的。
32. **规则位买卖的符号反了** —— 复杂度税变成了鼓励复杂。
33. **`onTick` 的频率要参与定价** —— 每 0.5 秒扣 3 点能量和每秒扣 3 点不是一回事。
34. **`balanceTolerance`** —— ⚠ 这条**已经被用户否掉了**（2026-09-30 日志 57：
   "既然正的容差没用，那容差就不该存在"）。当时的理由是定价表是有限项模型、
   硬追绝对 0 会让每个技能都差零点几；**现在的答案是"把点数取整 + 每个非零条目
   至少 1 点 + 差 1 点就算负值术式"**，而不是"给一条宽容线"。

**玩家玩到之后报出来的（这一批全是"读起来不对"）：**

35. **整本账的符号反了** —— `买 1 条规则位 +1.5` 读成"我赚了 1.5"。
    见上面第 4 条。**改完之后 UI 一行没动，颜色自己就对了。**
36. **`Rule.note` 里的数字会和数值脱节** —— 说明必须是生成的，
    note 只写设计意图（校验器加了 `NOTE_WITH_NUMBER`）。
37. **滑块不该有 300 个取值** —— 改成点表，平均 5.6 档。
38. **数值没有单位** —— `0.2` 要猜，`0.2 s` 不用。
39. **「收招 · 冷却」看不懂** —— 代价要单独分组，并且说清楚
    "数值是多少、阶段是什么时候付"。

## 点数账是"算"出来的

**点数一个字都不存进 JSON。** 它是内容的函数：`src/pricing.ts` 拿技能
（阶段时长、代价、规则里的伤害/治疗/状态）算出每一笔，加起来就是合计。

存档里曾经写过 `points.total`、`Rule.points`、`Phase.points` —— **全删了。**

### 为什么删

第一版把点数**手写**在规则和阶段上。在编辑器里实测的时候发现：
把"30 伤害"拖成"300 伤害"，点数**纹丝不动**。等于可以白嫖。

**手写的价格表和数值是两份会漂移的东西。** 现在只有一份。

### 符号约定：这是一本「额度账」

```
伤害 -2.6       消耗 2.6 点额度（效果）
扣能量 +1.5     提供 1.5 点额度（代价）
买规则位 -1.5   消耗 1.5 点额度（你要为更多规则位付账）
卖规则位 +1     提供 1 点额度（你放弃了复杂度）
```

**术式**的所有条目加起来必须**等于 0** —— 效果花掉的额度，正好由代价提供。
技能不必（它是零件，见上一节）。

**合计 < 0 = 花超了 = 负值术式** → 每次释放按 |合计| 消耗血契（不够就放不出来）。
**合计 > 0 = 额度还没用完** → 不超模，只是没配平。

### 方向错过四次，四次都没有东西报警

这一条值得单独写下来，因为四次都是"玩家一试就发现，代码全绿"：

| # | 错在哪 | 表现 |
|---|---|---|
| 1 | 点数手写在 JSON 上 | 改数值点数不动 |
| 2 | 状态的"强度"取了绝对值 | **给自己挂减益被算成收益** —— 加一条代价，点数反而变小，"牺牲 X 换 Y"整个循环是反的 |
| 3 | 规则位买卖两边符号都反了 | 规则越多的技能白拿越多点数，"复杂度税"变成了"鼓励复杂" |
| 4 | **规则位那一行反了，我却把整本账翻了过来** | 超模的判据跟着翻反了 |

第 4 条是玩家报的，而且报了两次 —— 值得完整记下来，因为**第一次我修错了方向**：

> 玩家第一次：**"买卖规则位得点数的正负反了。"**
> 我的理解：整本账的符号反了 → 把"收益"和"代价"全部对调。
>
> 玩家第二次：**"多出收益的不是超模技能，因为我已经付出代价了，
> 点数为负值的才是超模技能。"**

他第一次说的"反了"，指的是**那一行**：账本里别的东西消耗额度都是负的，
唯独"买规则位"（同样是消耗额度）显示成 **+1.5**。而我把整本账翻了过来，
顺手把超模的判据也翻反了。

**教训：账本的方向是从玩家那一侧定的，不能因为一行看着别扭就整本翻。**
现在只改那一行，其余全回来了。

（顺带一提，编辑器的 CSS 里绿色那条叫 `.gain`、红色那条叫 `.cost` ——
那个命名是照"额度账"写的，所以改回来之后**颜色自己就对了**。）

第 2 条还有个伴生问题：**一个状态对持有者是好是坏，和它对施法者是赚是亏，
是两件事。** 同一份"移速 ×0.7"：

```
挂在敌人身上 → 施法者赚了 → 收益 → 消耗额度（负）
挂在自己身上 → 施法者吃亏 → 代价 → 提供额度（正）
```

所以 `priceStatus` 必须知道 `toSelf`。少了这个参数，**自我减益会被定价成收益**。

这四条现在钉在 `tests/pricing.ts` 里。方向错了会有测试红，
不用等人去试。

### 汇率是标定出来的，不是拍的

`content/balance.json` 的 `rates` 是**数据**（改它不用改代码）。
但"10 点伤害算 1 点"这个 10 一开始是人拍的 —— 拍错的后果很具体：
七个技能一个个都配不平，玩家一打开编辑器满屏"多出 N 点代价"。

所以有了 `npm run calibrate`：

```
npm run calibrate            看看现在差多少，并给出建议的新汇率
npm run calibrate -- --write 直接写回 content/balance.json
```

**它把 pricing.ts 当黑盒**：不推导公式，只问"这组汇率下这七个技能各值多少分"，
然后在对数刻度上做梯度下降 + 坐标下降，最小化平方误差。没有随机数 ——
同样的内容跑一百次得到同一张表。

几个刻意的决定：

- **用了梯度下降，不是纯坐标下降。** 有些方向"单独动一个参数没用，一起动才有用"
  （比如同时放大 `damagePerPoint` 和 `energyPerPoint` 相当于换记账单位）。
  第一版就是纯坐标下降，`damagePerPoint` 一步都没动过，卡在那儿。
- **汇率被限制在原始值 ×/÷5 以内。** 优化器最喜欢把某个汇率推到边界上
  （把 `energyPerPoint` 推到 200，让所有能量代价几乎免费）—— 数学上误差更小，
  读起来是胡说。卡在一个数量级之内，剩下的残差才是**真的**信号。
- **标定时不比"容差"。** ⚠ 2026-09-30（日志 57）：**产品容差已经删掉了** ——
  标定现在拿到的账**本来就是整数**（逐条取整 + 每个非零条目至少 1 点），
  残差也是整数，判据改成"**差不到一格（1 点）**"（见 `tools/calibrate.ts` 的 `GRID`）。

### 点数改成整数（2026-09-30 日志 57）—— ⚠ **"配平容差"已经不存在了**

> 用户原话：**"点数之和大于 0 就能用，小于 0 就要支付血契才能用"**
> （"既然正的容差没用，那**容差就不该存在**"）

`balanceTolerance`（那个 ±2 点）**从 `content/balance.json` 里删掉了**，
代码里**没有任何地方**读它了。判据只剩一条：**合计 < 0 ⇒ 负值术式**（要付血契）、
**合计 ≥ 0 ⇒ 能用**（正好 0 和正数都算）。

同时**账上每一笔都是整数**：

| 规矩 | 怎么做 |
| --- | --- |
| **逐条取整 + 余数累积** | **最大余数法**（`pricing.ts` 的 `integerPointsOf`）：每条先取 `floor`（向 −∞，所以余数永远非负、正负条目一视同仁），要补的那几格由**合计**定，按**余数从大到小**分（余数相同按下标，保证稳定） |
| **各条之和 = 合计** | ⚠ **构造出来的**：合计就是各条加出来的那一个数。单独对合计取整会让"条目加起来对不上" —— 那正是这一条要修的毛病 |
| **每个非零条目至少 1 点** | 取 `floor` **之前**先把非零条目钳到 `±1` 起步（0.12 → 1、−0.85 → −1）。"账面上几乎免费"的条目（等待 0.2 秒 = 0.12 点、排布最便宜档 = 0.85 点）没有了 |
| **机器精度 = 1e-9** | `POINT_EPS`。**它不是容差**：只挡浮点噪声（1e-17 不会被钳成 ±1 点，0.9999999999999999 不会掉一格） |

⚠⚠ **两条实测后果**（照实记着，用户要签字的是它们）：

1. **`npm run calibrate` 的拟合变粗**：账是整数网格，绝对账又被"至少 1 点"的地板压过，
   所以拟合结果变了（见日志 57 第 3 节的新数字），**不是参数被调过**。
2. **几条小增量在整数账上被吃掉**：排布的"每米 0.1"（全行程 0.05~0.6 点）和
   "镜像角"（0.225 点）**跨不动 1 点这一格** —— 半径 0.5 米和 6 米在账上**都是 −1 点**。
   这几个数当初正是"为了让最贵那笔落进容差 2 点"被压低过的 ⇒ **现在可以重签**（日志 57 第 5 节）。

`npm run calibrate` 会把残差直接打出来，并在差出一格以上时明说：

> ⚠ 还有技能配不平。这说明**不只是汇率的问题**：
> 要么某个技能的数值本身不合理，要么定价表缺了一项（某个效果没被计价）。
> 这是给你看的信号，不是要把它抹平。

### 规则位：买是花掉，卖是赚到

```
买 N 条（上限高过基准）→ 你花掉了 N × buyCost    → 负
卖 N 条（上限低于基准）→ 你赚到了 N × sellGain   → 正
```

上限越高，你能塞的东西越多，所以要**付出**（复杂度税）；
主动把上限压下去是自缚，所以要**补偿**（让"极简技能"能把额度换成单点强度）。

`baseRuleSlots` 是 4 —— 出厂技能都声明 4（熔岩护甲 5，多出来那条它得付钱）。
基准值定高了等于**给每个技能发补贴**：少写几条规则就白拿点数，
而"省着写"本来就是它自己的收益，不该再算一遍。

点表里 `ruleSlots` 的档位就是 **0 1 2 3 4 5 6 7 8**，一个不缺。
玩家指出来过两次：下限 3 没有任何道理，中间跳档也说不通 ——
**它是条数，每一档都是一个不同的东西**，不像伤害那样"5 和 6 没区别"。

（9 档仍然是全项目最多的一个字段，但还在玩家定的"最多 10 个"那条线以内。
这也是为什么档位统计的判据是"七成在 6 档以内"而不是八成。）

## 打断等级：三档，不是布尔值

玩家原话：**"不应该所有技能都会被伤害打断，应该分成被伤害打断、被控制打断、
无法打断三个等级。"**

```jsonc
{ "id": "swing", "name": "挥砍", "duration": 0.2,
  "interrupt": "control" }      // 挨打不断，但吃硬控会断
```

| 等级 | 意思 | 点数 |
|---|---|---|
| `damage`（默认） | 受到任何伤害都会被打断 | 0 |
| `control` | 挨打不断，但被眩晕/沉默会断 | 半价收益 |
| `none` | 霸体帧，什么都不打断 | 全额收益 |

**为什么必须分三档**：只有"能/不能"两档的时候，一个"扛得住小伤害、
但吃硬控"的释放帧表达不出来 —— 而那恰恰是动作游戏里最常见的那种帧。
近战的挥砍如果被任何一点蹭伤打断，就根本没法玩。

### 实现上有一个坑

伤害是**管线的第 9 步**结算的，而施法推进是**第 5 步** —— 施法比伤害早。
想让"挨打就断"立刻反应，管线就得反过来 import 施法系统，那是个循环依赖。

所以伤害只在实体上留一个时间戳（`Entity.damagedTick`），施法那边自己比：

```ts
if (level === 'damage' && caster.damagedTick >= 0
    && caster.damagedTick === world.tick - 1) interrupt(...)
```

⚠ 那个 `>= 0` 不能省。没挨过打是 `-1`，而 `world.tick - 1` 在**第 0 个 tick**
也正好是 `-1` —— 少了这个判断，开局第一 tick 所有实体都会被当成"刚挨过打"，
什么技能都放不出来。**这个 bug 是测试抓到的：21 条断言同时变红。**

## 进入冷却的时机：前摇 / 释放 / 后摇

玩家原话：**"进入冷却的时间应该由玩家选择：在前摇、释放时还是后摇？
越靠前越先进冷却，但被打断的代价越大。"**

机制其实一直都在（代价在**进入阶段时**结算，而且**不退还**），
缺的是把它讲出来 —— 原来面板上写着「收招 · 冷却 3」，
玩家看到的是"收招这个阶段有个冷却"，而不是"我选了在收招时才进冷却"。

现在是一块独立的三选一：

```
进入冷却的时机
[前摇「起手」] [释放「挥砍」] [后摇「收招」] [没有冷却]
冷却时长 3 s
```

- **前摇** → 一按就进 CD。最先进冷却，但被打断就白付了（代价最大）
- **释放** → 打出去那一刻进 CD。被打断在释放之前就不付
- **后摇** → 挥完了才进 CD。最安全，也最晚

「释放」是**推出来的**：第一个真正打出效果（有 damage / heal 规则）的阶段。
两段式技能没有独立的释放帧，那时前摇和释放会指向同一个阶段 ——
面板上会出现两次，那是实话，不是 bug。

## 技能 / 术式：两层模型

**释放的是术式，修改的是技能。** 这一句是数据模型的全部。

```
技能 Skill        零件。有阶段、有规则、有代价。**玩家编辑的单位。**
   ↓ 引用
术式 Technique    编排。哪几个技能、按什么顺序、绑哪个键。**释放的单位。**
   ↓ 编译
编译产物          一条接起来的时间轴。**引擎唯一认的形态。**
```

```jsonc
// content/skills/cleave.json —— 裂地斩：起手 → 挥砍 → 收招
// ⚠ 瞄准（targeting）在**技能**上 —— 2026-09-21 日志 47 起术式那一层没有了
{ "id": "skill.cleave", "targeting": { "mode": "directional", "valid": ["enemy"], "range": 3 },
  "phases": [...], "rules": [...], "ruleSlots": 4 }

// 一份术式 = 技能列表（+ 可选的连接条件）。
// ⚠ 出厂不再带"两个技能接起来"的示范了（2026-09-21 清了示范术式）——
//    这是玩家在编辑器里拼出来的样子，形状和 tests/probes.ts 里那份「冲撞冲击」一样。
// ⚠ **术式不写 `targeting`**（每个技能自己那份说了算）
{ "id": "tech.mine-1", "activation": "press",
  "skills": ["skill.charge-dash", "skill.impact-burst"],
  "links": [{ "if": [{ "type": "prevHit" }] }] }
```

这就是 Noita 那种"把法术排成一列"的模型。**术式自己不带任何效果** ——
它的点数账就是它那些技能的总和。

### 为什么要有编译这一步

引擎不需要知道有两层，它只要一条时间轴。`compileTechnique` 把术式里
每个技能的阶段**接起来**，并且给 id 加上 `技能id#` 前缀：

```
skill.magic-bolt#cast      ← 两个技能都可能有叫 cast 的阶段
skill.cleave#windup
skill.cleave#swing
```

规则里的 `phaseId` 跟着一起改写，所以两边永远对得上。
**这样一来 `cast.ts` / `ai.ts` / `pipeline.ts` 一行都没改** ——
它们认的还是"一个有 phases 和 rules 的东西"。

前缀只在引擎内部存在。给人看的地方（运行器的时间轴、编辑器的规则列表）
用 `localId()` 去掉它。

### 这个改动是怎么被逼出来的

原本 `Technique` 自己带 phases 和 rules —— 那等于**每个术式只能有一个技能**，
"术式由若干技能组成"这句话在数据结构上根本不成立。

改的时候才发现校验器也没法拆：一个"技能"该不该配平到 0？
一个"术式"该不该有目标？分层的答案很清楚：

- **技能** 查结构（`validateSkill`）。**点数只算账，不判对错** —— 零件可以歪
- **术式** 查编排（`validateTechnique`）：激活方式、目标、引用了哪些技能，
  以及**配平到 0**（2026-09-21 定的：配平的责任在成品这一层）
- **引用是否存在** 是**编译期**的事（`compileTechnique`），因为那需要整个内容库

### 编辑一个技能之后必须重新编译

否则"改了等于没改"，而且玩家会以为是编辑器坏了。
`web/src/main.ts` 的 `applySkillEdit` 做的事：技能表换了 → 全量重编译 →
把新版本 `registerTechnique` 回世界。

八个术式的规模下，全量重编比"找出受影响的那些"更不容易出错。

## 把点表定下来时，出厂内容改了哪些数值

点表一旦收窄，**格子外的值就必须挪到格子上** —— 否则每个滑块都会带一个

| 裂地斩 | 起手 0.15→0.1、收招 0.25→0.2s | 同上；总时长 0.6→0.5s |
| 裂地斩 | 扇形半径 2.4→2.5m | 2.4 是个没有理由的数 |
| 无下限 | 减速 0.6→0.5s | 同上 |
| 熔岩护甲 | 开启 0.4→0.5s | 同上 |
| 熔岩护甲 | 三个状态 8→10s | 8 不在状态时长表上，往"一整场"那边靠 |
| 熔岩护甲 | 反伤范围 2→2.5m | 同上 |
| 熔岩护甲 | **反伤 15→30** | 标定之后它超预算 2.73 点；这一条是**加强它的身份**（标签就是"反伤"），不是为了凑数 |

| 裂魂 | 裂魂创伤 6→5s | 同上 |

## 注意

- `tests/fixtures/broken.json` 和 `broken-tech.json` 是**故意写坏的**，
  每一处错误都是精心放的。技能和术式各一份 —— 分层之后两边查的东西不一样。
- `content/balance.json` 用 `_comment` / `_xxx` 字段当注释 —— JSON 没有注释，这是常见做法。
- **改数值之后跑一遍 `npm run validate`**：点数会跟着变，可能就不配平了。
  用 `npm run calibrate` 看是汇率的问题还是内容的问题。
- **改数值的时候别把数字写进 `note`**：说明是生成的，手写的数字会脱节
  （校验器会报 `NOTE_WITH_NUMBER`）。
- **新内容要落在点表上**（`web/src/leaves.ts` 的 `VALUE_SETS`）。
  写了一个格子上没有的数不会报错，但那一格会被临时插进来、面板上标黄点 ——
  正确的做法是问一句"是表少了这一格，还是这个数本来就不该这么细"。
- `src/sim/` 下的代码**不许 import 任何 `node:` 模块**。跑 `npm run test:purity` 确认。
- 动作（`AttributePayload`）**只能改存储属性和管线伪属性**。派生属性要改，必须挂带
  `modifiers` 的状态 —— 因为动作是一次性的，而派生属性需要持续生效的修饰。
